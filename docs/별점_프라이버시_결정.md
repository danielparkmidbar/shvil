# 별점 시스템 — 프라이버시 트레이드오프와 결정 요청

> 2026-07-15. M7 착수 중 발견한 중대한 설계 긴장. 다니엘 쌤 결정 필요.
> 헌법 제9조(위치 비저장·불간섭) + M6에서 세운 예약 프라이버시와 충돌 가능.

---

## 0. 왜 이 문서가 필요한가

다니엘 쌤은 별점을 "상호 선택의 기준, 서로 감사를 전하는 수단"으로 요청하셨다.
그런데 별점을 순진하게 구현하면 **M6에서 그토록 공들여 숨긴 것을 도로 드러낸다.**

M6 예약 설계의 핵심:
- 예약(신청·승인)은 전부 E2E 암호 메시지 — **서버는 "누가 누구 집에 묵었는지 모른다."**
- 엔젤의 정확한 위치조차 서버에 없다 (R-4: 1km 눈금만).

그런데 별점을 서버에 저장하면:
- "리스트 A가 엔젤 B를 평가함" 레코드가 서버에 남는다.
- 이것은 곧 **"A가 B의 집에 묵었다"** 는 뜻이다 (별점 자격 = 실제 투숙).
- 서버가 해킹되면 **누가 누구 집에서 잤는지 관계망이 통째로 유출**된다.

즉, **별점 저장 위치가 이 시스템의 프라이버시 등급을 결정한다.** 이건 기능 디테일이
아니라 아키텍처 결정이라, 임의로 정하지 않고 보고한다 (CLAUDE.md 원칙).

---

## 1. 세 가지 설계안

### 안 A — 서버 집계 별점 (흔한 방식, 프라이버시 최약)
- 별점을 서버에 저장, 엔젤 프로필에 평균·개수 표시.
- 자격 검증: 예약 승인 서명을 서버에 제출 → 검증 → 1회 별점 허용.
- **장점**: 구현 단순, 평판이 위변조 불가(서버가 집계), 조작 저항 강함.
- **치명적 단점**: 서버가 투숙 관계망을 알게 된다. M6 프라이버시가 무너진다.
- **판정**: 헌법 제9조와 정면 충돌. **비권장.**

### 안 B — 지갑 보유 별점 + 서명된 후기 (프라이버시 최강)  ★권장
- 별점은 **받는 사람의 지갑에 보관**된다. 서버에 관계 레코드가 안 남는다.
- 흐름: 리스트가 엔젤을 평가 → 별점을 **엔젤의 기기 키로 암호화하지 않고, 리스트가
  서명**해서 엔젤에게 E2E 전송. 엔젤은 받은 서명된 별점들을 모아 **자기 프로필의
  집계(평균·개수)를 자발 공개**한다 (게스트북과 같은 자발 공개 모델).
- 위변조 방지(부분적): 각 별점은 제출자(리스트) 기기 키 서명 + 회원번호. 이 서명은
  **수신 지갑 안의 사적 사본**이 정직한 클라이언트에서 변조되지 않게만 지킨다.
  ⚠ **공개 집계는 그렇지 못하다** — 게시(POST /ratings) 때 서명이 서버로 가지 않으므로
  (서버가 서명을 검증하려면 평가자 신원을 알아야 해 프라이버시가 무너진다), **프로필
  주인이 서명 없는 가짜 5★를 자기 프로필에 날조 게시할 수 있다.** 이것이 안 B의
  내재적 한계다(위조 방지 = 서버가 평가자 신원 파악 = 프라이버시 붕괴). 따라서 공개
  별점은 "위변조 불가 평판"이 아니라 **참고 지표**로만 취급하고 UI도 그렇게 표시한다.
  다만 엔젤이 나쁜 별점을 **숨길** 수는 있다 → 이를 "N개 받음 / M개 공개"로 표시해
  **선택적 공개를 가시화**한다("받은 총 개수"는 피평가자 자발 신고 — 서버 카운터는
  관계망을 남기므로 두지 않는다).
- **장점**: 서버는 관계를 모른다. 헌법 정합. 감사 카드와 같은 사상(자발 공개).
- **단점**: 엔젤이 불리한 후기를 숨길 여지 → "공개율" 표시로 완화. 순수 신뢰도는
  안 A보다 약간 낮다 (하지만 선의 기반 커뮤니티엔 충분).

### 안 C — 이중 봉인 커밋-리빌 (보복 방지 특화, 복잡)
- 양측이 서로의 별점을 **제출하기 전엔 못 본다** (커밋), 둘 다 제출 또는 14일 경과 시
  동시 공개(리빌). 보복성 별점("네가 나 별 1개 줬으니 나도")을 원천 차단.
- 서버 저장이면 안 A의 프라이버시 문제 그대로. E2E 커밋-리빌로 하면 안 B에 보복
  방지를 얹은 형태 — 구현이 상당히 복잡(커밋 교환·타이머·양측 온라인 문제).
- **판정**: 가치 있으나 M7 1차엔 과함. 안 B로 시작하고 보복 방지는 후속 옵션.

## 2. 개발팀 권고

**안 B(지갑 보유 + 서명 후기) 채택, 보복 방지(안 C)는 후속.**

이유:
1. 헌법 제9조·M6 프라이버시를 지킨다 — 서버는 여전히 투숙 관계를 모른다.
2. 감사 카드·게스트북과 **동일한 사상**(자발 공개)이라 UX·코드가 일관된다.
3. "공개율 표시"로 선택적 숨김을 가시화하면, 선의 기반 커뮤니티에서 신뢰도는 충분하다.
4. 조작 저항은 서명으로 확보(점수 위조 불가). 남는 약점(숨김)은 치명적이지 않다.

이렇게 하면 별점은 "서버가 관리하는 평판 점수"가 아니라 **"당사자가 서명해 건네는
편지 같은 평가"** 가 된다 — 쉬빌의 대면·선의 철학과 맞다.

## 3. 별점의 자격과 범위 (안 B 기준 세부 — R-1)

| 항목 | 제안 |
|---|---|
| 척도 | 별 1~5 + 한 줄 후기(선택, 200자) |
| 자격 | 예약 승인(BOOKING_REPLY APPROVED) 또는 대면 지불(코인 전송 서명)이 있었던 관계. 노숙·무료 접대도 승인 이력이 있으면 자격 |
| 방향 | 상호 — 리스트→엔젤, 엔젤→리스트 양쪽 |
| 표시 | 프로필에 평균·개수·공개율. 개별 후기는 공개 선택분만 |
| 보복 방지 | 1차: 없음(안 B). 후속: 커밋-리빌(안 C) 옵션 |
| 삭제 | 받은 사람이 개별 후기 숨김 가능, 단 "받은 총 개수"는 숫자로 고정(숨김 가시화) |

## 4. 결정 결과 (2026-07-15 다니엘 쌤 — "별점 제안대로 진행")

- **R-1a ✅ 안 B (지갑 보유·서명 후기)**: 별점은 서버가 아니라 받는 사람의 지갑에
  보관. 서버는 투숙 관계를 모른다. 헌법 제9조·M6 프라이버시 유지.
- **R-1b ✅ 보복 방지는 후속**: 1차는 안 B 그대로. 커밋-리빌(안 C)은 후속 옵션.
- **R-1c ✅ 공개율 표시 채택**: "N개 받음 / M개 공개"로 선택적 숨김을 가시화.
  단 "받은 총 개수"는 위조·은폐 불가한 서버 카운터로 고정하지 **못한다** — 서버가
  카운트하면 접대 관계망이 남으므로(안 B 위배). 그래서 분모는 피평가자 자발 신고
  수치로 둔다(축소 신고로 부풀릴 여지는 남는 위험, R-1d 참조).

### R-1d — 근본 진위는 다니엘 쌤 결정 대기 (2026-07-16 적대적 검증 반영)

적대적 검증에서 드러난 한계: **공개 별점 집계를 프로필 주인이 날조할 수 있다**(본인이
가짜 5★ 다수를 임의 닉네임으로 자기 프로필에 게시). 이는 안 B의 내재적 한계다 —
위조를 막으려면 서버가 평가자 서명을 검증해야 하고, 그러려면 평가자 신원을 알아야
하며, 그 순간 "누가 누구를 평가함 = 누가 누구 집에 묵음"의 관계망이 서버에 남아
프라이버시가 붕괴한다.

- 이번 M7-B에서 한 것은 **완화 + 정직화**뿐이다:
  - 정직화: 코드 주석·이 문서·지갑/웹 UI가 별점을 "참고 지표 — 검증된 값이 아닙니다"로
    표시하고, "위변조 불가 평판" 같은 무자격 주장을 제거한다.
  - 완화: 수신 지갑이 받은 별점의 relationProof를 자기 로컬 이력과 대조해 낯선 가짜
    별점을 게시 후보에서 거른다(정직한 클라이언트 한정 — 서버 강제 아님). 게시
    쓰기에 피평가자당 상한(rate-limit)을 두어 무제한 날조 쓰기를 막는다.
- **결정 대기(다니엘 쌤)**: 자기 날조의 근본 해결책은 둘 중 하나이며 프라이버시와
  정면 트레이드오프라 개발팀이 임의로 정하지 않는다.
  - (가) 서버가 평가자 서명을 검증한다 → 프라이버시 순간 양보(관계 노출).
  - (나) 이중 봉인 커밋-리빌(안 C) → 프라이버시 유지, 구현 복잡.
  그때까지 공개 별점은 참고 지표로만 취급한다.

→ M7-B에서 이 방식(완화 + 정직화)으로 구현한다.
