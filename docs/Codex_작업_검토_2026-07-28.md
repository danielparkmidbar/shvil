## 2. 내 작업이 보존됐는가 — 사실로

### 보존됐다. 되돌려진 것이 하나도 없다.

```
git merge-base main gpt-wallet-release        → d6b1acb  (= main HEAD)
git merge-base --is-ancestor main gpt-...     → 참
git diff --diff-filter=D d6b1acb gpt-...      → 삭제된 파일 0건
```

- 내 커밋 4개(`8b1ba83` 이전의 `d6b1acb`·`2b2ff93`·`3dda10b`·`6223b86` …)가 **전부 조상에
  포함**된다. Codex는 내 위에 쌓았지, 내 것을 고쳐 쓰지 않았다.
- **삭제된 파일 0건.** 테스트 파일은 main 103개 → gpt 104개로 **늘었다**(신규
  `paymentAuthorization.test.ts` 1개).
- **`packages/shared`가 diff에 아예 없다.** 발행 요율·회랑 엔진·걷기 필터·원장 —
  화폐를 만드는 코드 전부가 무변경이다.

### 발행량이 그대로인지 실제로 돌려서 대조했다

두 워크트리에서 같은 헤비 시뮬을 각각 완주시켰다.

| | main (`d6b1acb`) | gpt (`015b0d7`) |
|---|---|---|
| 창 | 18,011 | 18,011 |
| ON_COURSE | 18,011 (100.00%) | 18,011 (100.00%) |
| 창 방출 거리 | 1,056.25 km | 1,056.25 km |
| **60일 완주** | **1,055.6 SHV** | **1,055.6 SHV** |
| 기각 | MISMATCH×4 TOO_FAST×1 VEHICLE×1 | 동일 |

**완전히 같다.** 45/30/25/20일 행까지 전부 일치한다.

### ★ 브리핑의 "1,077.9 SHV"는 Codex 탓이 아니다 — 내 탓이다

내 인계 브리핑에는 이스라엘 완주가 **1,077.9 SHV**로 적혀 있었다. 양쪽 다 1,055.6이
나오길래 `sim-report.txt`의 커밋 이력을 추적했다.

```
3dda10b (실물 이스라엘 등록)      → 방출 1077.95 km  → 1,077.9 SHV
2b2ff93 (내 커밋 — QR 압축·감사)  → 방출 1056.25 km  → 1,055.6 SHV
d6b1acb (내 마지막 커밋)          → 1056.25 km (동일)
gpt-wallet-release                → 1056.25 km (동일)
```

**1,077.9 → 1,055.6 하락은 Codex 분기점보다 두 커밋 앞선, 내 자신의 `2b2ff93`(회랑
폴리라인 투영 변경)에서 이미 일어났다.** 브리핑의 숫자가 낡았던 것이다.
그리고 현재 1,055.6은 등록 코스 실측 1,055.3 km에 대해 "1 km = 1 SHV"에 **오히려 더
정확하다**(100.1%). 이 항목은 Codex에게 책임을 물을 일이 아니다.

## 3. 잘한 것 — 공정하게

### (1) 내가 "빠졌다"고 보고했던 무결성 구멍을 실제로 메웠다

`server/src/playIntegrity.ts`에서 **main에는 `certDigests`를 환경변수로 채우는 배선이
아예 없었다.** 타입 선언(`certDigests?: string[]`)과 사용처만 있고, 값을 넣는 코드가
없었다 — 즉 main은 진짜 토큰이 와도 영구히 `CERT_DIGEST_NOT_CONFIGURED`였다.

Codex가 `SHVIL_ANDROID_CERT_DIGESTS` 파싱을 새로 넣었다. **회귀가 아니라 수리다.**

### (2) 무결성 판정이 느슨해진 곳이 하나도 없다 — 오히려 3군데 조여졌다

diff를 직접 읽어 확인했다.

- `REQUEST_PACKAGE_ABSENT` / `APP_PACKAGE_ABSENT` 신규 — 예전엔 패키지명이 **없으면**
  그냥 통과했다(`if (reqPkg && ...)`). 이제 부재도 UNVERIFIED.
- `TOKEN_TIMESTAMP_INVALID` 신규 — 예전엔 `ts > 0`이 아니면 신선도 검사를 **건너뛰었다.**
  이제 부재·0·NaN도 UNVERIFIED.
- `Math.abs(Date.now() - ts)` — **미래 시각 토큰(시계 조작)도 차단.** 예전엔 단방향이라
  통과했다.
- 서명 지문 실패는 여전히 강등이 아니라 `level = 'UNVERIFIED'` **고정**이다.

`server/test/integrity.test.ts`의 `+34줄`은 전부 신규 `describe('운영 환경 설정')`이다.
**기대값 하향·테스트 삭제 없음.**

### (3) 테스트를 숨기지 않았고, 오히려 플레이크를 없앴다

`vitest.config` 변경은 딱 두 가지다 — `testTimeout: 30_000`, 그리고 TypeScript 6
호환을 위한 `URL → .href`. `include` 패턴은 무변경이라 **테스트를 제외한 것이 없다.**

전체 스위트를 GPT 워크트리에서 직접 돌렸다:

| | shared | wallet | server | 합계 |
|---|---|---|---|---|
| gpt | 469 | 267 | 344 | **1,080 전부 통과** |

main은 기본 5초 타임아웃 때문에 CPU 경합 시 플레이크가 났다. 30초 상향은 그 플레이크를
실제로 없앤다.

### (4) 나머지 정당한 개선

- `expo-local-authentication` / `expo-screen-capture` / `@expo/app-integrity` 실제 설치·사용.
  예전의 **존재하지 않던 `react-native-google-play-integrity` import**를 실제 Expo 57
  공식 모듈로 교체했다.
- `RecoveryScreen`: 인증 전에는 니모닉을 JS 메모리에도 올리지 않는다. `usePreventScreenCapture`로
  스크린샷·화면 녹화 차단.
- `app.json`: `allowBackup: false`, `RECORD_AUDIO`·`SYSTEM_ALERT_WINDOW` 차단 —
  공격면을 줄였다.
- 버전 올림이 임의가 아니다. `expo@57.0.9`의 `bundledNativeModules.json`과 전수 대조한
  결과 **불일치 0건** — SDK가 지정한 정합값이다.
- `__DEV__` 격리 유지 — 개발용 `'dev-verified'` 토큰이 배포 빌드로 새지 않는다.

### 🔴 치명 3 — 생체 센서 없는 기기는 지불이 영구 불가 **[재현됨]**

`apps/wallet/src/screens/PayScreen.tsx:88-107`

`authorizePayment`가 `FALLBACK_REQUIRED`를 주면 Alert만 띄우고 `return`한다.
**우회로가 하나도 없다.**

```
if (authorization.status === 'FALLBACK_REQUIRED') {
  Alert.alert('지불 보호를 설정해 주세요', '...생체 인증을 등록한 뒤 다시 시도해 주세요.');
  return;
}
```

`FALLBACK_REQUIRED`는 `hasHardwareAsync()`(지문·얼굴 스캐너가 있는가) 또는
`isEnrolledAsync()`(등록됐는가)가 false일 때 나온다. 즉 **지문 센서 없는 구형 폰**,
**PIN·패턴만 걸어 둔 폰**은 지불 버튼을 눌러도 영원히 서명되지 않는다.
설정에서 고칠 수도 없다 — 센서 자체가 없으니까.

`paymentAuthorization.ts`는 `disableDeviceFallback: false`로 'PIN 폴백 허용'을
의도했지만, **그 앞의 `hasHardwareAsync` 게이트가 `authenticateAsync` 호출 자체를 막아
의도한 PIN 폴백에 도달할 수 없다.**

**실행 재현 — PayScreen 분기를 그대로 옮겨 운영 모듈로 실행:**

```
✗ 생체 센서 없는 구형 폰         → 지불 불가
✗ PIN만 걸어 둔 폰 (생체 미등록)  → 지불 불가
✗ 네이티브 모듈 없는 환경         → 지불 불가
✗ 약한 생체만 있는 저가폰         → 지불 불가  (biometricsSecurityLevel:'strong' 고정)
✗ lockout (젖은 손·센서 노후)     → 지불 불가
✗ 센서 고장                      → 지불 불가
✓ 생체 있는 정상 폰              → 지불 성공
```

`wallet.payCharge` 호출부는 `PayScreen.tsx:78` **하나뿐**이라 다른 지불 경로도 없다.

**방향이 거꾸로다.** 같은 커밋의 `RecoveryScreen`에는 `FALLBACK_REQUIRED`에
'보호 없이 보기' / '보호 없이 복구' 탈출구가 있다. **더 위험한 동작(니모닉 노출·키 교체)에는
탈출구가 있고, 가장 평범한 동작(지불)에는 없다.**

헌법 위반: **0층 신성불가침**(걸어서 만든 코인을 쓸 수 없다), **제7조 순환**(받은 사람이
다시 베푸는 경로가 끊긴다), **제8조**(작동이 성장보다 먼저).
트레일에서 쓰는 폰이 최신 기종이라는 보장이 없다.

### 🟠 높음 — 복구 문구를 영영 못 보게 되는 경로 **[코드 확정]**

`apps/wallet/src/screens/RecoveryScreen.tsx:47-58`

`FALLBACK_REQUIRED`에는 '보호 없이 보기' 탈출구를 주지만, **`DENIED`에는 안 준다.**

생체가 등록돼 있는데 센서가 고장났거나 lockout이면 → `hasHardware`·`isEnrolled`는 true
→ `authenticateAsync` 실패 → `DENIED` → **복구 문구를 볼 방법이 없다.**
폰을 잃기 전에 백업을 못 하면 **확정 코인이 영구 상실**된다.

우회로는 '기기 설정에서 생체를 삭제 → 재시도 → FALLBACK_REQUIRED → 보호 없이 보기'뿐인데,
앱이 이걸 안내하지 않는다. Alert 문구는 "복구 문구를 열지 않았습니다"가 전부다.


권한 판정이 실패하면 `Pedometer.watchStepCount`를 **아예 구독하지 않는다.**
기존 main 코드는 권한 결과와 무관하게 구독했으므로 권한이 뒤늦게 떨어져도 스스로 살아났다.

- **안드로이드는 안전하다** — Q 미만은 빈 권한 배열이 vacuous하게 granted로 집계되고,
  Q 이상은 `ACTIVITY_RECOGNITION` 정식 요청이다.
- **iOS가 위험하다.** `EXMotionPermissionRequester.m`은 `CMPedometer.authorizationStatus()`가
  `NotDetermined`면 `'undetermined'`를 돌려준다. 그 순간 `pedometerAvailable = false`로
  고정되고, `walkService`는 세션 내내 **다시 확인하지 않는다** → 모든 창 NO_STEPS → 0 SHV.
  사용자가 걷기를 껐다 켜야만 복구된다. **원래 되던 iPhone이 이번 변경으로 못 걷게 되는 경로다.**

제안(수정하지 않았다): `watchStepCount`는 조건 없이 구독하고 `pedometerAvailable`은
화면 표시용 플래그로만 쓰거나, 첫 창 마감 때 권한을 한 번 더 확인해 재구독.

### 🟡 중간 — 성공한 시작이 빨간 '오류'로 표시된다 **[코드 확정]**

`walkService.ts:170-173` / `HomeScreen.tsx:102`

백그라운드 없이 정상 시작한 경우에도 경고 문구를 **실패 필드**(`walkStartError`)에 싣는다.
`HomeScreen`은 이 필드를 `styles.error`(굵은 빨강)에 ⚠를 붙여 렌더한다.

**역전이 핵심이다** — 이 경고는 `#backgroundLocationStarted === false`일 때만 뜬다.
즉 **실제로 0 SHV가 나는 '항상 허용' 경로에서는 경고가 사라지고**, 상대적으로 안전한
'화면 켠 채' 경로에서만 빨간 경고가 뜬다. 정확히 반대다.

실패/경고 필드가 섞이면 진짜 실패가 묻힌다(제3조의 표시 계층 훼손).

### 🟡 중간 — Play Integrity는 여전히 켜져 있지 않다 **[코드 확정] (은폐 아님)**

`apps/wallet/eas.json` / `integrity.ts:96`

`EXPO_PUBLIC_PLAY_CLOUD_PROJECT_NUMBER`를 저장소 전수 검색한 결과 **값이 정의된 곳이
없다** — 코드 참조 1건 + 문서 언급 2건뿐. `eas.json`의 preview·production env에는
`EXPO_PUBLIC_DIRECTORY_URL` 하나뿐이다.

`EXPO_PUBLIC_*`는 **빌드 시점에 정적으로 인라인되는 값**이라, 지금 EAS로 빌드하면
모든 기기가 `PLAY_CLOUD_PROJECT_NOT_CONFIGURED` → `token: ''` → 서버 UNVERIFIED로
수렴한다. **무결성 배관은 완성됐지만 전원이 안 들어와 있다.**

**이건 회귀가 아니다** — main도 실토큰을 만든 적이 없다. fail-closed이므로 안전한 방향으로
틀렸고, README:66과 인계서에 "남은 단계"로 명시돼 있어 **제3조 정직화를 지켰다.**
다만 인계서의 "핵심 보강" 목록에 "Play Integrity 요청과 서버 검증 연결"이 나란히 적혀
있어 **이미 작동한다고 오독될 여지**가 있다.

### 🟡 중간 — `RECEIVE_BOOT_COMPLETED` 미선언 **[가설]**

`apps/wallet/app.json`

위 persisted job은 `setPersisted(true)`로 스케줄된다. 안드로이드는 persisted job을
스케줄하는 앱이 `RECEIVE_BOOT_COMPLETED` 권한을 갖고 있지 않으면
`JobScheduler.schedule()`에서 `IllegalArgumentException`을 던진다.

그런데 `TaskManagerUtils.java:152-158`의 try/catch는 **`IllegalStateException`만 잡는다.**
`node_modules` 안 어떤 AndroidManifest.xml도 `RECEIVE_BOOT_COMPLETED`를 선언하지 않으며
(전수 검색 0건), 새 `app.json`의 `android.permissions`는 `ACTIVITY_RECOGNITION` 하나로
줄어 있어 이 권한도 없다.

실기기에서 '항상 허용' 후 첫 백그라운드 픽스가 올 때 **크래시 또는 좌표 전량 유실**이
발생할 수 있다. prebuild 템플릿 매니페스트가 이 권한을 넣어 준다면 무해하므로
**'가능성'으로 보고한다.**

확인법: preview APK 설치 → 화면 끄고 걷기 → `adb logcat | grep -i "TaskManagerUtils"`

## 6. 병합 권고

### 병합 자체는 무충돌 fast-forward다

```
git merge-tree --write-tree main gpt-wallet-release  → 3603588...
git rev-parse gpt-wallet-release^{tree}              → 3603588...   (동일)
```

**병합 결과 트리가 gpt-wallet-release 트리와 완전히 같다 = 충돌 0건, fast-forward.**
기술적 위험은 없다. (실제 병합은 하지 않았다.)

### 권고: **조건부 병합 — 결정 3건을 먼저 받는다**

그대로 병합해도 저장소는 안 깨진다. **문제는 저장소가 아니라 배포다.**
지금 상태로 실기기에 내면 아래가 실사용자에게 그대로 간다:

1. 화면 끄고 온종일 걸어도 **0 SHV** — 그런데 상단 알림은 기록 중이라고 말한다
2. 그 사이 **좌표는 OS 디스크에 남는다** (헌법 제9조)
3. **지문 센서 없는 폰은 걸어서 만든 코인을 못 쓴다** (0층·제7조)

세 가지 선택지:

| | 방식 | 설명 |
|---|---|---|
| **ⓐ** | **부분 병합 — 권장** | 무결성·빌드·테스트 개선(§3 전부)은 명백히 이득이니 살리고, **백그라운드 추적 기능만 꺼서** 다음 후보로 미룬다. 지불 게이트에는 탈출구를 넣는다. 0층이 즉시 회복된다 |
| **ⓑ** | 전체 병합 후 수리 | fast-forward로 그대로 받고, 치명 3건을 별도 커밋으로 고친 뒤 배포. 이력이 깔끔하다 |
| **ⓒ** | 실기기 먼저 | preview APK를 1대에 깔아 치명 1·2·중간(부팅 권한)을 실물로 확인한 뒤 결정. 가장 느리지만 가장 확실하다 |

**어느 쪽이든 배포 전에 반드시 정해야 할 3건:**

1. **화면 꺼짐 추적을 이대로 낼 것인가.** 인계서가 요구한 실기기 확인 1번
   ("항상 허용 후 화면 끄고 10분 걸어 창이 계속 누적되는지")은 **실패할 것으로 예측된다.**
2. **지불에 탈출구를 줄 것인가.** 지금은 지문 센서 없는 폰이 걸어서 만든 코인을 영영
   못 쓴다. RecoveryScreen에는 탈출구가 있는데 지불에는 없다 — 방향이 거꾸로다.
3. **Play Integrity를 켜고 낼 것인가, 끈 채로 낼 것인가.** 배관은 완성됐고 네이티브도
   APK에 실려 있으나 프로젝트 번호가 없어 전 기기 UNVERIFIED다. fail-closed라 안전한
   방향이고 문서에 명시돼 있어 은폐는 아니다.

## 부록 — 검토 방법
