## v1.0 개정 — 2026-07-13~15 확정 사항 (본문에 우선)

### A. 폐기·정정 (v0.9 본문 중 더 이상 유효하지 않은 것)

1. **"1단계 MVP 원장은 서버 원장(포인트) 기반" — 폐기.** 코인은 각 사용자의
   스마트폰에서 생성·서명된다. 서버 발행·중앙 원장·거래 승인 서버는 어느 단계에도
   없다 (헌법·지시서 0장). 온체인 전환 계획도 없다 — SHV는 온체인이 아니며,
   스테이블코인(USDC on Base)은 마켓 결제 전용이다.
2. **요율 표의 "코스 이탈 감액 1/10" — 폐기 (T-1, 2026-07-15).** 설정 트레일을
   벗어나면 일상 걸음과 동일한 미세 요율 **1/1,000**. 사용자에게는
   "트레일 위 = 정상 형성, 벗어나면 = 조금"의 직관적 2단계뿐이다.
3. 잠자리 단일 선택(방/소파/텐트 중 하나 + 총원) — **복수 선택으로 대체** (아래 D-3).

### B. 제1원칙 — 극단적 단순함 (2026-07-15 다니엘 쌤)

- **설치하고 걸으면 끝.** 가입·설정·인증 없이 코인이 형성된다. 가입(전화 OTP+이메일)은
  관계가 시작될 때만 필요하다: 엔젤 등록·메신저·마켓.
- 설명서 없이 직관적으로: 트레일 위에서는 정상 형성, 벗어나면 조금 — 화면의 생성
  속도 차이로 스스로 배운다.
- 그 위의 모든 기능(예약·보물·QR·자전거)은 **운영자가 얹는 선택 계층**이며 기본
  걷기 경험에 복잡성을 추가하지 않는다 (docs/몸인증_보물마이닝_설계.md 0장).

### C. 역할 분담 — "사이트는 문, 지갑이 집" (2026-07-14)

- **웹 로그인은 없다.** 두 웹(shvilangel.org/shvilist.org)은 계정 없이 설명·공개
  열람·가입 시작·앱 다운로드만. 모든 회원 기능은 지갑 앱이다 (키가 기기에만 있으므로).
- 웹은 여행 준비(노트북·큰 지도·한눈에 보는 정보), 앱은 여행 중 모든 것.
- "양쪽 기능 동일"은 웹 로그인이 아니라 **한 앱의 이중 모드(리스트/엔젤)**로 이룬다.

### D. 구현 완료된 확정 기능 (M5·M6, 2026-07-14~15)

1. **위치 프라이버시 (R-4)**: 공개 지도에는 엔젤의 **대략 위치(0.01°≈1km 눈금) +
   닉네임만**. 정확 좌표·주소·연락처는 엔젤의 폰에만 저장되고, **투숙을 승인한
   손님에게만 E2E 메시지로 전달**된다. 지갑이 전송 전에 눈금화하고 서버도 방어적으로
   재눈금화한다 — 서버는 정확한 집 위치를 모른다.
2. **예약 (M6)**: 투숙 신청(BOOKING_REQUEST)·응답(BOOKING_REPLY: 승인/거부/대안
   날짜)은 전부 **E2E 암호 메시지** — 서버에 예약 엔드포인트가 없다. 서버가 아는 것은
   엔젤이 자발 공개한 "지금 손님 받기 가능" boolean과 갱신 시각뿐 (R-3). 신청자
   프로필(닉네임+가입시기+여정 한 줄, R-2)은 신청자가 동의해 첨부하며 서버에
   저장되지 않는다. 엔젤 모드에 **"손님" 탭**(수신함·승인/거부), 내 엔젤 포인트에
   **가능 스위치** 신설.
3. **잠자리 유형별 수용 인원 (2026-07-15)**: 방 베드 N명 + 거실 소파 N명 + 마당
   텐트 N명 — 복수 선택, 총원은 합계. `beds { room, sofa, tent }`. 기존 단일
   선택 데이터는 하위 호환 표시.
4. 보안 (M4 감사 반영): 니모닉(BIP-39) 복구, 발행 키 봉인 저장(KEK), 배포 서명
   +TOFU 핀, 회원 증서(기기 결속), 동기화 지문 기반 이중 사용 사후 탐지.

## 0. 프로젝트 개요와 확정 파라미터

쉬빌 코인(Shvil Coin) 프로젝트는 순례길을 걷는 사람(**쉬빌리스트**)이 걸은 거리만큼 코인(**SHV**)을 형성하고, 숙소·식사·샤워를 제공하는 **쉬빌 엔젤**에게 QR로 대면 지불하는 생태계입니다. 하나의 앱이 쉬빌리스트 모드와 엔젤 모드를 모두 담으며, "오늘의 엔젤이 내일의 쉬빌리스트가 되는" 순환을 지원합니다.

### 0.1 확정 파라미터 (변경 금지)

| 항목 | 값 |
|---|---|
| 적립 비율 | **1km = 1 SHV** |
| 1일 적립 상한 | **40 SHV** |
| 권장 가격 — 잠자리 | 10 SHV |
| 권장 가격 — 식사 | 5 SHV |
| 권장 가격 — 샤워 | 3 SHV |
| 권장 가격 — 풀 패키지(잠자리+식사+샤워) | 18 SHV |
| 광야 무통신 구간 대응 | **필수** (오프라인 걷기 기록 + 오프라인 소액 지불) |
| 1단계 MVP 원장 | **서버 원장(포인트) 기반**, 온체인 전환은 2단계 |

### 0.2 설계 기본 방향

1. **오프라인 퍼스트(Offline-first)**: 광야 구간에서 통신이 며칠간 끊길 수 있다는 것을 예외가 아닌 기본 조건으로 설계한다. 모든 핵심 기능(걷기 기록, 소액 지불, 일지)은 로컬에서 완결되고, 통신 복구 시 서버와 동기화한다.
2. **하나의 계정, 두 개의 모드**: 쉬빌리스트/엔젤은 별도 계정이 아니라 같은 계정의 두 가지 얼굴이다. 지갑(잔액)은 하나로 공유된다.
3. **대면 신뢰 우선**: 결제는 원칙적으로 두 사람이 마주 보고 QR을 주고받는 대면 거래다. 원격 송금은 MVP 범위에서 제외한다.
4. **저사양·저배터리 환경 존중**: 순례자는 며칠간 충전하지 못할 수 있다. GPS 상시 추적 대신 적응형 샘플링과 만보계 센서 병행을 기본으로 한다.

## 1. 정보 구조(IA)와 화면 흐름

### 1.1 전체 IA 트리

```
쉬빌 지갑 앱
├── 온보딩
│   ├── 스플래시 / 언어 선택
│   ├── 회원가입·로그인 (전화번호 OTP 또는 이메일)
│   ├── 프로필 설정 (닉네임, 사진, 성별 공개 여부)
│   ├── 권한 요청 (위치, 신체활동, 카메라, 알림)
│   └── 모드 선택 안내 ("걸으실 건가요, 맞이하실 건가요?")
│
├── [쉬빌리스트 모드]
│   ├── 홈 (오늘 요약 대시보드)
│   ├── 걷기 기록 (시작/일시정지/종료, 실시간 트래킹)
│   ├── 지갑 (잔액, 거래 내역, QR 스캔 지불)
│   ├── 엔젤 지도 (주변 엔젤 탐색, 필터, 상세)
│   └── 일지 (하루별 기록: 거리·경로·사진·메모)
│
├── [엔젤 모드]
│   ├── 수령 홈 (금액 입력 → QR 제시)
│   ├── 제공 서비스 등록·관리
│   │   └── 공간 유형: 방 / 거실 / 마당 / 처마 + 서비스: 식사 / 샤워
│   ├── 평판 (받은 후기, 엔젤 배지)
│   └── 알림 (근처 쉬빌리스트 접근, 수령 완료, 후기 도착)
│
├── [공통]
│   ├── 모드 전환 스위치 (상단 고정)
│   ├── 안전 센터 (비상 연락, 위치 공유, 여성 엔젤 필터 설정)
│   ├── 설정 (계정, 언어, 배터리 절약 수준, 오프라인 데이터 관리)
│   └── 동기화 상태 표시 (오프라인 대기 건수)
```

### 1.2 하단 탭 구성

**쉬빌리스트 모드** (5탭): `홈` · `걷기` · `지갑` · `지도` · `일지`
**엔젤 모드** (4탭): `수령` · `내 서비스` · `평판` · `알림`

모드에 따라 탭 자체가 교체된다. 지갑 잔액은 두 모드 모두 상단 헤더에 상시 노출한다(하나의 지갑임을 시각적으로 강조).

### 1.3 주요 화면 흐름 (사용자 여정)

**여정 A — 쉬빌리스트의 하루**
```
아침: 홈 → [걷기 시작] → (백그라운드 트래킹, 오프라인 가능)
낮:   걷기 화면에서 진행률 확인 (20km 목표 링)
저녁: [걷기 종료] → 오늘 18.4km = 18 SHV 적립 확인
     → 지도 탭 → 근처 엔젤 탐색 → 엔젤 상세 → 도보 안내
     → 엔젤 집 도착 → 엔젤이 QR 제시 → 지갑 탭 [스캔] → 18 SHV 지불
밤:   일지 탭 → 오늘 경로 지도 + 사진 + 메모 저장 → 엔젤 후기 작성
```

**여정 B — 엔젤의 저녁**
```
오후: 알림 "3km 근처에 쉬빌리스트 2명이 걷고 있어요" (선택적 기능)
저녁: 쉬빌리스트 도착 → 모드 전환 스위치 → 엔젤 모드
     → 수령 홈 → 서비스 선택(풀 패키지 18 SHV) → QR 생성·제시
     → 상대 스캔 → 양측 완료 화면 → 평판 탭에서 후기 확인
```

**여정 C — 순환 (엔젤 → 쉬빌리스트)**
```
엔젤이 모은 SHV 잔액 → 다음 휴가에 본인이 순례를 떠남
→ 모드 전환 → 쉬빌리스트 모드 → 모은 SHV + 걸어서 적립하는 SHV로 여정
```

### 1.4 모드 전환 UX

- **위치**: 모든 화면 상단 헤더 우측에 토글 스위치(🥾 걷는 중 / 🏠 맞이하는 중). 한 손 조작 가능 위치.
- **전환 동작**: 탭 1회 → 0.3초 플립 애니메이션과 함께 탭바·홈 화면이 교체된다. 확인 팝업 없음(전환 비용을 최소화해 순환 정체성을 강화).
- **상태 유지**: 걷기 기록 중에 엔젤 모드로 전환해도 트래킹은 백그라운드에서 계속된다. 헤더에 "걷기 기록 진행 중" 미니 배너를 유지한다.
- **최초 전환 시**: 엔젤 모드 첫 진입에는 서비스 등록 온보딩(3단계 위저드)으로 안내한다.
- **기본 모드 기억**: 마지막 사용 모드로 앱이 열린다. 설정에서 기본 모드 고정 가능.

## 3. QR 대면 지불 UX 상세

### 3.1 기본 원칙

- **방향**: 엔젤(수취인)이 금액이 담긴 QR을 **제시**하고, 쉬빌리스트(지불인)가 **스캔**한다. 금액 입력 실수를 수취인 쪽에서 한 번, 지불인 확인에서 한 번, 총 두 번 검증한다.
- **QR 페이로드**: 서명된 1회용 청구서(invoice). 포함 필드 — 엔젤 ID, 금액, 서비스 항목, 생성 시각, 유효기간(5분), 논스(nonce), 엔젤 기기 서명.
- **이중 지불 방지(온라인)**: 서버가 논스를 1회만 소비 처리.
- **재사용 방지(오프라인)**: 논스 + 유효기간 + 로컬 소비 기록으로 동일 QR 재스캔 차단.

### 3.2 온라인 표준 흐름

```
엔젤                          쉬빌리스트                    서버
─────                        ──────────                   ─────
① 서비스 선택 → 금액 확정
② QR 생성·제시  ──────────▶  ③ 지갑 탭 [스캔]
                             ④ 확인 시트: 수취인·금액·내역
                             ⑤ [밀어서 지불] ───────────▶ ⑥ 원장 이체 처리
⑧ 수령 완료 알림 ◀─────────────────────────────────────  ⑦ 양측에 확정 푸시
⑨ 양측 완료 화면 (효과음 + 햅틱 동시 발생 — 대면 신뢰 강화)
```
- ④→⑤ 사이 잔액 부족 시: "잔액 114 SHV, 4 SHV 부족" + 부분 지불 제안(엔젤 동의 UI: 엔젤 기기에서 금액 수정 후 QR 재생성).
- 전 과정 목표 시간: **10초 이내** (선택 2탭 + 스캔 1초 + 슬라이드 1회).

### 3.3 오프라인 흐름 (광야 구간, 양측 모두 무통신)

전제: 두 기기가 물리적으로 마주 보고 있으므로 **QR 자체를 통신 채널로 사용**한다. 별도 블루투스 페어링 없이 "QR 두 번 주고받기"로 완결한다.

```
① 엔젤: 오프라인 상태에서도 청구 QR 생성 가능
   (QR에 엔젤 기기 서명 + 논스 + 타임스탬프 포함)
② 쉬빌리스트: 스캔 → 로컬 잔액 검증(확정 잔액 기준) → [밀어서 지불]
③ 쉬빌리스트 앱이 "지불 확인 QR" 생성 (지불인 서명 포함) → 화면 제시
④ 엔젤이 역스캔 → 엔젤 로컬 원장에 "수령(미확정)" 기록
⑤ 양측 완료 화면: "⏳ 오프라인 거래 — 통신 연결 시 자동 확정" 배지
⑥ 어느 한쪽이라도 온라인 복귀 시 서명된 거래 영수증을 서버로 전송
   → 서버가 양측 서명 검증 후 원장 확정 → 양측 푸시 "✓ 확정됨"
```

**오프라인 리스크 통제 (MVP 정책)**
- 오프라인 지불 한도: 1회 최대 **20 SHV**, 미동기화 누적 최대 **60 SHV**(약 3일치). 초과 시 "통신 지역에서 동기화 후 이용" 안내.
- 오프라인 지불은 **확정 잔액**(서버가 마지막으로 승인한 잔액)에서만 차감. 미확정 걷기 적립분으로는 오프라인 지불 불가 → 이중 지불 구조적 차단.
- 동기화 시 충돌(잔액 부족 등) 발생하면: 거래는 "보류" 상태로 전환, 양측에 알림, 지불인의 다음 적립분에서 자동 우선 차감(마이너스 허용 한도 -20 SHV). 대면 신뢰 기반 커뮤니티 특성상 악의적 사례는 평판·계정 제재로 처리.

### 3.4 예외 처리

| 상황 | 처리 |
|---|---|
| QR 유효기간(5분) 만료 | 스캔 시 "만료된 QR — 엔젤에게 새로 요청" 안내 |
| 동일 QR 재스캔 | "이미 지불된 청구서" 차단 |
| 스캔 실패(역광/카메라) | 3회 실패 시 6자리 숫자 코드 수동 입력 폴백 |
| 지불 후 즉시 취소 | 완료 후 10분 내 양측 합의 취소 버튼(양쪽 모두 탭해야 성립) |
| 화면 파손 기기 | 엔젤의 인쇄된 고정 QR(계정 QR) 스캔 → 지불인이 금액 직접 입력 → 엔젤 구두 확인 (온라인 시에만 허용) |

## 4. 걷기 기록 UX

### 4.1 시작 / 일시정지 / 종료

- **시작**: 홈 또는 걷기 탭의 대형 버튼 1탭. GPS 워밍업(첫 위치 확보) 동안 "위치 잡는 중…" 상태 표시하되 기록은 즉시 시작(걸음 센서 기반). 아침 출발 루틴을 위해 "어제와 같은 시각에 시작 알림" 옵션 제공.
- **일시정지**: 수동 일시정지 + **자동 일시정지**(10분 이상 이동 없음 감지 시 자동 정지, 이동 재개 시 자동 재시작 — 식사·휴식 시 조작 부담 제거).
- **종료**: 롱프레스 + 확인 시트. 종료 시 요약 화면(화면 3)으로 이동. **자정 자동 마감**: 종료를 잊어도 24:00에 하루치 자동 확정 후 새 세션으로 이월.

### 4.2 적립 계산과 어뷰징 완화 (MVP 수준)

- 적립은 **검증된 이동 거리**의 정수 내림(18.4km → 18 SHV). 소수점 잔여분은 다음날로 이월하지 않음(단순성 우선).
- 1일 40 SHV 상한 도달 시: 링이 금색으로 변하고 "오늘 상한 도달 — 기록은 계속되지만 적립은 내일부터" 안내. 거리 기록 자체는 계속(일지용).
- MVP 어뷰징 완화 3종(서버 검증):
  1. **속도 필터**: 구간 평균 12km/h 초과 구간은 적립 제외(차량 탑승 추정). 6~12km/h는 "달리기 가능" 허용.
  2. **걸음-거리 교차 검증**: 만보계 걸음 수 대비 GPS 거리 비율이 비정상(예: 1km당 300걸음 미만)이면 해당 구간 보류.
  3. **경로 개연성**: 순간이동성 점프(GPS 스푸핑 의심)는 구간 제외. 정교한 부정 탐지는 2단계로 이월.

### 4.3 배터리 절약 전략

| 전략 | 내용 |
|---|---|
| 적응형 GPS 샘플링 | 기본 30초~1분 간격, 직선 이동 중엔 2분까지 확장, 방향 전환 감지(나침반/가속도) 시 즉시 샘플링. 순례길은 경로가 단순해 저빈도 샘플링으로도 거리 정확도 확보 가능 |
| 걸음 센서 병행 | OS 만보계(iOS Core Motion / Android Step Counter)는 저전력 하드웨어 센서. GPS 간격 사이 거리를 걸음×보폭으로 보간 |
| 화면 소등 전제 설계 | 트래킹은 100% 백그라운드 동작. 잠금화면 위젯/라이브 액티비티(iOS Live Activity, Android Foreground 알림)로 화면 켜지 않고 진행률 확인 |
| 배터리 절약 3단계 모드 | `표준`(1분 샘플) / `절약`(3분 샘플+걸음 보간) / `극한`(GPS는 시작·종료·1시간 간격만, 나머지 걸음 기반) — 설정 및 걷기 화면에서 전환. 배터리 20% 이하 시 자동 `극한` 전환 제안 |
| 지도 렌더링 억제 | 걷기 화면 지도는 정적 스냅샷 갱신(30초). 실시간 지도 애니메이션 금지 |
| 통신 억제 | 오프라인·절약 모드에선 위치 업로드를 하지 않고 로컬 큐 적재만 수행 |

### 4.4 GPS 끊김 처리

```
GPS 신호 상실 감지 (60초 이상 유효 좌표 없음)
 → UI: "GPS 탐색 중 — 걸음 센서로 기록을 계속합니다" (불안감 해소 문구)
 → 내부: 걸음 수 × 개인 보폭(최근 GPS 구간에서 자동 보정)으로 거리 추정
 → GPS 복구 시: 상실 지점~복구 지점을 직선이 아닌 순례길 경로 데이터에
   스냅(map-matching)하여 경로 보정. 걸음 추정치와 경로 스냅치 중
   보수적인(작은) 값을 적립에 사용
 → 일지에는 점선으로 "추정 구간" 표시 (투명성)
```
- 협곡·건물 등 멀티패스 오차: 정확도(accuracy) 50m 초과 좌표는 폐기.
- 앱 강제 종료/재부팅: 세션 상태를 로컬 DB에 10초마다 체크포인트 저장 → 재실행 시 "진행 중이던 기록을 복구했습니다" 자동 이어가기.

### 4.5 하루 진행률 표시 (20km 목표)

- 홈·걷기 화면의 **원형 링**: 0~20km를 주 링으로, 20~40km(상한)를 외곽 보조 링으로.
- 마일스톤 햅틱+알림: 5km("좋은 출발!"), 10km(절반), 20km("오늘 목표 달성 — 20 SHV"), 40km(상한).
- 잠금화면 위젯: `18.4/20 km · +18 SHV` 한 줄 표시.
- 주간 뷰(일지 탭 상단): 최근 7일 막대그래프 + 누적 SHV.

## 5. 안전 기능

순례길 특성상(외딴 구간, 낯선 이의 집 방문) 안전은 부가 기능이 아니라 신뢰 인프라다.

### 5.1 여성 엔젤 필터

- 프로필에 성별을 **선택적으로** 공개(공개는 본인 결정, 미공개 가능).
- 엔젤 지도 필터 칩 `여성 엔젤만`: 여성으로 공개·인증된 엔젤만 표시. 필터 설정은 계정에 저장되어 지도 진입 시 자동 적용 가능.
- 엔젤 측 옵션 `여성 쉬빌리스트만 맞이하기` 도 대칭적으로 제공.
- 성별 표시는 자기 신고 + 2단계에서 신분 인증(선택) 연계. MVP에서는 자기 신고 + 후기 기반 커뮤니티 검증(허위 신고 시 계정 제재 약관 명시).

### 5.2 비상 연락 (SOS)

- 앱 전역에서 접근 가능한 **안전 센터** + 걷기 화면의 SOS 버튼(3초 롱프레스로 오발동 방지).
- SOS 발동 시: ① 사전 등록한 비상 연락처(최대 3명)에게 SMS로 마지막 확정 위치 + 좌표 링크 전송, ② 현지 긴급 전화(국가별: 이스라엘 100/101, 한국 112/119 등 지역 설정 기반) 바로걸기 버튼 표시.
- **오프라인 시**: 데이터 통신 없이도 SMS는 음성망으로 발송 시도. 완전 무신호면 "발동 대기" 상태로 큐에 저장, 신호 복구 즉시 자동 발송 + 마지막 GPS 좌표 포함.
- 걷기 세션 비정상 중단(장시간 무이동 + 무응답) 감지 시 "괜찮으신가요?" 로컬 알림 → 30분 무응답이면 위치 공유 수신자에게 알림(옵트인 기능).

### 5.3 위치 공유

- **여정 공유 링크**: 신뢰하는 지인에게 웹 링크 공유 → 걷기 중 위치가 주기적으로(통신 가능 시) 갱신. 공유 범위는 `오늘 하루` / `이번 순례 기간` 선택, 언제든 즉시 해제.
- **체크인 방식(저전력 대안)**: 실시간 공유 대신 "출발/휴식/도착" 시점에만 위치 스냅샷 전송하는 모드.
- **엔젤 방문 체크인**: 엔젤 집 도착·지불 시 "지금 ○○ 엔젤에게 도착했음"을 비상 연락처에 자동 통지하는 옵트인 옵션 — 낯선 집 방문의 심리적 안전판.
- 프라이버시 원칙: 위치 공유는 전부 옵트인, 서버에는 공유 활성 기간의 위치만 보존(기간 종료 시 삭제), 엔젤 위치는 예약·안내 확정 전까지 300m 반경 흐림 처리.

### 5.4 평판·신고

- 거래 완료 후 상호 후기(별점+태그+텍스트). 거래가 실제 발생한 쌍끼리만 후기 작성 가능(허위 후기 차단).
- 신고 버튼(프로필·거래 상세): 안전 문제 신고는 우선 검토 큐로. 반복 신고 계정은 지도 노출 중단.

## 6. 기술 스택 제안

### 6.1 크로스플랫폼 프레임워크 비교

| 기준 | React Native (Expo) | Flutter |
|---|---|---|

| 걸음 센서 접근 | expo-sensors/브리지 필요 | pedometer 플러그인, 네이티브 채널 작성 부담 낮음 |
| 오프라인 로컬 DB | WatermelonDB, SQLite, MMKV | Drift(SQLite), Isar — 성숙도 높음 |
| 지도 | react-native-maps, Mapbox RN | google_maps_flutter, mapbox/MapLibre 플러그인 |
| QR 생성/스캔 | 성숙한 라이브러리 다수 | 성숙한 라이브러리 다수 (동급) |
| 저사양 기기 성능·배터리 | JS 브리지 오버헤드 존재(신아키텍처로 개선) | AOT 컴파일, 렌더링 일관성·성능 우위 |
| UI 일관성(iOS/Android) | 플랫폼 위젯 혼용, 파편화 가능 | 자체 렌더링으로 완전 일관 |
| 개발 인력 수급 | JS/TS 생태계로 매우 넓음 | 넓어지는 중, RN보다는 좁음 |
| Claude Code 등 AI 협업 | TS 생태계 — 학습 데이터·도구 풍부 | Dart — 충분하나 TS 대비 약간 열세 |
| 웹 확장(엔젤용 웹 대시보드) | React 코드 재사용 자연스러움 | Flutter Web 가능하나 문서형 웹에 부적합 |

**추천: React Native (Expo, 신아키텍처) + TypeScript**

근거:
1. 백엔드(Node/TS)와 **단일 언어(TypeScript)** 로 모노레포 구성 시 QR 페이로드 스키마·거래 검증 로직·타입을 앱과 서버가 공유할 수 있다. 오프라인 서명 거래처럼 클라이언트-서버가 같은 검증 코드를 써야 하는 이 프로젝트에서 결정적 이점.
2. 2단계에 필요한 엔젤용 웹(서비스 관리 대시보드), 커뮤니티 웹으로의 확장이 React 생태계 안에서 자연스럽다.
3. Claude Code 중심 개발 워크플로(8장)에서 TS 생태계의 도구·라이브러리 성숙도가 개발 속도를 좌우한다.
4. 백그라운드 위치의 약점은 `react-native-background-geolocation`(Transistorsoft, 유료 라이선스 ~수십만 원 1회) 채택으로 해소한다 — 배터리 최적화·이동 감지·iOS/Android 백그라운드 정책 대응이 검증된 사실상 표준이며, 이 영역을 자체 구현하는 비용보다 훨씬 저렴하다.

(팀이 Flutter 숙련자 중심이라면 Flutter도 충분히 타당하다. 그 경우 공유 스키마는 OpenAPI/JSON Schema 코드 생성으로 대체한다.)

### 6.2 백엔드 개요 (1단계: 서버 원장)

```
[모바일 앱] ⇄ HTTPS/JSON (+푸시)
     │
[API 서버]  Node.js + TypeScript (NestJS 또는 Fastify)
     │        - 인증: 전화번호 OTP(Twilio/알리고) + JWT, 기기 키 등록
     │        - 원장 서비스: 복식부기형 ledger 테이블(append-only),
     │          모든 잔액은 원장 재계산 가능해야 함 (2단계 온체인 이관 대비)
     │        - 걷기 검증 서비스: 세션 업로드 배치 검증(속도/걸음/경로 스냅)
     │        - 거래 서비스: 논스 소비, 서명 검증, 오프라인 거래 정산
     │        - 엔젤 카탈로그: 서비스 등록/검색(지리 쿼리)
     │
[DB] PostgreSQL + PostGIS (지리 검색), Redis (논스/세션 캐시)
[스토리지] S3 호환 (사진)
[푸시] FCM / APNs
[관측] Sentry(앱+서버), 구조적 로그
[배포] 단일 리전 컨테이너(초기: Fly.io/Railway/AWS ECS 중 택1), IaC는 후순위
```

핵심 설계 결정:
- **원장은 append-only 이벤트(적립/지불/조정)로 기록**하고 잔액은 파생값으로 계산. 2단계 온체인 전환 시 이 이벤트 로그를 그대로 마이그레이션 원본으로 사용한다.
- **기기 키 쌍**: 가입 시 앱이 키 쌍 생성, 공개키를 서버에 등록. 오프라인 QR 거래 서명의 뿌리. (2단계에서 이 키가 온체인 지갑 키로 승격 가능한 구조.)
- 걷기 데이터는 원시 좌표 전체가 아니라 **요약(구간별 거리·시간·걸음)+샘플 좌표**만 업로드해 통신량과 프라이버시 부담을 줄인다. 원시 데이터는 기기에 보존, 분쟁 시에만 제출.

### 6.3 지도 SDK

**추천: MapLibre GL Native + OpenStreetMap 계열 타일(자체 또는 MapTiler/Stadia 호스팅)**

| 후보 | 판단 |
|---|---|
| Google Maps SDK | 친숙하나 **오프라인 타일 캐싱 불가/제한** — 광야 요구사항과 충돌. 탈락 |
| Mapbox | 오프라인 팩 공식 지원, 품질 우수. 다만 MAU 과금 + 폐쇄 라이선스 |
| **MapLibre (권장)** | 오픈소스(BSD), 오프라인 타일 팩 구현 가능, Mapbox GL 호환 스타일. 타일 비용을 통제할 수 있고 순례길 GPX 오버레이 등 커스텀 자유 |

- 순례길 경로 데이터(GPX/GeoJSON)는 앱에 번들 또는 최초 실행 시 다운로드 — 오프라인에서도 경로 스냅·"진행 방향 앞쪽 엔젤" 정렬에 사용.
- 지역별 오프라인 지도 팩: 온보딩과 "구간 시작 전 체크리스트"에서 다운로드 유도(Wi-Fi 권장 안내).

### 6.4 앱 로컬 데이터

- SQLite(WatermelonDB 또는 expo-sqlite + drizzle): 걷기 세션, 로컬 원장, 미동기화 거래 큐, 일지.
- MMKV: 설정·세션 체크포인트 등 고빈도 소형 데이터.
- 동기화: "로컬 우선 기록 → 백그라운드 큐 업로드 → 서버 확정 응답으로 상태 승격(⏳→✓)" 단방향 패턴. 양방향 CRDT 같은 복잡한 동기화는 도입하지 않는다(거래·세션은 본질적으로 append-only라 충돌이 구조적으로 드묾).

### 7.2 2단계 이후로 미룬다

- **온체인 전환**: SHV 토큰 발행, 기기 키→체인 지갑 승격, 원장 이벤트 마이그레이션
- 사전 예약 시스템(MVP는 "오늘 가능" 표시 + 현장 대면으로 충분), 인앱 채팅(MVP는 전화/문자 딥링크)
- 실시간 위치 공유 고도화(MVP는 체크인 방식 중심), "근처 쉬빌리스트 접근" 엔젤 알림
- 신분 인증(여권/신분증) 연계 성별·본인 인증, 정교한 부정 탐지(ML 기반 이동 패턴 분석)
- 다국어 전면 지원(MVP: 한국어+영어 2개), 커뮤니티 피드·업적 배지 시스템 확장
- 엔젤 웹 대시보드, SHV 간 P2P 원격 송금, 법정화폐 연동 일체
- iOS/Android 워치 앱, 위젯 고도화

### 7.3 MVP 성공 기준(제안)

- 파일럿 구간(단일 순례길 1개 코스)에서 쉬빌리스트 30명 × 엔젤 10곳, 4주 운영
- 오프라인 거래 정산 성공률 99% 이상, 걷기 적립 이의제기율 5% 미만
- "엔젤이었던 사용자가 쉬빌리스트 모드로 걷기 시작"하는 순환 발생 사례 확보

```markdown

강제 규칙:
- SHV 관련 수치는 반드시 packages/shared/constants.ts에서 import한다.
- 거래·적립 금액 계산 로직을 화면 코드에 두지 않는다(shared로 위임).
- 새 화면은 접근성 라벨과 오프라인 상태 분기를 포함해야 완료로 간주한다.
- 작업 완료 시 타입체크(tsc)와 관련 유닛 테스트를 통과시킨 뒤 보고한다.
```

```markdown
---
name: backend-dev
description: API 서버(services/api) 담당. 원장, 인증, 거래 정산,

당신은 쉬빌 지갑 백엔드의 시니어 TypeScript 엔지니어입니다.

강제 규칙:
- 금액·상한 수치는 packages/shared/constants.ts만 참조한다.
- 신규 엔드포인트는 요청/응답 스키마를 packages/shared에 먼저 정의한다.
- 위치 데이터는 요약본만 저장하고 보존 기간 정책 주석을 남긴다.
- 작업 완료 시 통합 테스트(거래 동시성 케이스 포함)를 통과시킨 뒤 보고한다.
```

### 8.3 워크플로 운영 방식

1. **기능 단위 사이클**: 오너가 기능 명세(이슈) 작성 → `mobile-dev`/`backend-dev`가 병렬 구현(공유 스키마 선(先)합의) → `verification-engineer`가 독립 검증 → `security-auditor`가 거래·위치 관련 변경 감사 → 머지.
2. **구현자와 검증자 분리 원칙**: 구현 에이전트의 자기 검증을 신뢰하지 않고, 검증 에이전트가 별도 컨텍스트에서 테스트를 재작성·재실행한다.
3. **CLAUDE.md 계층화**: 루트(공통 규약·확정 파라미터) / apps/mobile(모바일 규약) / services/api(백엔드 규약)로 분리해 각 에이전트가 필요한 규칙만 로드하게 한다.
4. **ADR 기록**: 아키텍처 결정(예: MapLibre 채택, 오프라인 한도 값)은 docs/adr/에 1페이지씩 기록해 에이전트 간 컨텍스트 공유 비용을 줄인다.

### 8.4 개발 단계별 마일스톤

| 단계 | 기간(안) | 목표 | 완료 기준 |
|---|---|---|---|
| M0 기반 | 2주 | 모노레포·CI·shared 패키지 골격, 인증(OTP+기기 키), 원장 코어 | 원장 이벤트로 적립/지불 단위 테스트 통과 |
| M1 걷기 | 3주 | 트래킹 전체(시작/정지/종료, 배터리 모드, GPS 보간, 오프라인 기록), 서버 검증 배치 | 실기기 8시간 필드 테스트에서 거리 오차 ±5%, 적립 정확 |
| M2 지불 | 3주 | 온라인 QR 지불 전체 흐름, 지갑 화면, 거래 내역 | 두 기기 간 대면 지불 10초 이내, 이중지불 테스트 통과 |
| M3 오프라인 지불 | 2주 | QR 왕복 서명 거래, 한도, 정산·충돌 처리 | 양측 비행기 모드에서 거래→복귀→자동 확정 시나리오 통과 |
| M4 엔젤 | 3주 | 모드 전환, 서비스 등록 위저드, 엔젤 지도·상세·필터, 오프라인 지도 팩 | 엔젤 등록→지도 노출→탐색→지불까지 전체 여정 통과 |
| M5 안전·평판·일지 | 2주 | SOS, 위치 공유(체크인), 여성 엔젤 필터, 후기, 일지 | 안전 시나리오 검증 + security-auditor 전체 감사 통과 |
| M6 파일럿 준비 | 2주 | 관리자 도구, 크래시·로그 계측, 스토어 심사(TestFlight/내부 테스트), 파일럿 코스 지도 팩·경로 데이터 | 파일럿 킥오프 가능 상태 |

총 개발 기간 약 17주 + 파일럿 4주. M1(걷기)과 M2(지불)는 백엔드/모바일 에이전트 병렬 작업으로 일부 겹칠 수 있다.

## 부록 B. 미결 사항 (오너 결정 필요)

1. 파일럿 대상 순례길 코스 선정(경로 GPX 데이터 확보 경로 포함)
2. 오프라인 지불 한도 수치(본 문서 제안: 1회 20 / 누적 60 SHV)의 확정
3. SHV 마이너스 허용 한도(-20 SHV 제안)와 상환 정책의 약관 반영
4. 성별 자기 신고제의 파일럿 운영 원칙(허위 신고 제재 수위)
5. 지도 타일 호스팅 방식(자체 vs MapTiler류 유료 호스팅)
