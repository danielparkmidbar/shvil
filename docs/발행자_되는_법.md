# 발행자가 되는 법 — 제2, 제3의 쉬빌코인 발행기를 위한 규격

> 다니엘 쌤 2026-07-26 확정 방침:
> **"다른 사람이 다른 방식의 코인 생성기를 만들어도 된다. 그가 쉬빌코인과 같은 코드
> 체계의 코인을 생산한다면 — 달러 인쇄기를 다른 누군가가 만들어도 된다 — 같은 원리로
> 생성되고 같은 가치를 부여하며, 진짜 걸어서 만드는 방식이고 쉬빌코인 생태계와
> 호환된다면."**
> **"나의 발명은 쉬빌코인이라는 화폐를 발명한 것이다. 난 커뮤니티를 제공한다."**

이 문서는 그 문장을 **실행 가능한 규격**으로 옮긴 것이다. 발행기를 어떤 언어로
만들든, 여기 적힌 것을 그대로 구현하면 당신이 찍은 코인이 남의 지갑에서 검증된다.

- 참조 구현: `packages/shared/src/keyId.ts` (유도·해소), `server/src/app.ts` (발급)
- 화폐 규격 전체: `docs/쉬빌코인_규격.md` (직렬화·서명·코인·검증은 그쪽 2~8장)
- 이 문서가 다루는 것: **발행자 식별** 하나. 두 발행자가 충돌 없이 공존하는 법.

---

## 0. 먼저 — 지금 되는 것과 아직 안 되는 것 (2026-07-26 기준)

거짓말을 하지 않기 위해 이것을 맨 앞에 둔다.

| | 상태 | 근거 |
|---|---|---|
| 두 발행자가 **같은 이름 칸을 다투지 않는다** | ✅ **된다** | 이름이 공개키에서 유도된다 (2장) |
| 두 발행자의 코인이 **한 신뢰 목록에서 동시에 유효** | ✅ **된다** | 진짜 서버 두 대로 확인 — `server/test/multiIssuer.test.ts` |
| **옛 코인이 한 개도 죽지 않는다** | ✅ **된다** | `legacyKeyIdSurvival.test.ts`, `legacyUpgrade.test.ts` |
| 남의 이름을 참칭한 키가 신뢰 목록에 드는 것 | ✅ **막힌다** | 병합 관문 (3장) |
| 배포 서명 키로 코인을 발행하는 것 | ✅ **막힌다** | 용도별 권위 (1장) |
| **지갑이 제2 발행자의 키 목록을 받아 온다** | ❌ **아직 안 된다** | 배포 서명 핀이 지갑 전역 1개 (7장) |
| 사용자가 다른 발행자를 **명시적으로 수용하는 화면** | ❌ 없다 | 7장 |
| "모르는 발행자의 코인"과 "위폐"를 **다르게 표시** | ❌ 안 된다 | 7장 |
| 유출된 발행 키의 **폐기** | ❌ 없다 | 7장 |

**요약: 화폐 규격으로는 제2 발행자가 성립한다. 지갑 앱의 배송 경로가 아직 한 발행자만
전제하고 있다.** 지금 발행기를 만드는 것은 의미가 있다 — 코인은 규격대로 만들어지고,
키 목록을 손으로 합치면 검증된다. 다만 **일반 사용자의 지갑에 자동으로 들어가지는
않는다.** 그 마지막 다리는 아직 놓이지 않았고, 왜 서둘러 놓지 않는지는 6장에 있다.

## 1. 발행자가 갖는 여섯 개의 키

발행자 하나는 ed25519 키 여섯 쌍을 갖는다. 각 키는 **용도(purpose)** 를 갖고,
용도가 그 키로 무엇을 할 수 있는지를 정한다.

| purpose | 무엇에 쓰나 | 코인을 발행할 수 있나 |
|---|---|---|
| `MEMBERSHIP_ROOT` | 회원 증서(회원번호 ↔ 기기 공개키 결속)에 서명 | 아니오 (증서만) |
| `ANGEL_BONUS` | 엔젤 등록·첫 접대 보너스 GRANT 서명 | **예** |
| `COMMUNITY_CLAIM` | 커뮤니티 클레임 GRANT 서명 | **예** |
| `COMMUNITY_REWARD` | 격려·완주 보상 GRANT 서명 | **예** |
| `TREASURE` | 보물·스팟 GRANT 서명 | **예** |
| `DISTRIBUTION` | `/keys`·`/courses` 등 **응답 본문**에 `_sig`를 붙임 | **아니오** |

★`DISTRIBUTION`은 화폐를 찍는 키가 아니다. 이 구분을 흐리면 같은 코인이 어떤 구현에서는
진품, 다른 구현에서는 위폐가 된다(실제로 그런 불일치가 있었고 2026-07-26에 고쳤다).

이 여섯 개가 **규격이 아는 용도의 전부**다. 새 용도를 추가하면 그 이름을 유도할 수 없고
(2장), 다른 발행자·다른 지갑이 그 키를 받아들이지 못한다. 용도를 늘리려면 규격을
먼저 고쳐야 한다(`docs/쉬빌코인_규격.md` 10장 판올림).

## 2. 키 이름(keyId) 유도식 — ★정확히 이대로 구현하라

```
keyId = <slug> + "-" + SHA256(공개키 32바이트)의 앞 32 hex 문자
```

### 2.1 slug 표 (규격 고정값)

| purpose | slug |
|---|---|
| `MEMBERSHIP_ROOT` | `membership-root` |
| `ANGEL_BONUS` | `promo-angel` |
| `COMMUNITY_CLAIM` | `community-claim` |
| `COMMUNITY_REWARD` | `community-reward` |
| `TREASURE` | `promo-treasure` |
| `DISTRIBUTION` | `distribution` |

### 2.2 규약 — 여기서 어긋나면 호환이 깨진다

1. **해시 입력은 공개키의 32바이트 그 자체다.** hex 문자열(64자)을 해시하는 것이
   **아니다.** 이 둘은 절대 같은 값을 내지 않는다.
2. **공개키 표기는 소문자 hex 64자.** 대문자·길이 불일치는 거부한다.
3. **해시는 SHA-256**, 결과를 소문자 hex로 적고 **앞 32자**(=128비트)를 쓴다.
4. slug와 해시 사이는 하이픈 하나.

### 2.3 의사 코드

```
function deriveKeyId(purpose, publicKeyHex):
    assert purpose in SLUGS                      # 표에 없으면 실패시켜라(조용히 넘기지 마라)
    assert publicKeyHex matches /^[0-9a-f]{64}$/
    bytes  = hexDecode(publicKeyHex)             # 32바이트
    digest = hex(sha256(bytes))                  # 64자 소문자 hex
    return SLUGS[purpose] + "-" + digest[0:32]
```

### 2.4 적합성 벡터 — 이 값이 안 나오면 구현이 틀린 것이다

| 공개키 | purpose | keyId |
|---|---|---|
| `aa`×32 | `MEMBERSHIP_ROOT` | `membership-root-e0e77a507412b120f6ede61f62295b1a` |
| `aa`×32 | `ANGEL_BONUS` | `promo-angel-e0e77a507412b120f6ede61f62295b1a` |
| `aa`×32 | `DISTRIBUTION` | `distribution-e0e77a507412b120f6ede61f62295b1a` |
| `bb`×32 | `MEMBERSHIP_ROOT` | `membership-root-4ca14526b2751b640d549ce7caf8ac39` |

**흔한 함정 (미리 알려 둔다):** 공개키를 hex **문자열**로 해시하면 `aa`×32에 대해
`ffe054fe7ae0cb6dc65c3af9b61d5209`가 나온다. 이 값이 나왔다면 1번 규약을 어긴 것이다.
참조 구현의 테스트(`packages/shared/src/__tests__/keyId.test.ts`)가 이 함정 자체를
벡터로 고정하고 있다.

### 2.5 왜 이렇게 하는가

이름이 하드코딩 문자열(`membership-root-2026`)이던 시절, **모든 배포가 같은 이름을
썼다.** 신뢰 목록은 `이름 → 공개키` 사전이라 한 이름에 공개키 하나만 담긴다. 두
발행자의 목록을 합치는 순간 한 칸을 두고 다투고, **진 쪽의 코인이 전량 무효**가 됐다.
서명이 뚫린 게 아니라 **화폐 정체성이 "누구를 먼저 만났는가"라는 우연으로 결정**됐다.

이름을 키 재료에서 유도하면 배포마다 달라지므로 **애초에 같은 칸을 쓰지 않는다.**

### 2.6 왜 128비트인가

64비트로도 우연한 충돌은 거의 없다. 그러나 공격자가 **표적의 이름과 같은 이름이 나오는
키를 갈아서 찾는** 경우, 배포가 D개면 "아무 배포와나 충돌"의 비용이 2^64/D로 줄어든다.
충돌이 성립하면 2.5의 병이 그대로 되살아난다(한쪽 화폐가 통째로 죽는다). 화폐는 영구히
유통되는데 절단폭은 고정이므로 **유통 전인 지금** 128비트로 못박았다.

## 3. 키 목록을 주고받는 법

### 3.1 발행자가 게시하는 것 — `GET /keys`

```jsonc
{
  "keys": [
    { "keyId": "membership-root-3f2a…", "publicKey": "<hex64>", "purpose": "MEMBERSHIP_ROOT" },
    { "keyId": "promo-angel-9c14…",     "publicKey": "<hex64>", "purpose": "ANGEL_BONUS" }
    // … 여섯 개 (키를 회전했다면 은퇴한 키도 계속 실린다)
  ],
  "_sig": { "distKeyId": "distribution-…", "distPublicKey": "<hex64>",
            "signedAt": 1769000000000, "signature": "<hex128>" }
}
```

규칙 세 가지:

1. **추가 전용(append-only).** 키를 회전해도 **옛 키를 목록에서 빼지 마라.** 빼는 순간
   그 키로 서명된 코인이 세상에서 위폐가 된다. 회전은 새 키 재료 = 새 이름이므로
   항목이 하나 더 붙을 뿐이다.
2. **본문에 배포 서명(`_sig`)을 붙인다.** 서명 대상은 `{ body, meta }`이고 `signature`
   자체는 제외한다 (`packages/shared/src/distribution.ts` `signDistribution`).
3. **옛 이름(`-2026`으로 끝나는 여섯 개)을 새로 적지 마라.** 4장 참조.

### 3.2 받아들이는 쪽 규칙 — ★이것이 없으면 유도는 무의미하다

검증 코드는 이름과 공개키의 **관계를 검사하지 않는다.** 그래서 목록을 **받는 쪽**이
검사해야 한다. 규칙은 하나다:

> **들어오는 항목의 이름을 공개키에서 다시 유도해 적는다.**
> · 이름이 이미 유도값이면 → 그대로 받는다
> · **명시된 옛 이름**(4장의 여섯 개)이고 용도가 맞으면 → **유도 이름으로 고쳐 적는다**
> · 그 밖의 이름 / 모르는 용도 / 표기 위반 → **버린다**

참조 구현: `acceptKeyBindings` (`packages/shared/src/keyId.ts`), 호출 지점은
지갑 `mergeTrustedKeyInfos`와 서버 `recordPublicKey` **양쪽**. 한 곳만 막으면 다른 곳이
통로가 된다.

**왜 "버린다"가 아니라 "고쳐 적는다"인가 (옛 이름의 경우):** 이 목록은 이미 신뢰하기로
한 출처에서 온 것이고, 그 출처는 처음부터 자기 유도 이름으로 아무 키나 넣을 수 있었다.
이름을 고쳐 적는다고 새로 할 수 있는 일은 없다. 반대로 **버리면** 업그레이드하지 않은
서버의 목록이 통째로 사라져, 그 서버를 쓰는 새 지갑이 코인을 **한 개도 받지 못한다.**

### 3.3 캐시 규칙 (지갑을 만드는 사람에게)

1. **새 이름은 더한다.**
2. **이미 아는 이름의 공개키는 절대 바꾸지 않는다** (바꿔치기 차단 — 첫 응답이 기준).
3. **사라진 이름을 지우지 않는다** (유통 중인 옛 코인이 죽는다).
4. **이미 캐시에 있는 것은 검사하지도 고치지도 않는다.** 관문은 "새로 들어오는
   것"에만 세운다. 읽는 쪽에서 청소하면 앱을 업데이트한 그 순간 옛 키가 사라져
   **보유 중인 코인이 전부 죽는다.**

## 4. 옛 이름 여섯 개 — 있는 그대로

2026-07-26 이전에 원조 발행자가 발급한 증서·GRANT 안에는 아래 이름이 **서명 대상으로**
박혀 있다. 서명 안에 있으므로 **사후에 고칠 수 없다.**

```
membership-root-2026   community-claim-2026   promo-treasure-2026
promo-angel-2026       community-reward-2026  distribution-2026
```

### 4.1 검증기가 해야 하는 일

> `keyId`가 이 여섯 개 중 하나면, 코인이 **함께 들고 다니는 `issuerPublicKey`** 를
> 그 이름이 고정하는 용도로 유도해 신뢰 목록에서 찾는다. 찾으면 신뢰한다.

즉 **이름은 조회 색인일 뿐 권위가 아니다.** 참조 구현: `isTrustedKeyBinding`.

이 규칙 덕분에
- 옛 이름 칸을 **누가 차지하든** 원조의 옛 코인이 죽지 않는다,
- **두 발행자의 옛 이름 코인이 한 지갑에서 동시에 유효**할 수 있다,
- 옛 이름이 목록에 **한 칸도 없어도** 옛 코인이 검증된다.

### 4.2 발행자가 해야 하는 일 — 아무것도 하지 마라

**이 여섯 이름을 주장하지 마라.** 당신의 배포가 그 이름을 게시해도 남의 옛 코인을
죽이지는 못한다(4.1 때문에). 그러나 **당신의 코인이 누구 것인지 사람이 헷갈리게
된다.** 참조 구현의 서버는 아예 그 이름을 적지 못하게 막혀 있다(`recordPublicKey`가
유도되지 않은 이름을 예외로 던진다).

### 4.3 ★대가 — 정직하게 적는다

옛 이름은 **신원을 증명하지 않는다.** `membership-root-2026`이 박힌 코인을 보고
"원조 발행자가 만든 것"이라고 말할 수 없다. 내가 신뢰 목록에 넣은 발행자라면 누구든
그 이름을 쓸 수 있고, 그 코인은 그 발행자의 공개키로 검증된다.
**발행자를 구별하려면 공개키(=유도 이름)를 봐야 한다.**

이것은 잃은 것이 아니라 **원래 없던 것을 있는 척하지 않기로 한 것**이다. 이름이
신원을 증명하려면 "이 이름은 이 공개키의 것"이라는 **바깥의 공시**가 필요하고, 그것은
암호가 아니라 커뮤니티의 일이다(6장).

## 5. 발행자의 의무 — 지키지 않으면 무슨 일이 생기는가

| # | 의무 | 어기면 |
|---|---|---|
| 1 | keyId를 2장 유도식으로 만든다 (128비트) | 남의 지갑이 당신의 키를 **버린다**. 당신 코인 전량이 `UNTRUSTED_ISSUER` / `UNKNOWN_MEMBERSHIP_ROOT` |
| 2 | 옛 이름 여섯 개를 주장하지 않는다 | 남의 코인을 죽이지는 못하지만, 당신 코인의 출처가 사람에게 헷갈린다. 명부에서 배제될 사유 |
| 3 | 용도별 권위를 지킨다 (배포 키로 코인을 찍지 않는다) | 같은 코인이 지갑에서는 진품, 서버에서는 위폐가 된다 |
| 4 | `/keys`를 **추가 전용**으로 공개 게시한다 | 키를 회전하는 날 **당신이 발행한 옛 코인이 전부 죽는다** |
| 5 | 회원번호를 **자기 발행자 안에서 유일**하게 발급한다 | 인간 한계 검사가 무력해진다. "위조가 시장 전체에 영향을 못 준다"는 원칙의 근거가 무너진다 |
| 6 | 회원 증서에 기기 무결성 판정을 **정직하게** 담는다 | 변조 앱이 무제한 발행하는 통로가 된다 |
| 7 | 6장 생성 규칙(요율·상한·걷기 필터)을 그대로 쓴다 | "같은 가치를 부여한다"가 거짓이 된다. 규격 부적합 |
| 8 | 발행 개인키를 봉인 저장한다 (KEK는 DB 밖) | 유출 시 **당신 발행자의 코인 전량**이 위태롭다. 폐기 수단은 아직 없다(7장) |
| 9 | 8장 적합성 시험을 통과한다 | 주장이 아니라 검사다 |

★5번이 특히 중요하다. 회원번호가 유일하지 않으면 "하루 40 SHV 상한"·"인간 한계
프로파일" 같은 정량 방어가 전부 무력해진다.

## 6. ★신뢰 목록에 들어가는 것은 기술이 아니라 커뮤니티의 문제다

여기까지가 기술로 풀리는 전부다. **그리고 여기서 기술이 끝난다.**

2~4장이 푼 것은 **"신뢰하기로 한 두 발행자가 충돌 없이 공존하는가"** 하나뿐이다.
**"누구를 신뢰할 것인가"** 는 서명으로도 해시로도 풀리지 않는다. 어떤 유도식도
"이 발행자가 정직한가"를 계산해 주지 않는다.

> 다니엘 쌤: **"난 커뮤니티를 제공한다."**
> 이 문장이 바로 그 자리에 있다. 발행자 명부는 **기술 산출물이 아니라 커뮤니티
> 산출물**이다.

### 6.1 자동 병합이 왜 위험한가

"발행자 명부를 받아 와서 자동으로 신뢰 목록에 합친다"는 편리하고, **그것이 곧 공격
경로다.** 이유는 셋이다.

1. **자동 병합은 "신뢰 결정"을 네트워크에 넘긴다.** 목록을 주는 쪽(또는 그 자리를
   가로챈 쪽)이 곧 화폐 발행 권위를 나눠 주는 사람이 된다. 사용자는 자기가 무엇을
   신뢰하게 됐는지 알지 못한다.
2. **한 번 들어온 것은 되돌리기 어렵다.** 캐시 규칙 3.3-2·3(공개키를 바꾸지 않는다,
   지우지 않는다)은 옛 코인을 지키기 위한 것이지만, **오염된 항목도 똑같이 지킨다.**
   실측으로 확인했다: 잘못 들어온 항목은 앱을 다시 깔기 전에는 사라지지 않는다.
3. **모르는 발행자의 코인이 지금은 "위폐"와 같은 자리에 떨어진다.** 어휘가 분리되기
   전에는(7장) 자동 병합의 반대편 — 자동 거부 — 도 사람을 다치게 한다.

그래서 규격이 정한다:

1. **자기 발행자(가입한 서버)는 최상위 신뢰.**
2. **다른 발행자는 사용자의 명시적 수용만.** 자동 병합 금지.
3. **거부는 코인을 죽이지 않는다.** 모르는 발행자의 코인은 "모르는 화폐"이지
   "위폐"가 아니다.

> **헌법 제3조(속도보다 진리) 대조:** "빨리 제2 발행자를 받자"는 이유로 자동 병합을
> 택하면 위 세 가지가 그대로 열린다. **느려도 명시적 수용이 맞다.**
> **헌법 제9조(불간섭) 대조:** 신뢰 목록은 **로컬 위조 검사**용이다. 거래 승인이
> 아니고 위치와도 무관하다. 저촉되지 않는다.

### 6.2 그래서 지금 발행자가 되려면

1. 이 문서대로 발행기를 만든다 → **코인은 규격대로 만들어진다.**
2. `/keys`를 공개 게시한다 → **누구든 당신 코인을 검증할 수 있다.**
3. 당신의 코인을 받을 사람의 지갑에 당신 키가 들어가는 경로는 — **아직 손으로 합치는
   것뿐이다.** 자동 경로(명부·수용 화면)는 커뮤니티가 정한 뒤에 만든다.

## 7. 아직 남은 장벽 (정직한 목록)

기술로 아직 못 넘은 것들이다. 순서는 급한 순.

### 7.1 배포 서명 핀이 지갑 전역 1개 — **가장 큰 장벽**
`apps/wallet/src/core/distributionGuard.ts:12` `DIST_PIN_KEY = 'distKeyPin.v1'`는
서버 오리진별이 아니다. 발행자 A에 핀된 지갑이 발행자 B의 `/keys`를 부르면 본문이
완벽해도 `KEY_PIN_MISMATCH`로 통째 거부된다.
→ **"두 발행자가 서로를 덮어쓰지 않는다"는 성립했지만, "지갑이 B의 키를 받아 온다"는
아직 막혀 있다.** 핀 분리는 6장의 명시적 수용과 **같이** 설계해야 한다 — 핀만 쪼개고
자동으로 합치면 그 자동 병합이 곧 6.1의 공격 경로다.

### 7.2 판정 어휘가 분리되지 않았다
모르는 발행자의 코인이 `UNTRUSTED_ISSUER` / `UNKNOWN_MEMBERSHIP_ROOT`로 떨어진다 —
**위폐와 같은 자리다.** 다발행자 세계에서 "모르는 화폐"와 "위폐"는 다른 것이어야 한다.
(`docs/쉬빌코인_규격.md` 7.3, 결정 대기 3번)

### 7.3 유출된 발행 키를 폐기할 방법이 없다
키 회전은 "새 키를 더하는 것"이고, 옛 키는 계속 신뢰된다(그래야 옛 코인이 산다).
**개인키가 실제로 유출된 경우**를 위한 서명된 폐기 목록(revocation)은 미구현이다.
유도 keyId는 이 문제를 전혀 건드리지 않는다. 그래서 5장 의무 8번이 중요하다.

### 7.4 공개키 이력이 서명 없는 평문이다
서버의 `publicKeyArchive`는 평문 JSON이다. DB 쓰기 권한을 얻은 자가 항목을 직접 끼워
넣으면 관문을 거치지 않고 `/keys`에 실린다. 개인키는 봉인되어 꺼낼 수 없지만
**발행 권위는 갈아끼울 수 있다** — 봉인이 지키는 것과 이력이 지키는 것의 강도가 다르다.
지금은 기동 시 경고만 남긴다(`nonConformingArchiveEntries`).

### 7.5 명부가 없다
"어떤 발행자가 있는가"를 알 방법이 없다. 이것은 결함이 아니라 **미결정**이다 —
쉬빌코인.com이 게시할 것인가, 게시하면 "다니엘 쌤이 화폐를 통제한다"는 인상이 되는가.
(`docs/쉬빌코인_규격.md` 결정 대기 5번)

## 8. 발행기 자가 점검표

- [ ] 여섯 개 키를 만들고 각각 봉인 저장했다 (KEK는 DB 밖)
- [ ] 여섯 개 keyId가 2장 유도식과 벡터를 만족한다
- [ ] 어떤 keyId도 `-2026`으로 끝나지 않는다
- [ ] `/keys`가 여섯 개를 전부 싣고 `_sig`가 붙어 있다
- [ ] 키를 회전해도 옛 항목이 `/keys`에서 사라지지 않는다
- [ ] 남의 이름을 참칭한 키 목록을 넣어 보고, 내 서버·내 지갑이 그것을 버리는지 확인했다
- [ ] `DISTRIBUTION` 키로 서명한 GRANT를 만들어 보고, 거부되는지 확인했다
- [ ] 회원번호가 내 발행자 안에서 유일하다
- [ ] 요율·상한·걷기 필터가 6장 그대로다
- [ ] 옛 이름이 박힌 남의 코인을, 그 발행자의 유도 이름만 신뢰 목록에 넣고 검증해 봤다
      (통과해야 한다 — 4.1)
