# 공개 체크포인트와 규칙판(Rule Epoch) 설계 — "새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지는 않는다"

> 다니엘 쌤 2026-07-26:
> **"화폐 발행자는 위조 방지를 최선을 다해 하지만 위조 방지 시스템도 업그레이드한다.
> 새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지는 않는다."**
> **"나의 발명은 쉬빌코인이라는 화폐를 발명한 것이다. 난 커뮤니티를 제공한다."**

이 문서는 그 원칙을 **코드로 구현 가능한 형태**로 옮긴 설계다. 문서와 설계만이며 코드 변경은 없다.
관련 문서: `화폐규격_다발행자_설계.md`(발행자 여럿), `위폐감지기_설계.md`(판정 어휘).

---

## 0. 한 줄

> **유예는 "코인이 옛날 것이라고 주장한다"에 걸리지 않는다.
> **"코인이 옛날에 이미 공개적으로 기록되어 있었다"에 걸린다.**
> 앞의 것은 위조자가 적는 값이고, 뒤의 것은 위조자가 소급할 수 없는 사실이다.

---

## 1. 딜레마 — 왜 날짜로는 안 되는가

검증 규칙이 강해질 때 옛 코인을 봐주면(grandfathering) 위조자가 "내 코인은 옛것"이라 주장한다.
코인 안의 `startedAt`·`settledAt`은 **민팅하는 기기가 적는 값**이다(`types.ts:73~74`,
`proof.ts:32~48`). 서명은 그 값을 봉인하지만 **그 값이 참인지는 증언하지 않는다.**

그래서 유예의 근거는 코인 **안**에 있을 수 없다. 코인 **밖**에, 위조자가 손댈 수 없는 곳에
있어야 한다. 그 자리를 채우는 것이 공개 체크포인트다.

| 근거 후보 | 위조자가 소급할 수 있는가 | 쓸 수 있는가 |
|---|---|---|
| `proof.settledAt` (코인 안 날짜) | **예** — 자기가 적는다 | ✗ |
| `membership.issuedAt` (증서 발급 시각) | 부분적 — 증서를 가진 동안 아무 날짜나 적을 수 있다 | ✗ |
| 지갑 로컬 저장 시각 | **예** — 자기 기기다 | ✗ |
| 서버 DB의 최초 목격 시각 | 아니오, 그러나 **서버가 고칠 수 있다** (제9조 위반: 서버가 사후 권력을 쥔다) | △ |
| **외부에 앵커된 공개 체크포인트** | **아니오** — 비트코인 블록·신문 지면·여러 사람의 사본 | **✓** |

## 2. 체크포인트 규격

### 2.1 리프 — 무엇을 담는가 (좌표 없음)

체크포인트가 담는 것은 **코인 자체가 아니라 계보 다이제스트 한 개(32바이트)**다.

```
lineageDigest(coin):
  root = coin.provenance 를 SPLIT 따라 끝까지 거슬러 올라간 뿌리   // fingerprint.ts:41 과 동일
  WALK  → hashObject(root.provenance.proof)     // = CoinFingerprint.proofHash
  GRANT → hashObject(root.provenance.grant)

leaf = sha256("shvil-ckpt-leaf/1|" + lineageDigest)
```

**왜 `coin.id`가 아니라 뿌리 증명 해시인가**
`splitCoin`은 새 provenance로 **새 id를 만든다**(`coin.ts:180~189`). 이전(transfer)은 id를 바꾸지
않지만 분할은 바꾼다. `coin.id`를 등록하면 잔돈으로 쪼갠 순간 등록이 무효가 된다.
뿌리 증명 해시는 분할·이전에도 불변이고, `fingerprint.ts`가 이미 그렇게 뽑고 있다.
**부수 효과: 한 번 걸어 만든 코인을 100장으로 쪼개도 리프는 1개다.**

**좌표가 없다는 증명 (제9조·제10조)**
리프는 `hashObject(proof)`의 해시다. `WalkSegmentProof`에는 좌표·경로 필드가 애초에 없고
(`types.ts:65~95`, 남는 장소 정보는 `courseIds`뿐), 그마저 단방향 해시 뒤로 사라진다.
체크포인트만 보고는 **누가 어디를 걸었는지는커녕 코인이 몇 개인지 말고는 아무것도 알 수 없다.**
`FINGERPRINT_KEYS`(`fingerprint.ts:61~71`)에 대한 기존 정적 검사와 같은 방식으로
"체크포인트 리프는 다이제스트 한 개뿐"을 테스트로 못박는다.

**★새 데이터 수집이 아니다.** 서버는 이미 `walk_verified_credit(proof_hash, producer_member,
total_dshv, first_verified_at)`를 쌓고 있다(`db.ts:212~`, `trust.ts:106~110`). 이 표에 적재되는
것은 서버가 **직접 `verifyCoin`을 통과시킨** 코인의 뿌리 증명 해시다. 체크포인트는 이 표의
**주간 공개 요약**일 뿐이다. 수집 코드도, 프라이버시 논의도 새로 필요 없다.

### 2.2 머클 트리 (모호성 제거까지 명시)

```
node(a,b) = sha256("shvil-ckpt-node/1|" + a + "|" + b)

리프 목록: 사전순 정렬 + 중복 제거          // 결정성
홀수 레벨: 마지막 노드를 그대로 승격         // 복제 금지 (복제는 CVE-2012-2459류 모호성을 만든다)
root     = sha256("shvil-ckpt-root/1|" + count + "|" + treeRoot)   // count를 루트에 결속
```

도메인 분리 문자열(`leaf/`·`node/`·`root/`)은 리프를 내부 노드로 위장하는 2차 원상 공격을 막는다.
`count`를 루트에 결속하면 리프 수를 속여 다른 트리를 같은 루트로 만드는 경로가 닫힌다.
해시·정준 직렬화는 기존 `crypto.ts`(`sha256Hex`, `stableStringify`)를 그대로 쓴다 — 새 암호 없음.

### 2.3 헤더

```jsonc
{
  "v": 1,
  "observerId": "shvil-origin",         // 관측자 (★발행 권위가 아니다 — 4장)
  "observerPublicKey": "…",
  "epoch": 521,                          // 이 관측자의 연속 번호
  "prevCheckpoint": "<이전 헤더의 해시>", // 해시 체인 — 관측자가 과거를 몰래 갈아끼울 수 없다
  "root": "…", "count": 128450,
  "totalDshv": 4820310,                  // 선언 집계 (2.5)
  "memberCount": 3170, "maxPerMemberCount": 92,
  "periodStart": …, "periodEnd": …,
  "ruleEpochId": "shvil-rules-2026.07",  // 이 시점의 현행 규칙판
  "signature": "…"
}
```

### 2.4 앵커 — 시각을 증명하는 것은 헤더가 아니다

헤더의 `periodEnd`는 **관측자가 적는 값**이므로 그 자체로는 1장의 딜레마를 못 푼다.
시각을 증명하는 것은 **외부 앵커**다.

```jsonc
// checkpoint-0521.anchors.json
{
  "checkpointHash": "…",
  "ots": "<base64 .ots — 비트코인 블록 시각>",
  "git":  { "repo": "…/shvil-checkpoints", "commit": "…" },
  "btc":  { "txid": "…", "blockTime": … },      // 선택
  "print": { "paper": "…", "date": "2027-01-04", "section": "안내광고" }  // 선택(연 1회)
}
```

**`anchorAt(c)` = 앵커가 증명하는 가장 이른 시각.** OTS면 비트코인 블록 시각.
앵커가 확인되지 않은 체크포인트는 **시각 증명이 없으므로 유예 근거가 되지 못한다**(배포용 사본일 뿐).

### 2.5 집계값의 정직한 위치

`totalDshv`·`memberCount`·`maxPerMemberCount`는 **관측자의 선언값이며 개별 검증이 불가능하다.**
그래도 싣는 이유는 9장 1번(대량 선등록)이 **공개적으로 보이게** 하기 위해서다.
리포트·공시에서는 반드시 "선언 집계"라고 표시한다.

## 3. 어디에 공개하는가 — 실제 조사 결과

★기준: **쉬빌 서버가 사라져도 남아야 한다.** 그리고 제2조(무투자·무법정화폐·철저한 절약).

| 매체 | 비용 | 영속성 | 다니엘 쌤 직접? | 소급 불가능성 | 판정 |
|---|---|---|---|---|---|
| **GitHub 저장소 커밋** | 0원 | 중 — 계정·회사 의존, `force-push`로 역사 재작성 가능. 단 공개 저장소는 Software Heritage가 자동 수확해 별도 보존(17억 파일·3.5억 커밋 규모, 유네스코 지원, 사본 3벌) | 예 (`git push`) | **약함** — 커밋 시각은 조작 가능 | **배포처로만 채택.** 시각 증명이 아니다 |

| **여러 곳 동시 게시** | 0원 | 최상 (하나가 사라져도 나머지가 남는다) | 예 | 강함 | **★필수 채택** |
| **★사람이 보관 (커뮤니티 사본)** | 0원 | **사람 수에 비례** | 예 | 강함 (누구든 반증 가능) | **★채택.** 체크포인트 해시는 **64자**다. 공지에 붙여도, 종이에 적어도, 메신저로 보내도 보관된다. 제2조에 가장 맞는 매체 |

### 3.1 채택안 — 3층

```
매주  : 체크포인트 빌드 → OTS 스탬프 → shvil-checkpoints 저장소 커밋 → 커뮤니티 공지에 64자 게시
매년  : 그 해 마지막 체크포인트 해시 1개를 신문 안내광고 1회 (선택 — 제2조 지출 판단)
상시  : 누구나 저장소를 클론·미러링, 누구나 자기 관측자로 같은 것을 한다
```

핵심은 **비용 0원인 층(OTS + 깃 + 사람)만으로 이미 요건을 만족한다**는 것이다.
신문은 "인터넷 전체가 사라져도"라는 극단 시나리오용 보험이며 없어도 설계가 성립한다.

### 3.2 왜 OTS면 캘린더 서버를 믿지 않아도 되는가

캘린더 서버는 수천 개 해시를 머클로 묶어 **비트코인 트랜잭션 하나**에 넣는다.
확정 후의 `.ots` 파일은 "내 해시 → 머클 경로 → 비트코인 블록 헤더"를 전부 담으므로,
검증은 **비트코인 블록만 있으면 된다.** 캘린더 서버가 문을 닫아도 이미 발급된 증명은 유효하다.
즉 OTS는 **신뢰 주체를 추가하지 않는다** — 그래서 제9조와 충돌하지 않는다.

## 4. 누가 만드는가 — 이것이 중앙 권력이 아닌 이유

**체크포인트 발행은 권위가 아니라 관측이다. 시계이지 재판관이 아니다.**

악의적 관측자가 할 수 있는 최악을 전부 세어 보면:

| 악용 시도 | 결과 |
|---|---|
| 가짜 다이제스트를 잔뜩 넣는다 | **무해.** 포함은 유효성 증명이 아니다. 검사는 그대로 다 돈다. 물리적으로 불가능한 코인은 여전히 FORGED |
| 남의 코인 등록을 거부한다 (검열) | 그 코인은 **현행 규칙판으로 판정될 뿐 무효가 아니다.** 다른 관측자에게 내면 된다 (비용 0원) |
| 헤더의 시각을 조작한다 | 앵커가 반박한다. `anchorAt`은 비트코인 블록 시각이다 |
| 과거 체크포인트를 몰래 바꾼다 | `prevCheckpoint` 해시 체인 + 이미 앵커된 해시가 반박한다 |
| 자기 체크포인트를 세워 자기 위조 코인을 넣는다 | 앵커 시각은 **오늘**이다. 오늘 등록한 코인은 오늘 판(가장 엄격)으로 판정된다. 과거로는 못 간다 |

그러므로 **관측자 명부는 필요 없다.** 검사자는 "앵커가 실제로 확인되는 체크포인트"라면
누가 만든 것이든 쓴다. 다니엘 쌤의 체크포인트가 실제로 가장 많이 쓰이게 될 이유는
권한이 아니라 **연속성**이다 — 가장 오래되고 가장 촘촘하다. 원칙 7("난 커뮤니티를 제공한다")이
코드에서 이렇게 생겼다.

> **불변식 ①: 체크포인트 포함은 진품 인증이 아니다. 오직 "이 시점에 이미 존재했다"만 증언한다.**
> 이 한 줄이 관측자를 무해하게 만들고, 그래서 아무나 관측자가 될 수 있게 만든다.

## 5. 규칙판 (Rule Epoch)

### 5.1 자료 구조 — 동결·추가만·영구 보존

```ts
interface RuleEpoch {
  id: string;                    // 'shvil-rules-2026.07'
  effectiveFrom: number;         // 이 시각 이후 provenAt 코인에 적용
  /** ★파라미터 스냅샷 — 나중에 DEFAULT_*를 바꿔도 이 판은 안 변한다. */
  params: {
    economic: EconomicParams; walk: WalkFilterParams; bike: BikeFilterParams;
    humanLimits: HumanLimitProfile; maxSegmentSpanDays: number;
  };
  requireMembership: boolean;    // 옛 requireIntegrityToken — 검사자 옵션이 아니라 판의 속성
  requireIntegrity: boolean;
  notes: string;
}

/** 각 결정적 검사가 "언제 생겼는가". 이 표가 유예의 전부다. */
const CHECK_SINCE: Record<AuthenticityCheckId, string> = {
  LINEAGE: '2026.07', TIME_WINDOW: '2026.07', SPEED_LIMIT: '2026.07', /* … */
  WINDOW_TOO_LONG: '2026.07', BREAKDOWN_TOO_MANY: '2026.07', PROOF_CAP: '2026.07',
  // 앞으로 추가되는 검사는 그날의 판 id를 적는다
};
```

옛 판은 **절대 삭제하지 않는다.** 1930년 지폐를 감정하려면 1930년 규격서가 남아 있어야 한다.

### 5.2 판정 알고리즘

```
provenAt(coin, 아는_체크포인트들 C, 코인에 동봉된 포함증명들 P)
  = min{ anchorAt(c) : c∈C, ∃p∈P 가 leaf(coin) 의 c.root 포함을 증명 }
  = now                                     // 등록을 확인하지 못하면 (fail-closed)

epochOf(coin) = provenAt 시점에 발효 중이던 RuleEpoch

검사 X 를 돌린다  ⟺  CHECK_SINCE[X] ≤ epochOf(coin).id
파라미터        =  epochOf(coin).params      // ★검사 시점의 DEFAULT_* 가 아니다
증서 만료 기준   =  provenAt                  // now 가 아니다 (7-a)
```

### 5.3 리포트 — 유예는 정보를 숨기지 않는다 (제3조)

`AuthenticityReport`에 더한다:

| 필드 | 뜻 |
|---|---|
| `ruleEpochId` | 어느 판으로 판정했는가 |
| `provenAt` / `provenBy` | 언제 등록되었는가 / 어느 체크포인트·앵커로 |
| `registered` | 등록 확인 여부 |
| `skippedChecks: {check, since}[]` | **유예된 검사 목록** |
| `latestRulesVerdict` | **현행 최신 판으로 재면 어떻게 되는가** |

사람이 읽는 문구:

> "이 코인은 **2026.07 규칙판(구권)** 으로 판정했습니다 — 2026-08-03 체크포인트 #521에
> 등록되어 있고, 그 등록은 비트코인 블록 시각으로 확인됩니다.
> 이후 추가된 검사 2건(`SENSOR_ENTROPY`, `DEVICE_CONTINUITY`)은 **적용하지 않았습니다.**
> 참고로 현행 2027.02 판으로 재면 판정은 `SUSPECT`입니다."

### 5.4 구조적 잠금 — 기존 규칙 팩 설계와 같은 비대칭

`rulePack.ts`가 "팩은 검사를 **더할 수만** 있다"를 구조로 못박은 것과 **정확히 대칭**으로,
유예도 구조로 못박는다:

> **불변식 ②: 유예는 검사를 건너뛸 뿐, 이미 나온 판정을 낮추지 못한다.**
> 구현: 유예는 `CHECK_SINCE` 비교로 **검사 실행 전에** 결정된다. 발견(finding) 목록을
> 사후에 걸러내는 코드는 만들지 않는다 — 만들 수 있으면 언젠가 완화에 쓰인다.
> `escalateOnly`(`authenticity.ts:769`)와 같은 성격의 마지막 잠금장치를 하나 더 둔다.

> **불변식 ③: 미등록·확인불가 코인은 언제나 현행 판(가장 엄격)이다.**
> "모르면 관대"는 감지기에서 가장 위험한 습관이다. 갈리는 방향은 항상 엄격한 쪽이며,
> 그 사실을 `notes`가 말한다.

### 5.5 화폐가 쪼개지지 않는가 — 감지기마다 아는 체크포인트가 다르면?

포함 증명은 **코인과 함께 다닌다**(`.ots` 파일처럼). 그래서 두 검사자가 같은 증명을 본다.
갈릴 수 있는 경우는 "검사자가 그 체크포인트의 루트를 모를 때"뿐이고, 이때는 미등록 취급 →
**더 엄격** → 위조가 진짜가 되는 방향으로는 절대 갈리지 않는다.
그리고 이 어긋남은 자기 소멸적이다: 옛 체크포인트는 모두가 갖고 있고, 최근 체크포인트를
모르는 감지기는 **최근 코인**만 엄격히 볼 뿐인데, 최근 코인은 어차피 현행 판 대상이다.

## 6. 오프라인 감지기 — 크기 실측

측정: 저장소 밖 임시 스크립트로 실측(저장소 코드 무수정, 측정 후 폐기).

| 항목 | 크기 |
|---|---|
| 체크포인트 헤더 1개 | JSON **448 B** / 바이너리 **144 B** |
| **10년치 주 1회 (520개)** | JSON 227.9 KB / **gzip 40.2 KB** / **바이너리 73.1 KB** |
| 관측자 3곳 × 10년 | 바이너리 **219.4 KB** |
| 포함 증명 (리프 1,000개) | 노드 10개 = 원시 330 B / JSON 811 B |
| 포함 증명 (리프 10만) | 노드 17개 = 원시 561 B / JSON 1,378 B |
| 포함 증명 (리프 100만) | 노드 20개 = 원시 **660 B** / JSON 1,621 B |

**결론: 10년치 체크포인트를 앱 번들에 넣어도 100 KB 미만이다. 오프라인 판정이 성립한다.**
규칙판 목록은 판이 몇 개 되지 않으므로 수 KB다.

세부:
- 포함 증명은 **뿌리 증명당 1개**다. 한 번 걸어 만든 코인을 여러 장으로 쪼개 지불해도 증명은 1개.
- 지불 QR 동봉은 **크기 예산을 따로 확인해야 한다**(코인 JSON 자체가 이미 증명+증서+체인을 싣는다).
  기본은 **지갑 저장 + "검사용 내보내기"·마켓 에스크로 동봉**이고, QR 동봉은 여유가 있을 때만.
  QR에 없어도 손해는 "그 코인이 미등록으로 보인다" = 더 엄격 = 안전 방향뿐이다.
- 감지기 갱신은 파일 하나(`checkpoints.bin` + `ruleEpochs.json`)를 받는 것으로 끝난다.
  갱신하지 않은 감지기도 **틀리지 않는다. 다만 엄격해진다.**

## 7. 소급 무효화 경로별 처방

실측이 찾아낸 다섯 경로 전부에 대해 "옛 코인이 죽지 않게" 하는 방법.

### (a) 회원 증서 TTL 30일 만료 → 옛 코인이 `BAD_MEMBERSHIP` → **FORGED**

현재: `membership.ts:82` `if (now >= cert.expiresAt)` — 비교 대상이 **검사 시각**이다.
같은 코인이 30일 지나면 대면 수령·마켓 수령·신뢰 실적·스팟 예치에서 전부 거절된다.

**처방: 만료 판정 기준을 `now` → `provenAt`.**
```ts
// coin.ts VerifyCoinOptions 에 추가 (기본값 = 기존 동작)
certValidAt?: number;   // 이 시각에 증서가 유효했는가. 기본 options.now ?? Date.now()
```
`membership.ts`는 **한 줄도 안 바뀐다** — 이미 `now` 인자를 받는다(`membership.ts:74~78`).
바뀌는 것은 `coin.ts:297`이 무엇을 넘기느냐뿐이다.

**왜 `proof.settledAt`이 아니라 `provenAt`인가 (★중요)**
`settledAt`은 위조자가 적는 값이다. 증서를 한 번 가졌던 기기는 만료 후에도
"증서가 유효하던 날짜"를 적어 영원히 민팅할 수 있다. `provenAt`은 그것을 막는다 —
그 코인이 그때 **이미 존재했음**을 외부가 증언해야 한다.

**실물 선례:** 코드 서명 타임스탬프. 인증서가 만료돼도 **서명 시점에 유효했음이
타임스탬프로 증명되면** 서명은 계속 유효하다. 20년 넘게 쓰인 검증된 방식이다.

### (b) `requireIntegrityToken` 등 검사 옵션 토글 → 같은 코인이 옵션에 따라 AUTHENTIC/FORGED

**처방: 옵션을 규칙판 필드로 옮긴다.** `RuleEpoch.requireMembership` / `.requireIntegrity`.
검사자가 손잡이를 돌리는 것이 아니라 **코인의 판이 정한다.**
그러면 `coreVerdict`가 검사자와 무관해진다 — 실측이 지적한
"진리가 검사자에 의존한다"가 구조적으로 사라진다.
더 엄격하게 보고 싶은 사람은 **이미 있는 규칙 팩**으로 한다(더하기만 가능).

무결성 필수화 자체는 그대로 진행하되, **발효 시점의 판**에 적는다.
그 판 이전에 등록된 코인은 유예되고, 리포트에 `skippedChecks`로 드러난다.

### (c) 신뢰 루트 제거·로테이션 → 그 키의 모든 과거 코인이 일괄 FORGED

키 ID가 `membership-root-**2026**`(`app.ts:71`)인 것은 **연 단위 교체가 전제**라는 뜻이다.
즉 이 소급 무효화는 사고가 아니라 **예정된 일정**이다.

**처방: 지우지 말고 은퇴시킨다. 목록은 누적(union)한다.**
```jsonc
{ "keyId": "membership-root-2026", "publicKey": "…",
  "notBefore": …, "retiredAt": …, "compromisedAt": null }
```
- **정기 교체**: `provenAt < retiredAt` 이면 계속 인정. 이후 민팅분만 거부.
- **키 유출**: `compromisedAt` 이후 등록분만 거부. 유출을 뒤늦게 알아도 **피해가 그 시각 이후로 한정**된다.
  ★유예 원칙의 유일한 정당한 예외는 여기다. "새 검사"가 아니라 "그때 이미 거짓이었음이 밝혀진 것"이기 때문이다.
- 캐시 덮어쓰기 → union (`화폐규격_다발행자_설계.md` 3.2가 이미 지적한 **현재 버그**).
- 목록에 없는 루트 = `UNKNOWN_ISSUER`(모르는 화폐) ≠ `FORGED`(위폐).
  같은 문서 5장 4번과 어휘를 맞춘다.

### (d) ★소명 대기 목록(flagged) — 가장 크게 고쳐야 하는 곳

현재 결함 넷 (실독으로 확인):

1. **무차별.** `findFlaggedProducer`(`flagged.ts:34~41`)는 `coin.memberId`(생산자)만 본다.
   그 회원이 **언제 만든 코인이든 전부**, 소명이 풀릴 때까지 **무기한** 수령 거부된다
   (`walletService.ts:462~471`). 5년 전 정직하게 걸어 만들어 제3자가 보유한 코인까지 함께 멈춘다.
   → **다니엘 쌤 원칙 정면 위반.**
2. **표적 오류.** `DOUBLE_SPEND_SUSPECT`는 이중지불자를 **주소**로 잡는데(`anomaly.ts:64~88`),
   차단은 **생산자 회원 번호**로 한다. 결과: (i) 그가 정직하게 생산한 옛 코인이 막히고,
   (ii) 정작 그가 이중지불한 코인(남이 생산한 것)은 **안 막힌다**. 양쪽 다 빗나간다.
3. **미검증 입력.** 등재 입력인 지문이 서명 미검증이다 — `anomaly.ts:95~99`가 스스로
   "누구나 임의 JSON을 올릴 수 있다"고 인정한다. 제3자가 남의 회원 번호로 그 사람의 전 코인
   유통을 멈출 수 있다.
4. **경로 비일관.** 대면 수령만 막고 **마켓 수령(`ackEscrowPurchase`, `walletService.ts:684~720`)에는
   flagged 검사가 아예 없다.** 확인함.

**처방 다섯:**

**① 어휘를 분리한다** — `위폐감지기_설계.md`의 판정 어휘 개정과 함께.
| 판정 | 뜻 | 코인이 무효인가 |
|---|---|---|
| `FORGED` | 물리적 모순. 반박 불가 | 예 |
| `UNVERIFIABLE` | 재료·신뢰 루트 부족, 모르는 발행자 | **아니오** |
| `HELD` | 소명 절차 진행 중 — **유통만 보류** | **아니오** |
flagged는 지금도 판정에 들어가지 않지만 **이름과 문구가 없어 사용자에겐 위조로 보인다.**

**② 시간 범위를 건다 (★이 문서의 원칙이 flagged에 적용되는 지점)**
등재 항목에 `effectiveFrom`(사유의 증거 시각 — `OVERPRODUCTION_*`의 `params.date`,
분기가 관측된 시각)을 넣고:
> **`provenAt < effectiveFrom` 인 코인은 보류하지 않는다.**
> 사건 이전에 이미 공개 등록되어 있던 코인은 그 사건과 무관하다.

**③ 표적을 정정한다** — 사유별 스코프.
| 사유 | 스코프 | 보류 대상 |
|---|---|---|
| `OVERPRODUCTION_DAILY/WEEKLY` | `{ kind:'PRODUCER', memberId }` | 그 회원이 **`effectiveFrom` 이후 생산한** 코인만 |
| `DOUBLE_SPEND_SUSPECT` | `{ kind:'PAYER', address }` | **그 주소가 지불자로 등장하는 이전 링크**를 가진 코인 (생산자 무관) |
| `MANUAL` | 명시 | 명시 범위만 |
즉 "그 사람이 **나에게** 주는 것"만 보류한다. 제3자 간 유통은 건드리지 않는다.

**④ 자기 증명 증거를 동봉한다 (제9조 — 서버의 사후 승인권 제거)**
보류는 서버의 말이 아니라 **지갑이 로컬에서 검증할 수 있는 증거**로만 성립한다.
- 이중지불: 같은 `(coinId, chainLen)`에서 지불자 서명이 붙은 **서로 모순되는 두 링크**.
  이 두 링크는 **그 자체로 자기 증명**이다 — 지갑이 `verifyObject`로 확인한다(`coin.ts:326`).
- 초과생성: 같은 회원의 **서명된 증명들**과 그 일자합. 증명은 서명이 붙어 있으므로 검증 가능하다.
- 증거를 검증하지 못한 항목은 **`ADVISORY`(경고 표시)** 로만 내려가고 **수령을 막지 않는다.**
  → `anomaly.ts`의 미검증 지문 경로로는 더 이상 남을 얼릴 수 없다.

**⑤ 기한과 경로 일관**
- `PENDING`은 `expiresAt`(소명 기한)을 가지며 지나면 자동으로 `ADVISORY`로 강등된다. **무기한 동결 금지.**
- 대면·마켓·예치·신뢰 실적 네 경로가 **같은 함수**를 쓴다. 지금은 마켓만 뚫려 있다.

### (e) 인간 한계 파라미터 하향 → 과거 날짜 합계가 소급 위반

`checkHumanLimits`(`humanLimits.ts:68~119`)는 기간 제한 없이 옛 코인을 일자별로 합산하고
**검사 시점의** `DEFAULT_HUMAN_LIMIT_PROFILE`로 잰다.

**처방:** `humanLimits`도 `epochOf(coin).params`에서 읽는다.
그리고 이 위반은 코인 무효가 아니라 **HELD 계열**임을 명시한다(문구·타입 모두).

## 9. 못 하는 것 — 정직하게

1. **★위조자는 오늘 대량 선등록을 할 수 있다.**
   오늘 가짜 증명 10만 건을 만들어 오늘 등록하면, **내년에 추가되는 검사에서 영원히 면제된다.**
   이것은 버그가 아니라 유예의 본질적 대가다. "등록 이후에 발견된 취약점"을 등록분에
   소급 적용하면 원칙 1이 그 자리에서 무너지기 때문이다.
   완화(제거 아님): (i) 헤더 집계 공개로 대량 선등록이 **공개적으로 보인다**,
   (ii) **환금 게이트** — 쉬빌코인.com에서는 최신 판 + 규칙 팩 + 지갑 전체 제출을 요구한다.
   **유통에서 살아남는 것과 현금으로 바뀌는 것은 다르다.**
   이것이 다니엘 쌤의 "달러 위폐가 어딘가 돌아다니는 정도"의 정확한 구현이다.
   ※ 예외는 7-(c) 키 유출뿐 — 그것은 "새 검사"가 아니라 "그때 이미 거짓이었음"이므로 소급한다.
2. **미등록 코인은 유예를 받지 못한다.** 완전 오프라인 사용자가 손해를 본다.
   완화: 포함은 승인이 아니므로 **누구나 남의 코인을 등록할 수 있고**, 수령자가 자동 등록한다.
   그래도 한 번도 남에게 주지 않고 인터넷에도 닿지 않은 코인은 등록되지 않는다.
3. **체크포인트는 이중지불을 막지 않는다.** 시각 증명일 뿐이다.
4. **체크포인트는 GPS 위조·루팅 기기를 막지 않는다.** 그것은 무결성 인증·인간 한계·소명의 몫이다.
5. **앵커 확정까지 수 시간 걸린다.** 그 사이 코인은 미등록 = 현행 판. 안전 방향이므로 문제 없다.
6. **집계값(`totalDshv` 등)은 검증되지 않는 선언값이다.**
7. **이 설계는 "옛 위조 코인"을 되살릴 수도 있다.** 규칙이 강해지기 전에 이미 등록된 위조는
   유예 대상이다. 그 총량은 유한하고 공개적으로 셀 수 있다 — 그것이 다니엘 쌤 원칙 2의 조건이다.

## 10. 결정 대기 (다니엘 쌤)

1. **체크포인트 주기** — 주 1회 제안. 앵커가 0원이므로 일 1회도 가능하고, 잦을수록 유예 경계가 촘촘해진다.
2. **헤더에 회원별 등재 수를 공개할 것인가** — 대량 선등록 탐지에 유리하나 회원별 발행량이 노출된다.
   제안: **총계 + 1인 최대치만** 공개하고 회원별 명세는 넣지 않는다.
3. **신문 연차 게재** — 제2조(절약) 대비 지출 판단. 없어도 설계는 성립한다.
4. **소명 기한(HELD 자동 강등) 일수** — 제안 30일.
5. **오늘자 규칙판 id 고정** — 지금 코드 상태를 `shvil-rules-2026.07`로 동결한다.
   ★이 판 확정 전에 들어가는 검사(예: `WINDOW_TOO_LONG`)는 **소급 적용된다.**
   즉 지금이 소급 없이 강화할 수 있는 **마지막 시점**이다.
6. **주 상한 3,000 dSHV** — 실측상 죽은 조항이다(일 400 × 7 = 2,800 < 3,000).
   값을 고치는 순간 그것이 새 규칙판이 되므로, 5번과 **같은 판에서 함께** 정하는 것이 좋다.
7. **관측자 목록을 쉬빌코인.com이 게시할 것인가** — 게시해도 자동 신뢰는 하지 않는다(4장).

## 11. 작업 순서 (지시 후)

| 순 | 항목 | 왜 이 순서인가 |
|---|---|---|
| 0 | 신뢰 키 캐시 union (`화폐규격_다발행자_설계.md` 3.2) | **지금도 옛 코인이 죽고 있다.** 이 설계와 무관하게 버그 |
| 1 | `checkpoint.ts` — 리프·머클·포함증명 검증·앵커 파싱 (순수 함수 + 테스트) | 나머지 전부의 토대. 서버·네트워크 없음 |
| 2 | `ruleEpoch.ts` — 오늘 상태를 `2026.07`로 동결, `CHECK_SINCE` 표 | 결정 5번 답 후 |
| 3 | `verifyCoin`에 `certValidAt` 옵션 (기본 = 기존 동작) | 경로 (a)를 통째로 없앤다. `membership.ts` 무변경 |
| 4 | `authenticity.ts`에 `provenAt`·판 선택·`skippedChecks`·`latestRulesVerdict` | 유예가 정보를 숨기지 않게 |
| 5 | 서버 `/checkpoints` + 주간 빌드 스크립트 + OTS 스탬프 + 저장소 커밋 | 입력은 이미 있는 `walk_verified_credit` |
| 6 | flagged 재설계 (어휘·`effectiveFrom`·스코프·자기증명 증거·기한·경로 일관) | 가장 크고 가장 원칙에 어긋나 있는 부분 |
| 7 | 신뢰 루트 `retiredAt`/`compromisedAt` | 루트 교체 일정 전에 반드시 |
