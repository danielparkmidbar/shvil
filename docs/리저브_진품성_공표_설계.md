# 창시자 리저브 진품성 설계 — 공표·비발행·거래소 검증

> 다니엘 쌤 2026-07-26:
> **"결국 나에게 중요한 것은 내가 다음 사업을 위해 리저브한 내 쉬빌 코인이
> 진품으로 모두가 인정하는 구조만 되면 된다."**
> **"거래소는 쉬빌코인.com이 될 것이다." / "나의 발명은 쉬빌코인이라는 화폐를
> 발명한 것이다. 난 커뮤니티를 제공한다."**

**이 문서는 설계 문서다. `packages/shared`·`apps/`·`server/` 코드는 한 줄도 고치지
않았다.** 일련번호의 성질은 임시 vitest로 실측했고 측정 후 삭제했다(§1). git commit 없음.

## 0. 문제의 재정의 — 두 조건은 대칭이 아니다

지시문의 통찰이 정확하다. 리저브가 신뢰받으려면 두 가지가 동시에 필요하다.

| 조건 | 뜻 | 이 문서의 답 |
|---|---|---|
| **(a) 진짜임을 남이 확인할 수 있다** | 리저브 코인 하나를 집어 "이건 진짜다"를 제3자가 계산할 수 있다 | **완전히 가능하다.** 일련번호 + 위폐감지기 + 공표 목록으로 끝난다 (§1~3) |
| **(b) 나중에 몰래 더 만들 수 없다** | 창시자가 리저브를 조용히 부풀릴 수 없다 | **완전히는 불가능하다.** 원리적 한계가 있다 (§4-3) |

그리고 (b)가 (a)보다 어렵다는 사실이 이 설계의 전부다.

**(a)는 암호로 풀린다. (b)는 암호로 풀리지 않는다.** 쉬빌코인에는 전역 원장이 없고
(제9조 무승인), 신원 등록부도 없다. 그런 시스템에서 **"나는 다른 코인을 만들지 않았다"는
증명할 수 없다.** 비존재 증명이기 때문이다. 어떤 설계도 이것을 바꾸지 못한다.

그래서 이 문서는 (b)를 다음과 같이 **바꿔 놓는다**:

> **"창시자가 코인을 더 만들지 못하게 한다"(불가능)**
> **→ "창시자의 코인이 시장에 영향을 주는 모든 지점을 남김없이 보이게 한다"(가능)**

숨겨 둔 코인이 있어도 그것이 쓰이지 않으면 아무 일도 일어나지 않는다. 그것이 쓰이는
지점은 딱 둘이다 — **사람에게 직접 건네거나, 쉬빌코인.com에서 현금으로 바꾸거나.**
앞은 계보에 남아 받은 사람이 본다. 뒤는 거래소가 전량 공시한다. 이 두 개를 막으면
**"몰래"라는 말이 성립할 자리가 없어진다.** 코인은 만들 수 있지만, 몰래 쓸 수는 없다.

이것은 다니엘 쌤 자신의 원칙 2와 정확히 같은 논리다 — 위조를 0으로 만드는 것이 아니라
**영향을 0으로** 만든다.

## 1. 실측 — 일련번호는 이 용도에 적합한가

### 1.1 코드가 말하는 성질

`packages/shared/src/coin.ts:28`
```ts
id: hashObject({ t: 'coin', provenance }),
```
**`transferChain`이 id에 들어가지 않는다.** 이 한 줄이 아래 성질 전부를 만든다.
`serial.ts:59-66`의 `serialFromCoinId`는 `coin.id`만의 함수이므로 성질이 그대로 이어진다.

### 1.2 실측 결과 (임시 vitest 4건 — 실행 후 삭제)

| # | 실험 | 결과 |
|---|---|---|
| **A** | 코인을 남에게 이전(transfer+ack)한 뒤 번호 | `SHV-GPSD2-Z03RF-JQVS1-C` → **동일**. 이전은 번호를 바꾸지 않는다 |
| **B** | 400 dSHV를 100/300으로 분할 | 자식 번호는 **둘 다 새 번호**. 그러나 자식의 계보(`provenance.parent`)를 타고 올라가면 **부모 번호가 그대로 나온다** |
| **C** | 손자까지 2단 분할 | 조상 사슬 = `[중간 자식, 원조 부모]` — **원조 번호가 끝까지 남는다** |
| **D** | 같은 걷기 증명으로 두 번 민팅 | **같은 번호**. 번호는 계보의 결정적 함수다 — 갈아끼울 수 없다 |

(B·C가 가능한 이유: `types.ts:118-124`의 SPLIT provenance가 **부모 Coin 전체**를 품는다.)

### 1.3 → 적합하다. 그것도 정확히 필요한 세 가지 성질을 갖고 있다

| 필요한 성질 | 일련번호가 주는가 |
|---|---|
| 공표한 목록이 코인이 손을 옮겨도 계속 유효해야 한다 | **[A] 예** — 이전해도 번호 불변 |
| 목록에 있는 번호를 가진 **위조본**을 만들 수 없어야 한다 | **[D] 예** — 번호는 계보 해시. 계보를 바꾸면 번호가 바뀌고, 번호를 맞추려면 그 계보를 가져야 한다(= 그건 진짜다) |
| 공표가 **전역 추적기가 되어서는 안 된다** (제9조) | **[B] 예** — 분할하면 번호가 바뀌므로 목록만으로는 추적이 끊긴다. 이어 붙일 수 있는 사람은 **그 코인을 손에 든 사람뿐**이다 |

### 1.4 ★공표가 제9조를 어기지 않는 이유 (중요)

번호 목록을 전 세계에 뿌려도 감시 도구가 되지 않는다. **볼 서버가 없기 때문이다.**
서버는 거래를 기록하지 않고(제9조), 코인은 기기 안에 있다. 번호를 안다고 해서 그 코인이
지금 누구 손에 있는지 알 방법이 없다.

확인은 **코인을 실제로 받은 사람이, 자기 기기에서, 오프라인으로** 한다.
즉 공표된 리저브 목록은 **감시자의 도구가 아니라 수취인의 권리**다.
"내가 받은 이 코인이 창시자 리저브에서 나온 것인가"를 창시자에게 묻지 않고 스스로 답한다.

## 2. 공표 형식 — 3층으로 나눈다

### 2.1 왜 한 가지로는 안 되는가

| 방식만 쓰면 | (a) 확인 가능 | (b) 추가 불가 | 문제 |
|---|---|---|---|
| 총량 숫자만 | ✗ | ✗ | 그냥 주장이다. 아무것도 검증되지 않는다 |
| 머클 루트(해시)만 | △ | **✓** | 내 코인이 리저브인지는 증명 경로로 확인 가능. 그러나 커뮤니티가 **총량이 정말 그만큼인지** 볼 수 없다 |
| 전체 번호 목록만 | **✓** | △ | 목록이 나중에 조용히 한 줄 늘어나도 알기 어렵다 |
| **셋 다 (채택)** | **✓** | **✓** | 아래 |

### 2.2 채택 형식

**Layer 1 — 리저브 선언문 (1페이지, 창시자 서명, 공개)**

```
쉬빌코인 창시자 리저브 선언 v1
공표 시각      : 2026-08-XX
규격 버전      : shvil-coin-spec 1.x (감지기 코어 해시: sha256 …)
발행자         : 쉬빌 (원조 발행자, 루트 공개키 <hex64>)   ← ★이름이 아니라 공개키로 적는다
내 회원번호    : SHV-000001, SHV-0000XX          ← 전부. 빠짐없이
내 기기 공개키 : <hex>, <hex>                     ← 공개키만. 개인키 아님
리저브 코인 수 : N 장
리저브 총액    : M SHV
머클 루트      : <64 hex>
서약 6조       : §7-4 참조
서명           : <창시자 서명>
```

> ★**2026-07-26 정정 — 발행자를 `membership-root-2026`이라는 이름으로 적으면 안 된다.**
> 옛 이름은 이제 **신원을 증명하지 않는다**(`docs/발행자_되는_법.md` 4.3). 그 이름은
> 조회 색인일 뿐이고, 신뢰 목록에 있는 발행자라면 누구든 쓸 수 있다. 리저브의 명의는
> **루트 공개키(그리고 그로부터 유도되는 `membership-root-<128비트>`)** 로 적어야
> 한다. 공표문이 이름을 적으면, 그 이름을 쓰는 다른 발행자의 코인이 리저브 명의로
> 읽힌다.

**Layer 2 — 일련번호 목록 (기계 판독 JSON/CSV, 공개)**

```
일련번호, 금액(dSHV), 정산일(YYYY-MM-DD), 계보종류
SHV-GPSD2-Z03RF-JQVS1-C, 400, 2026-06-01, WALK
...
```
번호·금액·날짜·종류만. **회원번호도 기기 키도 상대방 정보도 들어가지 않는다.**
머클 루트는 이 목록의 정렬된 줄에서 계산한다.

**Layer 3 — 코인 원본 JSON (계보 전체, 요청 시 감사자에게만)**

`{coins:[...]}` 형식 그대로. 받은 사람이 위폐감지기에 그대로 넣어
`coreVerdict = AUTHENTIC`을 직접 확인할 수 있다.

★**Layer 3을 무조건 공개하면 안 되는 이유:** 코인이 남에게서 온 것이면(§5 옵션 B의
감사 이전분) 계보에 **기증자의 회원번호와 기기 키**가 들어 있다. 창시자가 자기 정보를
공개하는 것은 자유지만 남의 정보를 대신 공개할 권리는 없다(제9조).
→ **직접 걸어 만든 코인은 Layer 3 전면 공개 가능. 남에게서 받은 코인은 기증자 동의 후.**

### 2.3 머클 루트가 하는 일 — "한 줄도 못 늘린다"

목록에 한 줄만 더해도 루트가 바뀐다. 루트를 **여러 곳에 동시에 못 박아 두면**(§3),
나중에 목록을 조용히 늘리는 것이 물리적으로 불가능해진다 —
바꾸려면 이미 게시된 모든 사본을 동시에 바꿔야 한다.

이것이 (b)에 대해 **암호로 실제로 얻어낼 수 있는 유일한 보장**이다:
**"리저브라고 이름 붙일 수 있는 집합은 이미 닫혔다."**

## 3. 공표 위치 — 설계 1의 "체크포인트"와 같은 것인가

### 3.1 저장소에서 "체크포인트"라는 말은 두 가지다

| 뜻 | 위치 | 리저브 공표와의 관계 |
|---|---|---|
| **물리 체크포인트** (트레일 위 QR·NFC 금속판) | `쉬빌코인_프로토콜_설계.md` 7장 | **전혀 다른 것.** 걷기의 현장 증명이지 문서 공증이 아니다 |
| **시각 앵커** (증서 갱신 때 정산 체인 머리를 서버가 서명) | `위성시각결속_위치프라이버시_조사4.md` §5 대안 B(361-366행) | **같은 계열, 다른 레코드** |

### 3.2 시각 앵커와 리저브 공표 — 같은 원리, 다른 대상

둘 다 "**이 시점 이전의 과거를 다시 쓸 수 없다**"는 append-only 앵커다. 그러나:

| | 시각 앵커 (조사4 대안 B) | 리저브 공표 |
|---|---|---|
| 대상 | 사용자 개인의 정산 체인 머리 | 창시자 1인의 코인 집합 |
| 공개 여부 | **비공개** (서버↔지갑) | **전면 공개** |
| 주기 | 증서 갱신마다 (30일) | 1회 + 분기 재확인 |
| 막는 것 | 백데이팅(과거에 걷기를 끼워 넣기) | 리저브 부풀리기(목록에 코인을 끼워 넣기) |

**→ 답: 같은 것이 아니다. 그러나 같은 그릇에 담아야 한다.**

권고: **하나의 「공표 원장」(append-only 공개 로그)** 을 만들고 레코드 타입을 나눈다.
`{type: "RESERVE_DECLARATION" | "RESERVE_SALE" | "TIME_ANCHOR" | "ISSUER_REGISTRY", ...}`.
서명 형식·미러링 정책·검증 도구를 **한 번만** 만들면 되고, 나중에 발행자 명부
(`화폐규격_다발행자_설계.md` §5)도 같은 원장에 들어간다.

### 3.3 게시 장소 — 4곳 동시 (하나가 죽어도 남는다)

| # | 위치 | 근거 / 상태 |
|---|---|---|
| 1 | **투명성 페이지** shvilist.org / shvilangel.org `/transparency` | **자리가 이미 있다.** `apps/web-list/src/app/transparency/page.tsx:107-108`, `i18n/ko.ts:317-318` — "리저브 공시 / 준비 중" 플레이스홀더가 이 문서를 기다리고 있다 |
| 2 | **위폐감지기 배포본에 동봉** `tools/checker/배포/쉬빌_위폐감지기.html` | 오프라인 단일 HTML 파일. 리저브 목록을 이 파일 안에 넣으면 **서버 없이, 인터넷 없이** "이 코인이 리저브인가"를 확인할 수 있다. 쉬빌 서버가 사라져도 유효 |
| 3 | **외부 불변 앵커** (머클 루트 32바이트만) | RFC 3161 TSA / Roughtime(무료 우선), 또는 이미 마켓 결제에 쓰는 공개 체인. 조사4:366이 같은 수단을 이미 거론 |
| 4 | **커뮤니티 미러** | 누구나 Layer 1·2 파일을 받아 자기 깃허브·서버에 복사. 서명이 붙어 있으므로 원본이 사라져도 유효 |

**제2조 대조 — 3번 앵커에 수수료가 든다.** 이것은 "법정화폐를 투입해 **시장을 만드는**"
행위가 아니라 **문서 공증**이다(코인을 사거나 시세를 만들지 않는다). 그래도 무료 수단
(TSA·Roughtime)을 먼저 쓰고, 유료 체인 앵커는 대안으로 둔다. 제2조의 「투입」은 방향을
가진 말이고, 여기엔 시장이 없다.

## 4. "더 만들지 않는다"의 증명

### 4.1 지시문의 질문에 대한 직답 — 기기 키 공개는 답이 아니다

> "리저브 지갑의 기기 키를 공개하면 그 키로 만든 새 코인이 전부 보인다 — 되는가?"

**되지 않는다. 세 가지 이유로.**

**(1) 기기 공개키는 이미 전부 공개되어 있다.**
`WalkSegmentProof.devicePublicKey`(types.ts:71)는 **모든 코인 안에 들어 있다.** 코인을
받은 사람은 이미 그것을 본다. 따로 공개해도 새로 드러나는 것이 없다. 새로 생기는 것은
"이 키가 창시자다"라는 **이름표 하나**뿐이다.

**(2) 그리고 그 이름표가 있어도 "전부 보이지" 않는다.**
전역 원장이 없기 때문이다. 코인은 기기 안에 있고 서버는 거래를 기록하지 않는다(제9조).
그래서 그 키로 만든 코인을 볼 수 있는 사람은 **그 코인을 손에 든 사람뿐**이다.
키 공개는 **탐지 능력을 하나도 늘리지 않는다.** 늘어난다고 믿으면 그것이 더 위험하다 —
지키지 못할 약속이 된다.

**(3) 기기 개인키 공개는 절대 금지.**
개인키를 공개하는 순간 **누구나 창시자 이름으로 코인을 찍을 수 있다.** 리저브가 그 즉시
무의미해진다. "키 공개"라는 말이 나올 때 공개키/개인키를 반드시 구분해야 한다.

**제9조 충돌 여부:** 자기 키를 자기가 공개하는 것은 감시가 아니다(제9조는 남을 감시하지
말라는 조항이다). 다만 **부작용은 실재한다** — 창시자가 코인을 건넨 상대는 계보에서
창시자 회원번호를 본다. 이건 원래 보이던 것이고 이름표만 붙는다. 창시자 본인에게는
감수할 만하다. **그러나 일반 사용자에게 같은 것을 요구하면 그건 제9조 위반이다.**
리저브 공개는 **창시자 1인에게만 적용되는 자기 구속**이어야 한다.

### 4.2 그래서 실제로 구속하는 것 — 4중 장치

| # | 장치 | 무엇을 막는가 | 누가 검증하는가 |
|---|---|---|---|
| **(i)** | **닫힌 집합** — 리저브 = 공표된 머클 루트. 그 밖은 리저브가 아니다 | 나중에 만든 코인을 "원래 리저브였다"고 부르는 것 | 누구나. 루트 대조 1회 |
| **(ii)** | **예외 없는 물리 상한** — 창시자 코인도 40 SHV/일. **GENESIS provenance를 만들지 않는다** | 걸음 없이 태어난 창시자 코인 | 위폐감지기. Layer 3을 넣으면 끝 |
| **(iii)** | **신원 선언 + 몰수 서약** — 통제하는 회원번호를 전부 선언. **선언 안 한 번호로 만든 코인을 나중에 자기 것이라 주장하면 그 주장은 무효** | "숨은 신원"을 나중에 꺼내 쓰는 것 | 커뮤니티. 선언문 대조 |
| **(iv)** | ★**환금구 전량 공시** — 창시자가 쉬빌코인.com에서 판 코인은 번호·날짜·금액 전부 공시 | **위 셋을 다 빠져나가도 여기서 보인다** | 누구나. 공시 대 목록 대조 |

**(iii)이 (b)를 처음으로 "정의 가능"하게 만든다.** 선언이 없으면 "몰래"가 무슨 뜻인지
아무도 말할 수 없다. 선언이 있으면 "선언 밖에서 만들어 시장에 내놓았다"가 명확한
위반 사실이 된다. 신원을 추가할 일이 생기면 **미리** 공표한다(추가 선언 → 새 루트).

**(iv)가 나머지 셋의 빈틈을 덮는다.** 숨은 코인이 있어도 시장에 나오는 순간 보인다.

### 4.3 ★증명할 수 없는 것 (정직화 — 제3조)

이것을 적지 않으면 이 설계는 거짓말이 된다.

1. **"나는 다른 신원이 없다"는 증명 불가능하다.** 원리적으로 비존재 증명이다. 게다가
   실측상 지금 신원 비용은 사실상 0이다(이메일 검증 미구현, `device_public_key` UNIQUE
   없음, 무결성 실패해도 가입 성공). 신원 비용을 올려도(§8) **줄어들 뿐 0이 되지 않는다.**
2. **분기 재공표는 "안 늘었다"를 보여줄 뿐 "숨긴 게 없다"는 뜻이 아니다.**
3. **머클 루트는 "이 집합이 닫혔다"만 보장한다.** 창시자가 리저브 밖에서 새 코인을
   만드는 것 자체는 막지 않는다 — 막을 수도 없고, 막아서도 안 된다. 창시자도
   걸으면 코인이 생기는 것이 정상이다. 다만 그것은 **리저브가 아니다.**
4. **거래소 공시는 거래소가 정직할 때만 유효하다.** 거래소가 창시자 소유이므로
   구조적 이해상충이다 → §6-3의 제3자 감사·복수 거래소가 그 대응이다.

그러므로 정직한 문장은 이것이다:

> **"창시자가 코인을 더 만들 수 없다"는 보장할 수 없다.
> 보장할 수 있는 것은 "창시자가 만든 코인이 리저브 행세를 할 수 없고,
> 시장에 나오면 반드시 보인다"이다.**

이 문장을 그대로 선언문에 적을 것을 권고한다. **약속을 줄이면 신뢰가 는다.**

## 5. 리저브 코인은 어떻게 만들어지는가 — 선택지와 각각의 문제

**옵션 A — 다니엘 쌤이 직접 걷는다 (Provenance = WALK)**

| | |
|---|---|
| 헌법 | 제1조·제2조 완전 무해. 제6조(선행의 정량적 인정) 정합 |

**옵션 B — 커뮤니티가 감사로 보낸 코인 (제5조)**

| | |
|---|---|
| 헌법 | **헌법이 가장 강하게 지지한다.** 제4조(첫 수신자=기여자)·제5조(감사의 화폐)·제7조(순환) |
| 코드 | **변경 0줄.** 그냥 이전(transfer)이다 |
| 위폐감지기 | 통과한다 (뿌리가 WALK) |
| **문제 1** | **강제할 수 없다.** 커뮤니티가 주지 않으면 0이다 |
| **문제 2** | 계보에 기증자 회원번호가 남는다 → Layer 3 공개에 기증자 동의 필요 (§2-2) |
| **문제 3** | **창시자가 먼저 요구하면 제1조 위험.** "돈을 버는 것이 목적이 아니다"와 어긋나 보인다. 커뮤니티가 스스로 정할 때만 성립한다 |

**옵션 C — 엔젤로서 접대하고 받은 코인 (제7조)**

| | |
|---|---|
| 헌법 | 완전 정합. 제7조 순환의 원리 그 자체다 |

| **문제** | 규모가 접대 횟수에 묶인다. 그리고 창시자가 실제로 엔젤 노릇을 해야 한다(나쁜 일은 아니다) |

**옵션 D — 창시자 발행 키로 자기에게 GRANT**

| | |
|---|---|
| **문제 1** | ★**발행 키 권력.** 서명 하나로 코인이 생긴다 = 커뮤니티가 두려워하는 바로 그것 |
| **문제 2** | ★**GRANT 계보는 걷기 물리 검사 대상이 아니다.** 위폐감지기는 GRANT를 `grantCount`로 따로 세고 물리 검사에서 뺀다 → **창시자 코인만 진위 기준을 비껴간다.** 목표 #4를 자기 손으로 깬다 |

| **권고** | **자기 발행 금지를 규격에 명문화한다** — `grant.memberId`가 발행자의 선언 신원 집합에 속하면 **거부**. grant에 `memberId`와 `issuerKeyId`가 둘 다 있으므로 **누구나 검증할 수 있다.** 이 규칙은 제2 발행자에게도 그대로 적용된다 |

**옵션 E — GENESIS provenance 신설 (기획보고서의 7,000,000 SHV 경로)**

| | |
|---|---|
| **문제 1** | "모든 코인은 걸음에서 태어난다"(CLAUDE.md:35)가 깨진다 |
| **문제 2** | ★**목표 #4와 논리적으로 양립 불가.** "모두가 인정하는 진품"을 원하면서 자기 코인만 다른 규칙으로 만들 수는 없다. 이건 조문 문제가 아니라 **자기모순**이다 |
| **문제 3** | ★**규격이 무너진다.** 전략 전환 #6대로 제2 발행자가 나오면, 그도 GENESIS를 쓸 수 있다 → **모든 발행자가 무한 발행 가능.** 화폐가 끝난다 |
| **권고** | **하지 않는다.** 이것은 결정 대기 항목이 아니라 **닫는 항목**으로 권고한다 |

### 5.2 권고 — A + B + C

세 가지 모두 뿌리가 WALK다. **코드 변경 0줄, 새 발행 권력 0개, 위폐감지기 통과.**
Provenance에 손대지 않으므로 §4-2(ii)의 "예외 없는 물리 상한"이 저절로 성립한다.

**그 대가는 규모이고, 정직하게 말해야 한다:**

> **7,000,000 SHV 리저브는 이 구조에서 불가능하다.**
> 현실적 규모는 **연 수백~수천 SHV**다.

두 가지 길이 있다.

1. **리저브를 "재고"가 아니라 "흐름"으로 재정의한다.** 미리 쌓아 둔 700만 장이 아니라,
   시간이 지나며 걸어서 쌓이는 양. 기획보고서(`쉬빌_리저브_기획보고서.md`)의
   제네시스 배분 논리를 폐기하고 다시 쓴다.
2. **쉬빌 홈은 리저브 매각이 아니라 제7조 순환으로 조달한다.** 코인을 팔아 집을 사는
   것이 아니라, **집을 내어주는 사람에게 코인이 흐른다.** 이것이 원래 설계이고
   제10조(하루 걸은 사람이 하루의 양식과 쉼을 얻는다)의 문장 그대로다.

**함께 고쳐야 하는 문서:** `쉬빌_리저브_기획보고서.md` 0장 요약표(7,000,000 SHV /
mint-on-milestone / 15% 프리마인 기준선) 전체. 이 표는 옵션 E를 전제로 쓰였다.

## 6. 거래소(쉬빌코인.com)에서의 검증

실제 돈이 오가는 곳이므로 가장 엄격해야 하고, **동시에 가장 투명해야 한다.**

### 6.1 검사 4층

| 층 | 무엇 | 도구 |
|---|---|---|
| **L0 계보** | 서명·ID·이전 체인·회원 증서 | `verifyCoin({trustedRootKeys, requireIntegrityToken: true})` |
| **L1 코어 위폐 검사** | 물리 정합 + 코인 사이 시간 거리 | `checkAuthenticity(제출 지갑 **전량**)` → `coreVerdict` |
| **L2 거래소 규칙 팩** | 거래소가 정한 **더 엄격한** 선 | `rulePacks: [shvilcoin-exchange.v1]` — 공개 JSON |
| **L3 거래소 장부 검사** | 팩으로 표현할 수 없는 것 | 거래소 자체 로직 (아래) |

**★L1에서 반드시 지켜야 할 것: 지갑 전량 제출을 요구한다.**
위폐감지기의 시간 거리 검사(WINDOW_OVERLAP·TIME_BUDGET·SENSOR_DUPLICATE)는 **같은 회원의
코인이 여러 장일 때만 강해진다**(`위폐감지기_설계.md`:118-119). 한 장만 받으면 물리 정합만
본다. **거래소는 지갑 전체를 요구할 수 있는 유일한 장소다** — 그래서 세상에서 가장
강한 검사 지점이 될 수 있다. 이 권한을 쓰지 않으면 거래소를 만드는 의미가 절반 사라진다.

**L3 장부 검사 4종:**

1. **회원별·일자별 누계** (전 제출 이력 통합) — 실측이 지적한 "전역 집계 지점"이
   여기다. 코인을 여러 수신자에게 흩뿌려 일 상한을 우회하는 공격이 **환금구에서 합쳐진다.**
   → **제9조 무해:** 거래를 승인하는 것이 아니라 **자기가 살 것인지를 정하는** 것이다.
   사람 사이의 거래는 계속 무승인·오프라인이다.
2. **일련번호 중복 매입 검사** — 이미 산 번호가 또 오면 이중 판매다.
3. **★조상 번호 검사** — 실측 [B][C]가 이걸 가능하게 한다. 이미 산 코인을 잘게 쪼개
   다시 팔면 자식 번호는 새것이지만 **조상 사슬에 산 번호가 남아 있다.** 계보를 타고
   올라가며 매입 이력과 대조한다.
4. **리저브 목록 대조** — 창시자 리저브 코인이면 표시하고 §6-3의 특별 공시를 건다.

### 6.2 코인을 사들일 때 확인하는 순서

```
1. 규격 버전 + 발행자 신뢰 목록 대조
     → 모르는 발행자면 UNKNOWN_ISSUER (= "여기서 안 삽니다". 위폐가 아니다)
2. L0 계보 검증
3. L1 coreVerdict
     FORGED      → 매입 거부 + 근거(findings + proofHash) 전량 반환
     SUSPECT     → 보류. 사람 검토. 자동 거부하지 않는다(억울한 지목 방지, 제3조)
     AUTHENTIC   → 진행
4. L2 거래소 팩 (extendedVerdict)
5. L3 장부 (일자별 누계 / 중복 번호 / 조상 번호 / 리저브 대조)
6. 매입 확정 → 매입 공시 (일련번호, 금액, 날짜)
     창시자 코인이면 원번호 그대로 100% 공시
```

### 6.3 ★거래소가 새로운 중앙이 되는 것을 막는 5개 장치

이것이 이 장에서 가장 중요하다. 판정 권력은 발행 권력보다 강하다 —
**무엇이 진짜인지 정하는 자가 화폐를 소유한다.**

| # | 장치 | 왜 이것이 권력을 없애는가 |
|---|---|---|
| **1** | **기준 전량 공개** — 코어 버전(해시 고정) + 규칙 팩 JSON + 장부 규칙 문서. 비공개 기준 금지 | 기준이 공개면 그것은 규격이지 권력이 아니다 |
| **2** | **사전 자가 검사** — 팔기 전에 판매자가 **같은 답**을 자기 기기에서 얻는다. `tools/checker/배포/쉬빌_위폐감지기.html`(오프라인 단일 파일)에 거래소 팩을 얹으면 된다 | 판정이 **순수 함수**라서 가능하다. 거래소가 "우리 서버만 아는 판정"을 할 수 없다 |
| **3** | **거부 사유 기계 판독** — `findings` + `proofHash` + `packId/ruleId`. "그냥 안 삽니다" 금지 | 재현 가능한 거부만 허용. 자의적 거부가 즉시 드러난다 |
| **4** | **어휘 분리** — `FORGED`(위폐) / `NOT_PURCHASABLE_HERE`(안 삼) / `UNKNOWN_ISSUER`(모르는 발행자)를 절대 섞지 않는다 | ★**거래소는 화폐를 죽일 권한이 없다.** 거래소가 안 사도 그 코인은 사람 사이에서 계속 돈다(제9조). 다니엘 쌤 원칙 1("새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지 않는다")이 여기서 코드 수준으로 지켜진다. `화폐규격_다발행자_설계.md` §5-4와 같은 요구다 |
| **5** | **복수 거래소 명문 허용** — 규격이 공개이므로 누구나 거래소를 열 수 있다 | 독점이 아니면 판정 권력이 아니다. 전략 전환 #6("다른 사람이 다른 코인 생성기를 만들어도 된다")의 거래소 판이다 |

**추가 — 이해상충 처리:** 거래소가 창시자 소유인데 창시자 리저브를 거기서 판다 =
구조적 이해상충이다. 대응 셋:
 (ㄱ) 창시자 매각분은 **사전** 공시(팔기 전에 번호·수량·날짜를 먼저 게시).
 (ㄴ) 제3자 감사자 1인 이상을 커뮤니티가 지명하고, 그에게 Layer 3 열람권을 준다.
 (ㄷ) 창시자 매각은 **일반 사용자 매입보다 불리한 조건**(예: 후순위·수량 상한)을 스스로 건다.

**★거래소가 절대 해서는 안 되는 것 한 가지: 코어 검사를 완화하는 것.**
규칙 팩은 구조적으로 **더하기만 가능**하다(`rulePack.ts`:19-26 — DSL에 "무시"·"허용"·"예외"
연산자가 아예 없다). 거래소가 "우리는 이 검사를 끕니다"라고 말하는 순간 **coreVerdict가
사람마다 달라지고 화폐가 쪼개진다.** 이것은 정책이 아니라 규격의 불변식으로 못 박아야 한다.

## 7. 다니엘 쌤이 실제로 해야 할 일

개발자가 필요한 부분과 아닌 부분을 나눠 적는다.

### 7.1 단계

| 단계 | 다니엘 쌤이 하는 일 | 개발자가 하는 일 | 소요 |
|---|---|---|---|
| **0. 결정** | §7-3의 질문 5개에 답한다 | — | 하루 |
| **1. 걷는다** | 지갑을 켜고 걷는다. "여기서 정산"으로 코인을 만든다 | 없음 (지금 코드 그대로) | 계속 |
| **2. 분리 보관** | **리저브 전용 기기 1대.** 일상 지갑과 절대 섞지 않는다. 백업 문구를 종이로 2부 보관 | 없음 | 1일 |
| **3. 목록 뽑기** | 지갑의 "검사용 내보내기"를 눌러 파일 하나를 개발팀에 보낸다 | 일련번호 목록 + 머클 루트 생성 | 반나절 |
| **4. 선언문 서명** | 1페이지 선언문을 읽고 서명한다 (§7-4) | 선언문 서식 준비 | 1시간 |
| **5. 게시** | "게시해도 좋다"고 승인한다 | 투명성 페이지 + 감지기 배포본 + 외부 앵커 + 미러 (§3-3) | 2~3일 |
| **6. 유지** | **3개월마다** 같은 루트를 다시 서명한다. 늘었으면 늘어난 내역을 함께 | 재공표 스크립트 | 분기 1시간 |
| **7. 매각 시** | 팔기 **전에** 번호·수량·날짜를 알린다 | 매각 공시 게시 | 건당 |

### 7.2 다니엘 쌤 없이는 못 하는 일 / 개발자 없이는 못 하는 일

- **다니엘 쌤만 할 수 있는 것:** 걷기, 신원 선언(어느 회원번호가 자기 것인지), 서명,
  "7,000,000을 폐기한다"는 결정, 매각 공시 승인.
- **개발자가 해야 하는 것:** 머클 루트 계산, 페이지 게시, 앵커 트랜잭션, 재공표 스크립트,
  거래소 검사 파이프라인.
- **아무도 할 수 없는 것:** "숨긴 코인이 없다"는 증명 (§4-3).

### 7.3 지금 답해야 할 5개 질문

1. **리저브를 걸어서 만드는가?** (옵션 A+B+C) — 그렇다면 §5-2에 따라
   **7,000,000 SHV는 폐기**되고 기획보고서를 다시 써야 한다.
2. **GENESIS를 만들지 않는다는 데 동의하는가?** (옵션 E 영구 폐기) — 권고: 동의.
3. **신원 선언에 동의하는가?** — 통제하는 회원번호를 전부 공개하고, 선언 밖 코인에 대한
   소유 주장을 스스로 포기하는 것.
4. **창시자 매각분 100% 사전 공시에 동의하는가?** (§4-2 iv, §6-3)
5. **커뮤니티가 감사로 코인을 보내는 것(옵션 B)을 받을 것인가?**
   받는다면 **먼저 요구하지 않는다**는 원칙을 함께 세울 것인가.

### 7.4 선언문 6조 (초안 — 그대로 서명 가능한 문장)

```
1. 내가 통제하는 회원번호는 아래 목록이 전부다.
2. 아래 일련번호 목록 N장, 합계 M SHV가 내 리저브 전부이며, 머클 루트는 …이다.
3. 이 목록에 없는 회원번호로 만들어진 코인을 나중에 내 리저브라고 주장하지 않는다.
   주장하더라도 그 주장은 무효다.
4. 신원을 추가할 일이 생기면 코인을 만들기 전에 먼저 공표한다.
5. 리저브를 팔 때는 팔기 전에 일련번호·수량·날짜를 공시한다.
6. 나는 "내가 코인을 더 만들 수 없다"고 약속하지 않는다. 나도 걸으면 코인이 생긴다.
   내가 약속하는 것은 그것이 리저브 행세를 하지 않는다는 것,
   그리고 시장에 나오면 반드시 보인다는 것이다.
```

6조가 이 선언문에서 가장 중요하다. **지킬 수 없는 약속을 하지 않는 것**이
신뢰를 만든다(제3조 — 속도보다 진리).

## 10. 한계 (정직화)

- **§4-3이 이 문서의 가장 중요한 부분이다.** (b)는 완전히 달성되지 않는다.
- **거래소의 제2조 적법성은 이 문서가 다루지 않는다.** `거래소_헌법제2조_충돌정리.md`의
  질문 4개(②의 주어 / 매각 대금은 매출인가 투자인가 / 리저브는 걸은 것인가 발행할 것인가 /
  T-4는 유효한가)가 먼저 답해져야 §6 전체가 착수 가능하다.
  **그중 세 번째 질문에 대한 이 문서의 답은 §5다 — "걸어서 만든다".**
- **머클 루트 형식·정렬 규칙·해시 도메인 문자열을 규격에 못 박지 않았다.**
  제2 발행자가 다르게 구현하면 호환이 깨진다. `화폐규격_다발행자_설계.md` §7-1과 같은
  종류의 결정 대기 항목이다.
- **`설계 1`의 체크포인트 정의를 직접 읽지 못했다.** §3은 저장소에 실재하는 두 가지
  체크포인트(물리 QR / 시각 앵커)를 기준으로 썼다. 설계 1이 세 번째 정의를 쓴다면
  §3-2의 표를 다시 맞춰야 한다.
- **거래소 규칙 팩 `shvilcoin-exchange.v1`의 실제 임계값을 정하지 않았다.**
  파일럿 데이터 없이 정하면 억울한 거부가 난다(제3조). 초기값은 **코어만**으로 시작하고
  팩은 데이터가 쌓인 뒤 더할 것을 권고한다.
