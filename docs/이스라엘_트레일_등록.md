# 쉬빌 이스라엘 트레일 등록 — 8.27 km → 1,055 km

> 2026-07-27. 다니엘 쌤 질문: **"왜 등록 코스가 8.27 KM 밖에 안 되지?"**
> 출처 지시: israeltrail.net/maps, https://israelhiking.osm.org.il/
>
> 헌법 제3조(속도보다 진리)·제6조(선행의 정량적 인정)에 걸린 사안이다.
> 등록 코스 좌표가 곧 코인이 생성되는 땅이므로, 틀리면 (가) 정직한 하이커가
> 인정을 못 받거나 (나) 트레일 밖에서 코인이 생성된다.

## 0. 한 줄 결론

배포되던 `shvil-israel`은 **개발 초기에 손으로 찍은 11점짜리 가짜 선**이었다.
OSM 관계 282071(이스라엘 트레일 위원회 관리)의 실측 경로로 교체했고,
**등록 코스는 6.72 km → 1,055.28 km(5,569점)** 가 됐다. 분당–불곡산 1.55 km를
합해 다니엘 쌤이 보신 8.27 km가 나왔던 것이다.

## 1. 왜 8.27 km 였나 — 원인 3가지

### 원인 ① 세계 코스 생성기 매니페스트에 **이스라엘이 아예 없었다**

M14 "세계 10대 코스 활성화" 작업이 카미노·안나푸르나·밀포드 같은 해외 트레일만
매니페스트에 올렸다. **본진인 쉬빌 이스라엘은 "이미 된 것"으로 착각하고 빠뜨렸다.**
그래서 실측 데이터를 받아오는 파이프라인이 이스라엘에는 한 번도 돌지 않았다.

### 원인 ② `SHVIL_ISRAEL_NORTH_SAMPLE`이 실제 트레일이 아니었다

`packages/shared/src/courses.ts`에 있던 11점·6.72 km 상수는 회랑 엔진 단위 테스트용
합성 좌표였다. 그런데 그것이 그대로 서버 배포 목록(`BUILTIN_COURSES`)에 실려 나갔다.

실측한 결과 **이 선은 실제 INT 위에 단 한 점도 없다**:

| 샘플선 → 실제 트레일 최단거리 | 값 |
|---|---|
| 최소 | 961 m |
| 중앙 | 1,793 m |
| 최대 | 3,142 m |
| 회랑 50 m 안에 드는 비율 | **0.0 %** |

즉 교체 전에는 **실제 쉬빌 이스라엘을 종주해도 전 구간이 "코스 밖"** 이었고,
반대로 트레일이 아닌 그 선 위를 걸으면 코인이 생성됐다. 정직화(제3조) 위반이다.

### 원인 ③ 카미노 검사 실패가 파이프라인 신뢰를 떨어뜨렸다

카미노 프란세스를 처음 생성했을 때 **1,518.6 km(기대 780 km 대비 +95%)** 가 나와
`expectedKm ±15%` 검사에서 탈락했다. 원인은 OSM 데이터가 아니라 생성기의
**구간(하위 관계) 정렬 버그**였다 — 상위 관계의 하위 6개 구간을 이어붙이는 순서가
틀려 왕복 경로가 만들어졌다. 이 실패 때문에 "세계 코스 데이터는 아직 못 믿는다"는
인상이 남았고, 이스라엘까지 손대지 않은 채로 넘어갔다.
(2026-07-27 수정됨 — 재생성 시 767.5 km → 단순화 756.9 km, 기대 대비 -3.0% 통과.)

## 5. 성능·번들 영향 (숫자)

### 5-1. 회랑 판정 (앱 CPU)

`nearestOnPolyline`은 공간 색인 없는 **O(n) 전수 스캔**이다.

| | 판정 1회 (데스크톱 V8) |
|---|---|
| 옛 샘플 (11점 + 분당 8점) | 0.0002 ms |
| 실물 (5,569점 + 분당 8점) | **0.089 ms (429배)** |

픽스 1개당 판정 2회(`addFix` 1회 + `closeWindow` 1회), 5초 간격 → 하루 10시간이면
7,200픽스 / 14,400판정 / 선분 거리계산 80.3 M회.

폰 환산(Hermes 감속 ×15 가정 — **실기기 측정 아님, 추정임을 밝힌다**):
하루 CPU 19.2초 = 10시간의 **0.053 %**, 에너지 약 8 mWh.
대조: GPS `BestForNavigation` 10시간 = 1,000~2,000 mWh, 배터리 4,500 mAh = 17,325 mWh.

→ **배터리 문제가 아니다** (GPS 대비 1/125~1/250). 체감 가능한 유일한 지점은
60초 창 마감 때 60 Hz 프레임 1~2개 드랍.
→ 코스가 30개를 넘으면 공간 색인(bbox 조기탈출 + 타일)이 필요하다. 시제품 실측으로
   전수 대비 55배 빨라지고 판정 결과는 동일함을 확인했다.

### 6-1. ★재현되지 않았다 — 회랑 오탐 (그래서 고치지 않았다)

### 6-2. ★재현되지 않았다 — 트레일 아닌 땅이 회랑에 들어오는가

3-4에 적은 양방향 대조가 답이다. 최대 편차 20.3 m로 회랑 50 m 안이다.

한계: 이 측정의 기준이 OSM 원본이다. **원본 자체가 성긴 37.2 km(3.4 %)** 는 이
방법으로 잡히지 않는다. 실제 걸은 사람의 보고로만 잡힌다.

### 6-3. ★재현됐다 — 창 경계 거리 누락 8.33 % (**고쳤다**)

`closeWindow()`가 창 안의 픽스 사이만 합산하고 버퍼를 비워서, "직전 창의 마지막
픽스 → 다음 창의 첫 픽스" 구간이 어느 창에도 들어가지 않았다.

| 픽스 간격 | 창 픽스 수 | 수정 전 누락 | **수정 후 (실측)** |
|---|---|---|---|
| 1초 | 60 | 1.67 % | ~0 % |
| **5초 (운영 설정)** | 12 | **8.33 %** | **0.25 %** ← 실물 1,080 km 완주 실측 |
| 6초 (3.0 km/h) | 10 | 10.00 % | ~0 % |
| 7.2초 (2.5 km/h 무거운 배낭) | 8 | 12.50 % | ~0 % |
| 10초 | 6 | 16.67 % | **0.67 %** ← 실물 98.5 km 구간 실측 |
| 15초 | 4 | 25.00 % | **1.09 %** ← 실물 98.5 km 구간 실측 |

남는 0.25~1.09 %는 `WalkSample.distanceM`이 정수 미터라 창마다 ±0.5 m 반올림이
생기는 것과, **세션의 첫 창에는 이월할 직전 창이 없기 때문**이다. 둘 다 정직한 값이다.

**느리게 걷는 사람일수록 손해가 컸다** (`distanceInterval: 5`가 픽스 간격을 늘린다).
1,055 km 완주 기준 **90~140 SHV**가 사라지고 있었다. 실제로 걸은 거리이므로
제6조(선행의 정량적 인정) 위반이다.

수정: `apps/wallet/src/walk/corridorEngine.ts` — 창이 닫힐 때 마지막 좌표 **한 점**을
남겨 다음 픽스가 오면 거리로 환산하고 **좌표는 즉시 폐기**한다(다음 창이 들고 가는 것은
미터·초 스칼라뿐 — 제9조 위치 비저장 유지). 세 겹으로 잠근다:

1. **시간 한도 30초** — 그보다 벌어지면 이월하지 않는다(GPS 두절·앱 재시작·차량).
2. **자기 속도 상한** — 이월분 ≤ (그 창의 평균 속도 × 경계 시간).
   수식상 `(D + p·Δt)/(T + Δt) ≤ D/T` 이므로 **이월은 창의 평균 속도를 절대 올리지
   않는다.** 경계에서 GPS가 500 m 튀어도 멀쩡한 창이 TOO_FAST/VEHICLE로 뒤집히지
   않고, 걷지 않은 거리가 새로 생기지도 않는다.
3. **무효 창은 이월을 끊는다** — mock location·픽스 부족 창을 건너뛰어 잇지 않는다.

회귀 테스트: `apps/wallet/src/walk/__tests__/windowBoundaryLoss.test.ts` (7개, 상시 실행)

### 6-4. ★재현됐다 — 회랑 반폭 무검증 (**고쳤다**)

`POST /courses/proposals`의 `segments`가 `unknown[]`로 들어와 **검증 없이** 저장·배포됐다.
실행으로 확인한 결과:

```
200 m 직선 코스 + corridorHalfWidthM: 50000
  코스 위: ON_COURSE   1 km 밖: ON_COURSE
  20 km 밖: ON_COURSE  45 km 밖: ON_COURSE   서울 시청: ON_COURSE
```

승격에는 사람 검토가 없다 — 완주 기록(`distanceM`/`days`)은 자기신고 정수이고,
`promotionThreshold`(운영 기본 100명)만 모이면 자동 OFFICIAL이 된다.
**"트레일 밖에서 코인이 생성되는가"의 답이 '예'인 유일한 경로였다.**

수정 (두 겹):
- `packages/shared/src/courses.ts` — `validateCoursePolyline` / `validateCourseSegments`
  신설. 회랑 반폭 **10~150 m**, 난이도 계수 **10~40(×1.0~×4.0)**, 지형 열거값,
  인덱스 범위, 좌표 범위를 검사한다. 값을 **조용히 고치지 않고 거부**한다.
- `corridorHalfWidthAt`이 읽는 쪽에서도 **클램프**한다 — 옛 DB 행·조작된 캐시·다른
  배포자를 통해 검사를 우회한 데이터가 들어와도 회랑은 150 m를 넘지 않는다.
- `segmentMetaAt`이 빈 `segments`에서 던지지 않게 안전값으로 떨어진다
  (예전에는 픽스마다 예외 → 걷기 자체가 멈춤 = 0층 붕괴).

대역 자체는 **새 정책이 아니다.** 150 m는 `DEFAULT_CORRIDOR_HALF_WIDTH_M.URBAN`,
40은 `difficultyMaxTenths`(확정 파라미터)에서 그대로 왔다.

회귀 테스트: `packages/shared/src/__tests__/courseGeometry.test.ts` (14개),
`server/test/courseGeometryGuard.test.ts` (8개)

### 6-5. ★재현됐다 — 생성기가 등록 코스를 지운다 (**고쳤다**)

작업 도중 **`SHVIL_ISRAEL`이 파일에서 통째로 사라져 3개 워크스페이스가 컴파일되지

## 7. 남는 위험

### 7-1. ★GPS 흔들림이 요율을 결정한다 (고치지 않았다 — 실기기 측정 필요)

`distanceM`은 픽스 사이 haversine의 **절댓값 합**이라 평균 0인 GPS 오차도 거리를
한쪽으로만 부풀린다. 결과는 둘 중 하나이고 둘 다 나쁘다: 과대발행이거나,
속도가 `maxWalkSpeedKmh=6`을 넘어 **창 전체가 TOO_FAST로 기각**(감액이 아니라 0)이다.

| 잡음 모형 | 방출/걸은 | 기각 창 |
|---|---|---|
| σ 5 m, ρ 0.98 (양호) | -6.3 % | 0.00 % |
| σ 10 m, ρ 0.98 (보통) | +0.5 % | 0.61 % |
| σ 15 m, ρ 0.98 (나쁨) | +10.4 % | 2.66 % |
| σ 15 m, ρ 0.90 (협곡) | +47.4 % | **34.77 %** |

★**이번 세션 실측 (σ=15 m 드리프트를 얹은 1,080 km 완주, 창 18,011개)**:

```
ON_COURSE 17985 (99.86%)  OFF_COURSE 26  DAILY_LIFE 0
폴리라인 이탈거리: 중앙 10.5m p95 31.1m p99 41.2m 최대 65.1m / 회랑밖 픽스 0.18%
실제 걸은 1080.66 km → 창이 방출한 거리 1706.47 km (+57.9% 부풀림)
60일 776.9 SHV | 기각 TOO_FAST×5017 STEP_DISTANCE_MISMATCH×3806 VEHICLE×30
```

**회랑은 99.86 %를 통과시켰는데 발행은 1,077.9 → 776.9 SHV (-28 %) 로 떨어졌다.**
잃은 301 SHV는 전부 **속도·보폭 필터의 창 기각**에서 나왔다. 취약한 부품은 회랑이
아니다. 빠른 사람이 더 위험하다(5 km/h에서 기각 64 %) — 6 km/h 컷까지 여유가
20 %뿐이기 때문이다.

정직하게 적는다: **잡음은 합성이다.** ρ=0.9(5초 간격)는 비관적이고 실제 GPS 드리프트는
분 단위로 상관되므로 ρ≈0.98이 현실적이다. 실기기 픽스는 이미 융합·평활되어 팽창이 더
작을 수 있다. **방향은 확실하나 크기는 `docs/M1_실기기_테스트_가이드.md`로 실측해야
한다.** 필터 상수를 바꾸는 것은 통화정책 인접 결정이므로 손대지 않았다.

### 7-2. ★1,055 km 전 구간이 단일 구간 메타

`worldCourses.ts`의 `segments`는 `[{fromIdx:0, toIdx:5568, terrain:"OPEN",
difficultyTenths:10}]` 하나뿐이다. 즉 전 구간 회랑 50 m·난이도 ×1.0이다.
6-1에서 회랑은 문제없음이 확인됐으므로 이것은 **오탐 위험이 아니라 난이도 미세조정
과제**다. 구간별 난이도 계수는 산정 공식이 확정되지 않았다(→ 9절).

### 7-3. ★도시 구간 — 트레일이 맞지만 발행 누수처럼 보인다

시가지 안 트레일이 **113.2 km = 전체의 10.7 %** 다. 특히 **야르콘 회랑 27.26 km**
(텔아비브 항 하구 → 로쉬하아인, 야르콘 강 공원길 그대로)와 해안 산책로 31.47 km.

실측: 야르콘 위 5 km 산책 → **65창 전부 ON_COURSE, 필터 거부 0, 5.0 SHV.**
**어떤 방어층도 이걸 잡지 못한다** — 회랑 통과(진짜 트레일이니까), 걷기 필터 통과
(진짜 걷고 있으니까), 인간 한계 통과, mock 아님. 탐지할 신호 자체가 없다.
야르콘 회랑 편도가 27.3 km라 **왕복 한 번이면 하루 상한 40 SHV**다.

| 선택지 | 성격 |
|---|---|
| **A (권장)** 그대로 둔다. 야르콘을 걷는 시민도 쉬빌 이스라엘을 걷는 게 맞다 | 현상유지 |
| B 도시 구간 난이도를 ×0.1~×0.3으로 낮춘다 | **통화정책 — 다니엘 쌤 결정** |
| C 도시 구간 회랑 반폭을 50 → 20 m로 좁힌다 | 판정 관용도 |
| D 종주 문맥 요구 (연속 진행일 때만 기준 요율) | 만보기 모델과 충돌 검토 필요 |

권고는 **A + 관찰**이다(제3조·제8조 — 아직 존재하지 않는 남용을 막느라 정직한
하이커의 인정을 깎지 않는다). 다만 **지금 사용자가 사실상 없을 때가 요율을 바꿀 수
있는 마지막 시점**이라는 것은 짚어 둔다.
※ 도시 구간 길이는 도시 중심·반경 근사로 추정한 값이다(OSM landuse 미사용).
   야르콘·해안 구간은 폴리라인 궤적으로 직접 확인했다.

### 7-4. OSM 원본이 성긴 37.2 km (3.4 %)

way 내부 노드 간격 250 m 초과 81곳(합계 37.2 km), 500 m 초과 18곳, 최대 1,912 m.
아라바 사막 트랙에 몰려 있다. 그 구간은 OSM이 직선으로만 말하므로 **실제 길이 굽으면
회랑 밖**이다. 우리 파이프라인 잘못이 아니라 원본 한계이고, **실제 걸은 사람의
보고로만 잡힌다**(→ 계획서 §5 좌표 보정 절차).

### 7-5. 회랑 판정은 여전히 O(n) 전수 스캔

5-1 참조. 코스 30개를 넘으면 공간 색인이 필요하다. 지금 값어치 있는 것은
bbox 조기탈출 한 줄뿐(코스 없는 나라에서 CPU 0).

### 7-6. `/courses` 173.8 KB 무압축

`@fastify/compress`가 설치돼 있지 않다. gzip이면 34.0 KB, brotli 20.1 KB.
사막 2G(20 kB/s)에서 약 9초. 지갑 fetch에 타임아웃도 없다
(`apps/wallet/src/core/api.ts`에 AbortSignal 없음). **의존성 추가는 다니엘 쌤 결정.**

### 7-7. 배포 캐시 지문이 폴리라인을 읽지 않는다

`registryFingerprint`(server/src/courses.ts)는 공식 코스 ID 목록만 본다. 현재
`course_proposals` 행은 삽입 후 status만 UPDATE되므로 정확하지만, **나중에 코스
데이터를 수정 가능하게 만들면 지문에 수정 시각을 반드시 넣어야 한다.**

### 7-8. 가짜 엔젤이 오프라인 폴백에 실려 있다

`SAMPLE_ANGELS`(다프나의 집(샘플)·하고쉬림 정원(샘플))가 실물 트레일에서 각각
1.90 km / 1.93 km 떨어져 있다. 회랑 안에서는 엔젤 판정이 돌지 않으므로 발행 왜곡은
없지만, 갈릴리 km 18~22에서 코스를 벗어난 사람이 **확정될 수 없는** ANGEL_DETOUR를
받고 `getLiveStatus().nearestAngel`이 실제 하이커에게 가짜 엔젤을 표시한다.

### 7-9. 일련번호 체크 문자가 단일 오타를 3.1 % 놓친다 (이번 작업 무관)

`serial.ts`의 체크 문자는 Crockford Base32 한 글자(32값)라 한 글자 오타가
**1/32 = 3.1 %** 확률로 검출되지 않는다. 이것은 구현 결함이 아니라 형식의 성질이며
`serial.ts` 주석도 "체크 문자는 오타를 즉시 잡기 위한 것이지 위조 방어가 아니다"라고
적고 있다. 이번에 **검출률을 재는 검사를 추가해 못박았다**(10절).

남는 위험: 사람이 번호를 손으로 옮겨 적다 한 글자를 틀리면 3.1 % 확률로
**다른 유효한 번호**가 되어 조용히 통과한다. 진위 판정은 `authenticity.ts`가 코인
전체를 보고 하므로 화폐가 위조되지는 않지만, "이 코인 맞나요"를 번호로 확인하는
장면에서는 오답이 나올 수 있다.
체크 문자 알고리즘을 바꾸면 **모든 코인의 표시 일련번호 끝자리가 바뀐다** —
화폐 표기 변경이므로 다니엘 쌤 결정 사항이다. 알고리즘은 손대지 않았다.
