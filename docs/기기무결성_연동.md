# 기기 무결성 실연동 (Play Integrity) — M15

> 2026-07-26 다니엘 쌤: **"앱 코드를 바꾸면 앱 무결성이 손상되잖아"** — 이 지적이
> 이 작업의 근거다. 생체 인증·인간 한계·회랑 판정은 전부 **앱 안의 검사**라 변조 앱이
> 지우면 그만이다. 무결성 인증만이 앱 **바깥**에서 "이 앱이 진짜인가"를 증언한다.

## 1. 왜 이것이 방어의 뿌리인가

지금까지 쌓은 방어를 나열해 보면 전부 앱 안에 있다:

| 방어 | 어디서 | 변조 앱이 지우면? |
|---|---|---|
| 회랑 판정 (코스 위인가) | 앱 | 아무 데서나 코인 생성 |
| 인간 한계 (일 40 SHV) | 앱 | 무제한 발행 |
| 생체 인증 | 앱 | 지문 없이 서명 |
| **기기 무결성** | **Google/Apple** | **불가능 — 서명이 바뀌면 인증 자체가 안 나온다** |

이번 세션에서 수리한 **스팟 예치 무제한 발행구**도 뿌리가 같았다. 부풀린 걷기 코인이
진짜 그랜트로 재배포됐는데, 그것을 만든 것이 변조 앱이고 그 변조를 아무도 증언하지
못했기 때문이다. 무결성이 있으면 그런 코인은 UNVERIFIED 증서를 달고 나와 수신 지갑이
거부한다 — **"앱을 고친다"는 선택지 자체가 값을 잃는다.**

## 2. 헌법 제9조와 어긋나지 않는 이유

무결성 검증은 **민팅 자격 확립**이지 거래 승인이 아니다:

- 서버는 **가입·증서 갱신 시점에만** 개입한다 (30일 주기)
- 이후 지불·수령·검증은 계속 **두 기기의 로컬에서 오프라인**으로 완결된다
- 서버가 무결성을 근거로 **개별 거래를 막는 경로는 코드에 없다** — 반환값은 증서에
  각인될 등급뿐이다

구글/애플도 "중앙"이긴 하다. 그러나 **거래를 통제하는 중앙이 아니라 기기를 증언하는
중앙**이다. SMS(통신사 DB 조회)보다 오히려 덜 중앙집중적이며, 통신사 가입 없이 동작한다.

## 3. 구현한 것 (코드 완료)

### 서버
- **`server/src/playIntegrity.ts`** (신규): Google에 토큰 제출 → 판정 수신.
  서비스 계정 JWT로 액세스 토큰 발급 → `decodeIntegrityToken` 호출 →
  `deviceIntegrity`로 등급 판정 (MEETS_DEVICE_INTEGRITY→VERIFIED, MEETS_BASIC→BASIC).
  패키지명 대조·토큰 신선도(10분) 검사 포함.
- **`server/src/integrity.ts`**: 챌린지 발급·소비 + 비동기 실검증(`verifyIntegrityAsync`).
- **`POST /auth/integrity-challenge`** (신규): 1회용 챌린지 발급 (비서명 — 가입 전에도 필요).
- 가입·증서 갱신이 실검증 결과를 증서에 각인한다.
- **`integrity_challenges`** 테이블: 챌린지·기기공개키·발급/만료/소비 시각. 좌표·개인정보 없음.

### 지갑
- **`apps/wallet/src/core/integrityNonce.ts`** (신규): 서버와 **정확히 같은** nonce 계산.
- **`apps/wallet/src/core/integrity.ts`**: Play Integrity 네이티브 모듈 지연 로드 →
  실토큰 획득. 모듈이 없으면(Expo Go·iOS) 조용히 폴백 — 앱은 계속 동작한다.
- 증서 갱신 흐름이 챌린지를 먼저 받아 nonce에 실어 보낸다.

### 재생·중계 공격 방어 (핵심)

토큰만 훔쳐 다른 기기에서 쓰지 못하도록 **서버 챌린지 + 기기 공개키를 함께 묶어**
nonce를 만든다. Google이 토큰 안에 그 nonce를 되돌려주므로 서버가 전부 대조한다:

```
nonce = sha256("shvil-integrity|<len>:<challenge>|<len>:<devicePublicKey>").base64url
```

★길이 접두(`<len>:`)는 테스트가 잡아낸 실제 결함의 수리다 — 단순 연결이면
`("a|b","c")`와 `("a","b|c")`가 같은 nonce가 되어 결속이 무의미해진다.

검사: ①내가 낸 챌린지인가 ②소비 전인가 ③이 기기 것인가 ④만료 전인가 ⑤nonce 일치.
**실패한 시도도 챌린지를 소비**해 무차별 재시도를 막는다.

### fail-closed 원칙

미설정·API 오류·미지원 플랫폼·토큰 없음 — **전부 UNVERIFIED**로 수렴한다. 통과로
삼지 않는다. 대신 등급 정책이 UNVERIFIED에게도 기본 걷기를 허용해 0층을 지킨다.

**검증**: 서버 18 + 지갑 5 = 무결성 전용 테스트 23개. 전체 604개 통과.

## 4. 다니엘 쌤이 할 일

### ① Play Console 등록 (진행 중)
$25 1회. 패키지명 **`org.shvil.wallet`** (APK와 일치해야 함). "내부 테스트" 트랙이면 충분.

### ② Google Cloud 서비스 계정 만들기

1. https://console.cloud.google.com → 프로젝트 선택(또는 새로 만들기)
2. **API 및 서비스 → 라이브러리** → "Play Integrity API" 검색 → **사용 설정**
3. **IAM 및 관리자 → 서비스 계정** → **서비스 계정 만들기**
   - 이름: `shvil-integrity` (아무거나)
   - 역할은 지정 안 해도 됨 → 완료
4. 만든 계정 클릭 → **키** 탭 → **키 추가 → 새 키 만들기 → JSON** → 파일 다운로드
5. Play Console → **설정 → API 액세스** → 그 서비스 계정을 연결 (앱 권한 부여)

### ③ Render에 환경변수 넣기

다운로드한 JSON 파일을 열면 `client_email`과 `private_key`가 있습니다. Render →
shvil-directory → **Environment**에 3개 추가:

```
SHVIL_PLAY_PACKAGE       org.shvil.wallet
SHVIL_PLAY_CLIENT_EMAIL  (JSON의 client_email 값)
SHVIL_PLAY_PRIVATE_KEY   (JSON의 private_key 값 — 통째로 붙여넣기)
```

⚠ `private_key`는 `-----BEGIN PRIVATE KEY-----`로 시작하는 긴 문자열입니다. 줄바꿈이
`\n`으로 되어 있어도 그대로 붙여넣으면 서버가 변환합니다.

### ④ 나중에 (Play 배포 후)
```
SHVIL_REQUIRE_PLAY_RECOGNIZED = 1
```
이걸 켜면 **앱 변조까지** 막힙니다. Play Store로 배포하기 전에는 끄고 두어야 합니다
(사이드로드 APK는 정상적으로 "인식 안 됨"이 나오기 때문).

## 5. 전환 순서 (중요 — 기존 사용자를 깨지 않으려면)

지금 `requireIntegrity: !devMode`인데, 무결성이 UNVERIFIED만 반환하는 상태에서 devMode를
끄면 **모든 걷기 코인이 즉시 거부**된다. 순서를 지켜야 한다:

1. **지금**: devMode=1 유지. 코드만 배포 (무결성은 아직 UNVERIFIED)
2. **②③ 완료 후**: 환경변수 넣고 재배포 → 안드로이드 실기기에서 VERIFIED가 나오는지 확인
3. **VERIFIED 확인 후**: devMode=0으로 전환
4. **Play 배포 후**: `SHVIL_REQUIRE_PLAY_RECOGNIZED=1`

## 5-A. 적대적 검증 결과 — 치명 결함 3건 시정 (2026-07-26)

구현 직후 3렌즈(우회·가용성·헌법) 적대검증에서 **44건**이 나왔고, 그중 치명 3건은
"이 구현이 다니엘 쌤 질문에 사실은 '아니오'라고 답한다"는 것이었다. 시정 내역:

### ① 변조 APK가 그대로 VERIFIED를 받았다 (치명·시정 완료)
**문제**: 앱 동일성 검사가 "패키지명 문자열 일치" 하나뿐이었다. 그런데 패키지명은
공격자가 자기 빌드에서 임의로 정하는 값이다. 공격자가 쉬빌 APK를 디컴파일해 인간
한계·회랑 판정을 제거하고, 패키지명은 그대로 둔 채 **자기 키로 서명**해 정품 폰에
설치하면 → 패키지명 일치 + 기기 진짜 → **VERIFIED**. 무결성의 목적 자체가 무효.

**시정**: `appIntegrity.certificateSha256Digest`를 EAS 키스토어 지문
(`SHVIL_ANDROID_CERT_DIGESTS`)과 대조한다. 서명 키는 공격자가 가질 수 없으므로
**지문 대조만이 "우리가 빌드한 앱"을 증명한다.** 지문 불일치·부재·미설정은 전부
UNVERIFIED로 **고정**한다(강등 아님 — BASIC도 P2P 수령이 열리므로).

### ② 무인증 요청으로 남의 코인을 소각할 수 있었다 (치명·시정 완료)
**문제**: 챌린지 발급이 같은 기기 키의 미소비 챌린지를 전부 `DELETE` 했다. 그런데 이
라우트는 **무인증**이고 `devicePublicKey`는 코인 계보에 실려 **공개 유통되는 값**이다.
공격자가 피해자 키로 반복 호출 → 피해자가 방금 받은 챌린지가 계속 지워짐 → 증서
갱신 영구 실패 → 30일 뒤 만료 → **그 사람의 모든 걷기 코인이 무효화**.

**시정**: 남의 챌린지를 지우지 않는다. 동시 보유 개수 상한(5개)만 두고 초과 시
**가장 오래된 것 하나만** 밀어낸다 — 방금 받은 사람은 피해를 보지 않는다.

### ③ 실토큰이 단 한 번도 만들어지지 않았다 (치명·부분 시정)
**문제**: `react-native-google-play-integrity`가 package.json에 없어 지연 로드가 항상
실패하고, 무조건 `'dev-verified'`를 반환했다. 코드와 문서는 "실연동 완료"로 읽히는데
실제로는 아무것도 검증되지 않았다.

**시정(부분)**: 폴백을 정직하게 만들었다 — 배포 빌드는 빈 토큰 + `reason` 코드를
보내고, 개발 토큰은 `__DEV__`에서만 쓴다. **남은 것**: 네이티브 모듈 실제 설치 +
EAS 재빌드 + 실기기 실측. 그전까지 안드로이드도 UNVERIFIED다.

### ④ 오라클 중계는 막지 못한다 (수용 — 주석 시정)
공격자가 **자기 키쌍**을 만들어 그 키로 챌린지를 받고, 깨끗한 폰에서 토큰을 받아
제출하면 VERIFIED가 자기 키에 결속된다 — 공격자가 곧 그 키의 소유자이기 때문이다.
코드 주석이 "그 키의 소유자만 쓸 수 있다"고 **과장**하고 있어 삭제했다. 원리적 차단은
하드웨어 키 증명 병행뿐이며 미구현이다. 챌린지 결속이 막는 것은 "남의 토큰을 주워
쓰는" 수동적 재사용까지다.

### 추가 환경변수
```
SHVIL_ANDROID_CERT_DIGESTS   EAS 키스토어 SHA-256 지문 (base64url, 쉼표로 복수)
```
EAS 대시보드 또는 `npx eas credentials`에서 확인한다. **이 값이 없으면 VERIFIED가
나오지 않는다** — 앱 동일성 검사가 없는 상태를 통과로 삼지 않기 때문이다.

## 6. 남는 한계 (정직화 — 제3조)

- **iOS는 아직 안 된다.** App Attest에 Apple 개발자 계정($99/년)이 필요하다. 그동안
  아이폰은 UNVERIFIED로 남는다. 등급 정책에서 이들을 배제하지 않는 것이 제7조에 맞다.
- **GMS 없는 기기**(화웨이·중국 롬·커스텀 롬)는 영원히 VERIFIED를 못 받는다.
- **시빌은 여전히 못 막는다.** 무결성은 "기기가 진짜"를 증언할 뿐 "1인 1계정"을 강제하지
  않는다. 폰 N대면 계정 N개다 — 다만 **비싸진다**. 이것이 무결성이 주는 시빌 저항의 전부다.
- **네이티브 모듈 미설치**: `react-native-google-play-integrity`가 아직 package.json에
  없다. 지연 로드로 감싸 두어 지금도 앱은 정상 동작하지만(폴백), 실토큰을 받으려면
  설치 후 EAS 재빌드가 필요하다.
