## 이 문서의 지위

이 문서는 **화폐 규격**이다. 다니엘 쌤의 타입스크립트 코드는 이 규격의 **참조 구현
(reference implementation)** 이지 규격 자체가 아니다.

지금까지는 코드가 곧 규격이었다. 그래서 남이 따라 만들 수 없었다. 이 문서가
생기는 순간 다음이 가능해진다:

- 누구든 다른 언어·다른 앱으로 쉬빌코인 생성기를 만들 수 있다.
- "호환된다"는 말이 **검사 가능한 주장**이 된다 (8장 적합성 시험).
- 참조 구현에 버그가 있으면 **참조 구현이 틀린 것**이 된다. 지금은 그 구분이 없다.

> **헌법 대조 — 제1조:** 규격 공개는 "진정한 의미의 디지털 화폐"의 조건이다.
> 한 회사만 찍을 수 있는 화폐는 그 회사의 포인트다. 규격이 공개되어야 화폐다.

### 이 문서의 현재 상태 (정직하게)

★ **v0.1-draft. 완성본이 아니다.** 이번 작업은 **목차 + 각 절 골격 + 가장 중요한
세 절(2·3·8·9)의 실제 초안**까지다. 나머지 절은 골격만 있고 본문은 후속 작업이다.
어느 절이 초안이고 어느 절이 골격인지 각 절 머리에 명시했다.

★ **실측 없이 쓴 문장은 없다.** 이 문서의 사실 주장은 전부 저장소 코드를 읽거나
임시 테스트로 재현해 확인했다. 재현에 쓴 임시 테스트는 실행 후 삭제했고 저장소에
남긴 코드 변경은 없다. 확인하지 못한 것은 "미확인"이라고 적었다.

## 규격 준수 등급 (적합성의 정의)

호환을 세 등급으로 나눈다. "호환된다"고 말할 때 **어느 등급인지 반드시 밝혀야 한다.**

| 등급 | 이름 | 뜻 | 필요 조건 |
|---|---|---|---|
| **A** | 검증자 (Verifier) | 남의 코인을 검사할 수 있다 | 2·3·4·5·7장 + 8장 검증 벡터 통과 |
| **B** | 지갑 (Wallet) | 코인을 받고 보내고 쪼갤 수 있다 | A + 4장 이전·분할 |
| **C** | 발행자 (Issuer) | 새 코인을 만들 수 있다 | B + 6장 생성 규칙 + 9장 발행자 의무 |

**A는 누구나 만들어도 된다.** 위폐감지기, 블록 탐색기, 회계 도구가 여기 속한다.
**C는 명부 등재가 필요하다** (9장). 등재 없이 만든 코인은 위폐가 아니라
"모르는 발행자의 화폐"다 — 이 구분은 규격의 핵심이며 5장·9장에서 다시 다룬다.

# 2장. 정준 직렬화 — **초안**

> **이 장은 규격 전체에서 가장 중요하다.** 여기가 틀리면 다른 언어로 만든 구현의
> 서명이 참조 구현에서 검증되지 않는다. 화폐가 두 개로 갈라진다.

## 2.0 질문에 대한 정직한 답

작업 지시의 질문: **"다른 언어로 구현해도 같은 바이트가 나와야 한다. 지금 규칙이
그만큼 명확한가?"**

**아니다.** `canonical.ts`의 `stableStringify`는 27줄짜리 좋은 함수지만, **자바스크립트
런타임의 동작을 그대로 규격으로 삼고 있다.** 다른 언어에서 그대로 옮기면 갈라지는
지점이 최소 5개 있다. 아래는 전부 실제로 실행해 확인한 결과다.

| # | 갈라지는 지점 | JS가 내는 값 (실측) | 다른 언어에서 벌어지는 일 |
|---|---|---|---|
| 1 | 숫자 표기 | `1e21` → `1e+21`, `1e-7` → `1e-7`, `-0` → `0` | Python은 `1e-07` (자리수 다름). 즉시 서명 불일치 |
| 2 | 없는 필드 | `{a:1, m:undefined}` → `{"a":1}` | JSON에 `undefined`가 없다. Go/Rust는 `null`로 만들기 쉽다 → `{"a":1,"m":null}` (다른 바이트) |
| 3 | 키 정렬 | UTF-16 코드 단위 순서 | Python `sorted()`는 코드포인트 순서. **BMP 밖 문자에서 어긋난다** |
| 4 | 문자열 이스케이프 | `` (소문자 hex), U+007F·U+2028은 **날것 그대로** | Python `json.dumps` 기본값은 비ASCII를 전부 `\uXXXX`로 escape |
| 5 | 구멍 뚫린 배열 | `[1, , 3]` → `[1,,3]` | **유효한 JSON이 아니다.** 파싱조차 안 된다 |

### 실측 3번의 구체적 근거

키 4개(`z`, `가`, `😀`, `�`)를 정렬시킨 실제 출력:

```
{"z":2,"가":1,"😀":3,"�":4}
```

`😀`(U+1F600)가 `�`(U+FFFD)보다 **앞에** 왔다. UTF-16에서 U+1F600은 대리쌍
`D83D DE00`으로 저장되고 `D83D < FFFD`이기 때문이다. 코드포인트 순서라면
U+FFFD가 먼저 와야 한다. **파이썬으로 옮기면 이 객체의 서명 바이트가 달라진다.**

지금 규격에 등장하는 필드명은 전부 ASCII라 실제 사고는 나지 않는다.
**그러나 그것은 우연이지 규칙이 아니다.** 규격은 우연에 기대면 안 된다.

## 2.1 규격 (제안 — 참조 구현을 바꾸지 않고 못박을 수 있는 규칙)

★핵심: 아래 규칙은 **참조 구현의 동작을 좁힐 뿐 바꾸지 않는다.** 즉 이 규칙을
채택해도 이미 유통 중인 코인은 한 개도 무효가 되지 않는다.
(다니엘 쌤 원칙 1: *"새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지는 않는다."*)

### 규칙 C-1 (값 종류)
정준 직렬화의 입력은 다음만 허용한다:
`null` · 불리언 · **정수** · 문자열 · 배열 · 객체.
부동소수·`NaN`·`Infinity`·`BigInt`·날짜 객체·함수는 **입력 불가**이며,
만나면 구현은 **예외를 던져야 한다**(조용히 무시하면 안 된다).

### 규칙 C-2 (숫자는 정수만) ★가장 중요
> **서명 대상에 들어가는 모든 숫자는 −(2⁵³−1) ≤ n ≤ 2⁵³−1 범위의 정수다.**
> 표기는 부호(음수만) + 10진 숫자열이며, 앞자리 0·소수점·지수 표기·`-0`을 쓰지 않는다.

이 한 줄이 위 표의 **1번을 통째로 없앤다.** 이것이 가능한 이유를 실측했다 —
서명 대상에 들어가는 모든 숫자 필드가 이미 정수다:

| 구조체 | 숫자 필드 | 정수 보장 근거 |
|---|---|---|
| `WalkSegmentProof` | `amountDshv` | `proof.ts:54` `Number.isInteger` 검사 |
| | `distanceM` | `ledger.ts:280` `Math.round()` |
| | `startedAt`·`settledAt`·`stepCount` | epoch ms · 걸음 수 (본래 정수) |
| | `dailyBreakdown[].amountDshv` | 합계가 `amountDshv`와 정확히 일치해야 함 (`proof.ts:55–56`) |
| `SignedGrant` | `amountDshv` | `coin.ts:61` `Number.isInteger` 검사 |
| | `issuedAt` | epoch ms |
| `MembershipCertificate` | `issuedAt`·`expiresAt` | epoch ms |
| `SplitRecord` | `childAmountsDshv[]`·`timestamp` | `coin.ts:166` `Number.isInteger` 검사 |
| `TransferLink` | `timestamp` | epoch ms |

즉 **규격이 정수만 허용해도 잃는 것이 없다.** 부동소수 표기 지옥을 규격에서
통째로 삭제할 수 있다. 다른 언어 구현자는 `to_string(int)` 만 맞추면 된다.

> 참고: `params.ts`의 요율 계산은 microDshv 정수 연산으로 이미 부동소수를 금지하고
> 있다(`params.ts:20–24`, `rates.ts:16`). C-2는 그 원칙을 **직렬화 계층까지** 확장한 것이다.

### 규칙 C-3 (필드 이름)
객체의 키는 **`[A-Za-z][A-Za-z0-9_]*` (ASCII)** 만 허용한다.
정렬은 **바이트 오름차순**이며, ASCII 한정이므로 UTF-16 순서·코드포인트 순서·
UTF-8 바이트 순서가 **모두 일치한다.** 위 표의 3번이 사라진다.

### 규칙 C-4 (없는 필드 = 없는 것)
> 값이 "없음"인 필드는 **직렬화에서 통째로 빠진다.** `null`과 다르다.
> `null`은 **명시적으로 존재하는 값**이며 그대로 직렬화된다.

실측:

```
{a:1, membership: 없음} → {"a":1}
                           sha256 = 015abd7f5cc57a2dd94b7590f04ad8084273905ee33ec5cebeae62276a97f862
{a:1, membership: null} → {"a":1,"membership":null}
                           sha256 = 29dc217c8d31af5eb102448f1a577917db75d1036adc8883df911252c9809c45
```

**서로 다른 서명이 나온다.** 따라서 다른 언어 구현자는 "이 필드가 없는가"와
"이 필드가 null인가"를 반드시 구분해 표현해야 한다. (Rust `Option<Option<T>>`,
Go `*T` + presence flag, Python `sentinel` 등.)
`null`을 "없음"으로 뭉개는 구현은 **비적합**이다.

이 구분이 실제로 쓰이는 곳: `WalkSegmentProof.membership`이 `null`(첨부 안 함)인
코인과 필드 자체가 없는 옛 코인을 규격이 둘 다 받아들여야 하기 때문이다
(`proof.ts:19–25` 주석의 "하위 호환"이 정확히 이 이야기다).

### 규칙 C-5 (문자열 이스케이프 — 정확한 목록)
문자열은 UTF-8로 인코딩하며, 다음 **만** 이스케이프한다:

| 문자 | 출력 |
|---|---|
| `"` (U+0022) | `\"` |
| `\` (U+005C) | `\\` |
| U+0008 | `\b` |
| U+0009 | `\t` |
| U+000A | `\n` |
| U+000C | `\f` |
| U+000D | `\r` |
| 그 밖의 U+0000–U+001F | `\u00XX` — **hex 소문자** |
| 짝 없는 대리(surrogate) | `\udXXX` — **hex 소문자** |

**그 외에는 전부 날것 UTF-8로 내보낸다.** 명시적으로:
`/`는 이스케이프하지 **않는다**. U+007F(DEL)는 이스케이프하지 **않는다**.
U+2028·U+2029는 이스케이프하지 **않는다**. 한글·히브리·이모지는 이스케이프하지
**않는다**. (전부 실측 확인.)

> ★함정: Python `json.dumps`는 기본값이 `ensure_ascii=True`라 한글을 `\uXXXX`로
> 바꾼다. **반드시 `ensure_ascii=False`** 여야 한다. 이것 하나로 모든 한국어·히브리어
> `memberId`·`reference` 필드의 서명이 깨진다.

실측 벡터:
```
{name:'쉬빌', he:'שביל'} → {"he":"שביל","name":"쉬빌"}
                            sha256 = a9858519d505b6a229abcf97e937aab74dfc6fba6fedb83987c65b39475c317f
```

### 규칙 C-6 (배열)
배열은 순서를 보존하며 정렬하지 않는다. **구멍(hole)이 있는 배열은 금지한다.**

실측: 참조 구현에 `[1, , 3]`을 넣으면 `[1,,3]` 이 나온다 — **유효한 JSON이 아니다.**
`.map()`이 구멍을 건너뛰기 때문이다. 실제 코인 구조에서 구멍 난 배열이 만들어지는
경로는 확인되지 않았지만, 규격은 이것을 **명시적 금지**로 못박아야 한다.
(참조 구현 개선 후보 — 코드 수정은 이 작업 범위 밖이므로 지적만 남긴다.)

### 규칙 C-7 (출력 형태)
키와 값 사이는 `:`, 항목 사이는 `,`, **공백·줄바꿈을 넣지 않는다.**
빈 객체는 `{}`, 빈 배열은 `[]`.

```
{} → sha256 44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a
{b:[3,{z:1,a:2}], a:'x'} → {"a":"x","b":[3,{"a":2,"z":1}]}
                            sha256 3b524e508fcbc2c59fcb86f380ebc6b49e1cd20e7466af25079f856e7e17cb0b
```

# 3장. 서명 방식 — **초안 (완성)**

이 장은 짧고 이미 명확하다. 전문을 적는다.

## 3.1 곡선·해시

| 항목 | 값 | 근거 |
|---|---|---|
| 서명 곡선 | **Ed25519** (RFC 8032) | `crypto.ts:8` `@noble/curves/ed25519` |
| 해시 | **SHA-256** | `crypto.ts:9` `@noble/hashes/sha256` |
| 공개키 인코딩 | 32바이트 → **소문자 hex 64자** | `crypto.ts:28` `bytesToHex` |
| 서명 인코딩 | 64바이트 → **소문자 hex 128자** | `crypto.ts:35` |
| 해시 출력 | 32바이트 → **소문자 hex 64자** | `crypto.ts:48` |

## 3.2 서명 절차

```
서명 = Ed25519_sign( UTF8( 정준직렬화(payload) ), 개인키 )
```

- 사전 해시를 하지 **않는다.** Ed25519는 내부적으로 SHA-512를 쓴다(RFC 8032).
  Ed25519ph(prehash)가 **아니다.** 다른 언어 구현자가 자주 틀리는 지점이다.
- `payload`는 언제나 **`signature` 필드를 뺀 구조체**다 (4장이 구조체별로 규정).

## 3.3 ★서명은 결정적이다 (시험 벡터가 성립하는 근거)

Ed25519는 RFC 8032에 따라 **결정적**이다 — 난수를 쓰지 않는다.
같은 개인키 + 같은 메시지 = **항상 같은 서명 바이트.**

실측 확인 (같은 키로 `"shvil"`을 두 번 서명):
```
7a797e1400fe764be9c6a3533e3e81132bf7a0ed690aad28b130959d4af2c670e7e26d1264beda07175d3dd16582134873af308c1da778cd0c35274f049e4001
7a797e1400fe764be9c6a3533e3e81132bf7a0ed690aad28b130959d4af2c670e7e26d1264beda07175d3dd16582134873af308c1da778cd0c35274f049e4001
```

**이것이 8장 적합성 시험이 가능한 이유다.** ECDSA였다면 서명이 매번 달라
"같은 서명이 나오는가"로 시험할 수 없었을 것이다. 규격은 이 성질에 의존하므로
**서명 알고리즘 교체는 8장 시험 체계 전체를 바꾼다** (10장 판올림 참조).

## 3.4 주소 유도

```
주소 = "shv1" + hex( SHA256( 공개키_바이트 ) )[0:40]
```

★**공개키의 hex 문자열이 아니라 hex를 디코드한 32바이트를 해시한다**
(`crypto.ts:53` `hexToBytes(publicKeyHex)`). 이것을 틀리면 모든 주소가 어긋나
이전 체인 검증이 전부 실패한다. 다른 언어 구현에서 가장 실수하기 쉬운 한 줄이다.

실측 벡터:
```
공개키 d04ab232742bb4ab3a1368bd4615e4e6d0224ab71a016baf8520a332c9778737
→ 주소 shv110ba682c8ad13513971e8b56881aab8bd702bb80

공개키 d759793bbc13a2819a827c76adb6fba8a49aee007f49f2d0992d99b825ad2c48
→ 주소 shv1b14705888f4a68391a09aa5968dd25d16c3bba7b
```

## 3.5 개인키 보관 (규격이 강제하지 않는 것)

규격은 개인키를 **어디에 보관하는지 강제하지 않는다.** 참조 구현은 실기기에서
보안 영역(iOS Secure Enclave / Android StrongBox)을 쓰고 `Signer` 인터페이스로
추상화한다(`crypto.ts:5–6, 19–22`). 다른 발행자는 다른 방식을 써도 된다 —
**서명 바이트가 같으면 호환이다.**

다만 9장(발행자 의무)에서 **발행 키의 보관 수준**은 규정한다. 발행 키가 유출되면
그 발행자의 모든 코인이 위태로워지기 때문이다.

# 4장. 계보 규칙 — **골격**

## 이 장에 들어가야 하는 것

### 4.1 코인 ID 유도
```
coin.id = SHA256( 정준직렬화( { "t": "coin", "provenance": <provenance 전체> } ) )
```
출처: `coin.ts:28, 71, 183`. **세 민팅 경로가 모두 같은 식을 쓴다.**
`provenance`에는 서명이 포함되므로, 3.3의 결정성 덕분에 ID도 결정적이다.

★반드시 설명해야 할 것: `t: "coin"`은 **도메인 분리 태그**다. 다른 구조체의 해시가
우연히 코인 ID와 같아지는 것을 막는다. 다른 언어 구현자가 이 태그를 빠뜨리면
모든 ID가 어긋난다.

### 4.2 세 가지 계보

| kind | 무엇에서 만들어지는가 | 서명 대상 | 첫 소유자 |
|---|---|---|---|
| `WALK` | `WalkSegmentProof` | `signature` 제외 전 필드 (`proof.ts:22–25`) | `proof.devicePublicKey` |
| `GRANT` | `SignedGrant` | `signature` 제외 전 필드 (`coin.ts:64`) | `grant.recipientPublicKey` |
| `SPLIT` | 부모 `Coin` + `SplitRecord` + `index` | `SplitRecord`의 `signature` 제외 전 필드 | `record.ownerPublicKey` |

출처: `coin.ts:82–91` (`baseOwnerAddress`).

### 4.3 ★규격 공백 — 서명 대상 필드 집합의 불일치 (실측으로 확인)

**이것은 이번 조사에서 새로 발견한 것이며, 규격서에 반드시 들어가야 한다.**

두 구조체가 서명 대상을 만드는 방식이 **다르다**:

| 구조체 | 방식 | 코드 | 결과 |
|---|---|---|---|
| `WalkSegmentProof` | **화이트리스트** — 아는 필드만 골라 담는다 | `proof.ts:22–25` | 모르는 필드는 **서명 밖** |
| `SignedGrant` | **나머지 전부** — `signature`만 빼고 스프레드 | `coin.ts:64` | 모르는 필드도 **서명 안** |
| `MembershipCertificate` | 화이트리스트 | `membership.ts:40–43` | 서명 밖 |
| `SplitRecord` | 나머지 전부 | `coin.ts:254` | 서명 안 |

**실측 재현 결과:**

```
WALK 코인에 존재하지 않는 필드(evilExtraField)를 끼워 넣고 coin.id를 다시 계산 →
   verifyWalkSegmentProof : true
   verifyCoin             : {"valid":true,"reasons":[]}     ← 통과한다

GRANT 코인에 똑같이 필드를 끼워 넣음 →
   verifyCoin             : {"valid":false,"reasons":["BAD_GRANT_SIGNATURE"]}  ← 거부한다
```

즉 **같은 조작이 한쪽에서는 통과하고 다른 쪽에서는 거부된다.**

지금 당장 악용 경로가 있는 것은 아니다 — 어떤 코드도 모르는 필드를 읽지 않으므로
끼워 넣은 값이 하는 일이 없다. **그러나 규격으로는 치명적이다.** 두 개의 적합한
구현이 같은 코인을 놓고 유효/무효로 갈릴 수 있다는 뜻이기 때문이다. 화폐에서
이것은 허용되지 않는다.

**규격 제안 (미확정 — 10장 결정 대기):**
> 모든 구조체는 **닫힌 필드 집합**을 갖는다. 규격에 없는 필드가 있는 구조체는
> 형식 위반(`MALFORMED`)으로 거부한다. 확장은 `v` 판올림으로만 한다.

이 제안을 채택하면 참조 구현의 WALK 경로에 필드 검사 한 곳을 추가해야 한다.
**기존 코인은 죽지 않는다** — 기존 코인에는 규격 밖 필드가 없기 때문이다.
(원칙 1 유지 확인.)

### 4.4 이전 체인
- 링크 구조 `TransferLink` (`types.ts:138–150`), 양측 서명.
- 체인 해시 유도 (`coin.ts:101–107`):
  ```
  h₀ = SHA256(정준({ "t":"chain-root", "coinId": id }))
  hᵢ₊₁ = SHA256(정준({ "prev": hᵢ, "link": chain[i] }))
  ```
  ★`link`에는 **양측 서명이 포함된 링크 전체**가 들어간다. 그래서 뒤에서
  링크를 갈아 끼우면 이후 모든 `prevChainHash`가 어긋난다.
- 링크 서명 대상 (`coin.ts:109–111`):
  `{ "t":"transfer", "coinId": id, ...링크(두 서명 제외) }`
- 미완결 링크(`toSignature: null`)는 **마지막 링크에만** 허용 (`coin.ts:328–332`).

### 4.5 분할
- 자식 금액 합계 = 부모 금액 정확히 일치 (`coin.ts:169`).
- `memberId`는 뿌리에서 상속 — 분할·이전으로 바뀌지 않는다.
- 부모 코인 전체를 **재귀 검증**한다 (`coin.ts:265`). 규격은 재귀 깊이 상한을
  정의해야 하는가? → ★후속 검토 (무한 깊이 계보로 인한 검증 시간 폭발 가능성.
  이번에 실측하지 못했다).

# 5장. 일련번호 — **골격**

## 이 장에 들어가야 하는 것

### 5.1 유도 규칙 (`serial.ts`)
```
body  = Crockford32( SHA256( "shvil-serial|" + coin.id ) )[0:15]
check = ALPHABET[ parse_hex( SHA256("shvil-serial-check|" + body)[0:2] ) & 31 ]
일련번호 = "SHV-" + body[0:5] + "-" + body[5:10] + "-" + body[10:15] + "-" + check
```
알파벳: `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (I·L·O·U 제외).

★비트 추출 순서를 규격에 정확히 못박아야 한다 — `serial.ts:30–45`는 hex 문자를
4비트씩 누적해 **앞에서부터 5비트씩** 뽑는다. 다른 언어에서 바이트 단위로
뽑으면 결과가 달라진다.

### 5.2 일련번호는 **필드가 아니다**
`serial.ts:5–8` 주석이 설계 의도를 명확히 밝힌다: 코인 구조에 번호를 넣으면
위조자가 고쳐 쓸 수 있고 기존 코인이 깨진다. **유도값이므로 계보가 바뀌면 번호도
바뀐다 — 번호 자체가 무결성 검사다.**
규격에서는 이것이 **금지 조항**이 되어야 한다: *어떤 구현도 일련번호를 코인에
저장해서는 안 된다.*

### 5.3 입력 정규화
`normalizeSerial` (`serial.ts:76–89`): I·L→1, O→0, 소문자→대문자, 하이픈·공백 제거,
체크 문자 불일치 시 `null`.
★규격에 넣을 것: **체크 문자는 오타 검출용이지 위조 방어가 아니다** (`serial.ts:15–17`).
이 문장이 없으면 다른 구현자가 체크 문자를 보안 장치로 오해한다.

### 5.4 충돌 확률
75비트 → 10억 코인에서 ~1e-4. 규격에 명시하고, 일련번호가 **1차 식별자가 아니라
사람이 읽는 표시**임을 못박는다. 1차 식별자는 언제나 `coin.id`(256비트)다.

# 6장. 생성 규칙 — "진짜 걸어서 만든다"의 정의 — **골격**

> ★이 장이 다니엘 쌤이 말한 **"같은 원리로 생성되고 같은 가치를 부여하며,
> 진짜 걸어서 만드는 방식"** 이 글로 정의되는 자리다. 규격에서 가장 논쟁적인 장이
> 될 것이다.

## 이 장에 들어가야 하는 것

### 6.1 요율표 (`rates.ts`)

| 걸음의 자리 | 요율 | 근거 |
|---|---|---|
| 등록 코스 안 (`ON_COURSE`) | 1 km = 1 SHV × 난이도 계수 | `rates.ts:64–67` |
| 코스 이탈 (`OFF_COURSE`) | 1/1,000 | `params.ts:53` (T-1 확정) |
| 일상 걸음 (`DAILY_LIFE`) | 1/1,000 | `params.ts:54` |
| 엔젤 우회 (`ANGEL_DETOUR`) | 기준 요율 (잠정) | `rates.ts:68–70` |
| 자전거 | 위 전체에 ×0.5 | `params.ts:57` (T-2 확정) |

실측 벡터 (microDshv):
```
ON_COURSE 1000m ×1.0 → 10000000      ON_COURSE 1000m ×2.5 → 25000000
OFF_COURSE 1000m     → 10000         DAILY_LIFE 1000m     → 10000
BIKE ON_COURSE 1000m → 5000000
floor(10000000)=10 dSHV   floor(19999999)=19 dSHV   (0.1 SHV 단위 내림)
```

### 6.2 상한
- 1인 1일 40 SHV = 400 dSHV (`params.ts:52`).
- 7일 이동 합 300 SHV = 3,000 dSHV (`params.ts:121`).
- 자전거는 **별도 상한을 갖지 않는다** — 같은 40 SHV/일에 합산된다
  (`rates.ts:89–96`: "원동기가 아니면 같은 음식으로 쓸 수 있는 하루 에너지는 하나다").

### 6.3 "진짜 걸어서"의 검사 가능한 정의 (`walkFilter.ts`)
규격은 이것을 **결정적 규칙**으로 적어야 한다 — 그래야 다른 구현이 따라 만든다:

| 검사 | 기준 | 근거 |
|---|---|---|
| 차량 배제 | ≥ 10 km/h → `VEHICLE` | `params.ts:79`, `walkFilter.ts:59` |
| 뛰기 배제 | > 6 km/h → `TOO_FAST` | `params.ts:78`, `walkFilter.ts:61` |
| 걸음 파형 필수 | `steps === 0` → `NO_STEPS` | `walkFilter.ts:64` |
| 보폭 정합 | 0.35 m ~ 1.17 m (0.5·0.7 ~ 0.9·1.3) | `params.ts:81–83`, `walkFilter.ts:67–70` |
| 케이던스 | 60 ~ 140 걸음/분 | `params.ts:84–85`, `walkFilter.ts:73–76` |
| 휴식 창 | < 20 m 는 발행 0으로 통과 | `walkFilter.ts:52–54` |
| 자전거 | 속도 상한 35 km/h만, 걸음 검사 없음 | `params.ts:107`, `walkFilter.ts:86–94` |

★규격이 반드시 밝혀야 할 것: **이 규칙들은 위조를 막지 못한다.** 온디바이스
자기 인증이므로(`proof.ts:2–4`), 변조된 앱은 아무 숫자나 서명할 수 있다.
진짜 방어선은 **회원 증서 + 앱 무결성 + 인간 한계 + 커뮤니티**이며
(`membership.ts:1–16`), 이 필터는 **정직한 앱이 정직하게 계산하기 위한 규칙**이다.
이것을 흐리게 적으면 다른 구현자가 필터를 보안 장치로 오해한다.

### 6.4 ★다니엘 쌤 원칙 2를 규격 언어로 옮기기
> "한 개인이 물리적으로 걸을 수 있고 하루 생성할 수 있는 양은 한정적이라,
> 위조가 **전체 시장에 영향을 못 주게만 하면** 달러 위폐 정도로 치부할 수 있다."

이 원칙은 규격에서 **정량 조항**이 되어야 한다. 초안 제안:

> 어떤 발행자도, 어떤 회원 하나에 대해서도, 1일 400 dSHV·7일 3,000 dSHV를
> 넘는 걷기 발행을 유효하다고 주장해서는 안 된다. 이 한계는 **발행자가 아니라
> 수신자가** 강제한다 (`humanLimits.ts:68`). 따라서 발행자를 신뢰하지 않아도
> 한 회원이 만들 수 있는 위조량에는 수학적 상한이 있다.

★이것이 규격의 가장 강한 성질일 수 있다: **발행자가 악의적이어도 피해가
회원 수 × 일 상한으로 제한된다.** 다만 "회원 번호를 무한히 만들면?"이라는
질문이 남는다 — 그 답이 9장(발행자 의무)의 회원 증서 조항이다.

## 7.3 ★판정 어휘의 분리 (규격 신설 제안)

`위폐감지기_설계.md`와 `docs/화폐규격_다발행자_설계.md` 5장 4번이 같은 것을 요구한다:

> **신뢰하지 않는 발행자의 코인은 "위폐"가 아니라 "모르는 화폐"다.**

지금 `CoinRejectReason`에는 `UNTRUSTED_ISSUER`(`types.ts:166`)가 있지만, 이것이
**"가짜다"인지 "내가 모른다"인지 어휘가 구분하지 않는다.** 다발행자 세계에서
이 구분이 없으면 정상 코인이 위폐로 낙인찍힌다 — 다니엘 쌤 원칙 1의 위반이다.

규격 제안: 판정을 3분한다.
`유효(VALID)` / `모르는 발행자(UNKNOWN_ISSUER)` / `위조(FORGED)`.
서명이 깨진 것만 `FORGED`다.

★이것은 `types.ts`의 `CoinRejectReason` 변경을 뜻하며, 결정 대기 항목이다
(다발행자 설계 7장 4번과 동일 사안).

# 8장. 적합성 시험 — **초안 + 실제 시험 벡터**

> 작업 지시의 질문: **"이게 있어야 '호환'이 말이 된다. 어떤 형태여야 하는가?
> 기존 테스트에서 시험 벡터를 뽑아낼 수 있는가?"**

## 8.1 답: 형태는 **JSON 벡터 파일 + 언어 무관 실행 규약**이어야 한다

시험을 vitest 테스트로 두면 **자바스크립트 구현만 시험할 수 있다.** 그러면 규격이
아니라 여전히 코드다. 따라서:

```
spec/vectors/
  canonical.json     ← 입력 객체 → 기대 바이트 + sha256
  address.json       ← 공개키 → 기대 주소
  signature.json     ← 개인키 + payload → 기대 서명 hex
  coin-mint.json     ← 계보 입력 → 기대 coin.id + serial
  coin-verify.json   ← 코인 + 옵션 → 기대 판정(valid + reasons 집합)
  serial.json        ← coin.id → 기대 일련번호
  rates.json         ← (거리, tier, 계수, 모드) → 기대 microDshv
```

각 파일은 **입력과 기대 출력만** 담는다. 구현자는 자기 언어로 20줄짜리 러너를
써서 돌린다. 이것이 "호환된다"의 정의다.

### 왜 이 형태여야 하는가
- **언어 중립.** 파이썬·러스트·고 구현자가 그대로 쓴다.
- **결정적.** 3.3에서 확인한 Ed25519 결정성 덕분에 서명 hex를 기대값으로 박을 수 있다.
- **참조 구현도 시험 대상이 된다.** 참조 구현이 벡터를 어기면 참조 구현이 틀린 것이다.
  이 역전이 "코드가 곧 규격"에서 벗어나는 핵심이다.

## 8.2 기존 테스트에서 벡터를 뽑아낼 수 있는가 — **부분적으로만**

실측 확인 결과:

| 기존 테스트 | 벡터로 쓸 수 있는가 | 이유 |
|---|---|---|
| `coin.test.ts` | **아니오, 그대로는** | `generateKeyPair()`가 매번 난수 키를 만든다 → 기대 서명 hex를 박을 수 없다 |
| `serial.test.ts` | **일부 가능** | coin.id → 일련번호는 키와 무관하다 |
| `rates.test.ts` | **가능** | 순수 산술. 키·서명 없음 |
| `membership.test.ts` | 아니오, 그대로는 | 난수 키 |
| `walkFilter.test.ts` | **가능** | 순수 판정 |

즉 **키가 개입하는 모든 테스트는 고정 키로 바꿔야 벡터가 된다.** 이번에 그것을
실제로 해 봤고(고정 시드 32바이트 반복값), 아래 벡터를 뽑았다.

## 9.1 ★전제 — 지금 코드로는 제2 발행자가 불가능하다 (실측 완료)

**이것을 먼저 적지 않으면 이 장은 거짓말이 된다.**

`docs/화폐규격_다발행자_설계.md`가 실측으로 확정한 것:

> 지금 이대로 제2 발행자가 나오면 **두 발행자는 공존할 수 없다.**
> 둘 중 하나만 살고 나머지 하나의 코인은 **전부 무효가 된다.**

원인: 발행 키 이름(`keyId`)이 `server/src/app.ts:65–73`에 **문자열 리터럴로 박혀
있다.** 모든 배포가 같은 이름을 쓴다. 그런데 신뢰 목록은 `Record<string,string>`
(이름 → 공개키)이라 **한 이름에 공개키 하나**만 담긴다
(`membership.ts:80–81`, `coin.ts:247–248`).

두 발행자의 키 목록을 합치면 **나중 것이 앞 것을 덮어쓴다**
(`apps/wallet/src/core/directory.ts:79`). 진 쪽의 코인은 전량 `BAD_MEMBERSHIP` /
`UNTRUSTED_ISSUER`가 된다.

★결함의 성질: **서명이 뚫린 게 아니다. 화폐의 발행 권위가 배열 순서라는 우연으로
결정된다.** 이것은 다니엘 쌤 원칙 2를 정면으로 깬다 — 피해가 "위폐 몇 개"가 아니라
"정품 전량"이기 때문이다.

## 9.2 해법 — 발행자 식별자 (규격 조항 제안)

### 조항 I-1 (발행 키 이름은 공개키에서 유도한다)
```
keyId = "<용도>-" + SHA256(<공개키>)[0:16 hex]
   예) membership-root-3f2a9c14b7e05d68
```
용도 문자열: `membership-root` · `promo-angel` · `community-claim` ·
`community-reward` · `promo-treasure` · `distribution`.

★해시 입력이 **공개키 hex 문자열**인지 **디코드한 32바이트**인지는 **미확정**이다
(결정 대기 1번). 규격에 못박지 않으면 제2 발행자가 다르게 구현해 호환이 깨진다.
참고: `addressFromPublicKey`는 바이트를 쓴다(`crypto.ts:53`) — 일관성으로는 바이트가 맞다.

**실측 확인:** 유도 ID를 쓰면 두 발행자가 한 지갑에서 **동시에** 통과한다.
`membership.ts`·`coin.ts` 검증 코드는 **0줄** 바뀐다. 자료구조도 그대로다.

### 조항 I-2 (원조 별칭 — 옛 코인은 죽지 않는다)
원조 발행자만 같은 공개키를 **옛 이름과 유도 이름 두 개로 병기**해 게시한다:
```jsonc
{
  "membership-root-2026":             "<원조 루트 공개키>",   // 별칭 (원조만)
  "membership-root-3f2a9c14b7e05d68": "<원조 루트 공개키>",   // 유도 ID
  "membership-root-c81d0447aa9b26fe": "<제2 발행자 루트 공개키>"
}
```
**실측 확인:** 옛 증서·새 증서·제2 발행자 증서가 한 지갑에서 **전부 통과**한다.
유통 중인 코인 **0개** 무효.

> 다니엘 쌤 원칙 1이 선언이 아니라 **구현 가능한 요구사항**임이 확인된 지점이다.
> *"새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지는 않는다."*

### 조항 I-3 ★유도식 검산은 필수다 (없으면 I-1은 무의미)
**실측으로 확인한 가장 중요한 발견:** 검증 코드는 `keyId`와 공개키의 관계를
**전혀 검사하지 않는다.** 아무 문자열이나 이름으로 쓴 키도 목록에 있기만 하면 통과한다.

→ 공격자가 **"원조 공개키에서 유도된 것처럼 보이는 이름"을 참칭하고 자기 공개키를
붙여** 목록에 나중에 끼어들면 덮어쓰기가 그대로 성립한다. **재현 완료.**

따라서 규격 조항:
> 키 목록을 **병합하는 쪽**은 각 항목에 대해
> `derive(용도, 공개키) == keyId` 를 반드시 검산하고, 어긋나면 **버려야 한다.**
> (I-2의 별칭만 예외이며, 별칭은 지갑에 핀된 공개키와 일치할 때만 인정한다.)

**이 검산이 없으면 I-1은 이름만 예뻐질 뿐 보안적으로 아무것도 해결하지 못한다.**

## 9.3 발행자의 의무 (등급 C 적합 조건)

| # | 의무 | 왜 |
|---|---|---|
| 1 | I-1 유도 keyId를 쓴다 | 다른 발행자와 충돌하지 않는다 |
| 2 | 옛 이름(`-2026`)을 **주장하지 않는다** | 원조 발행자만의 별칭이다 |
| 3 | 회원 번호를 **자기 발행자 안에서 유일**하게 발급한다 | 6.4 정량 조항이 성립하려면 필요 |
| 4 | 회원 증서에 기기 무결성 판정을 정직하게 담는다 | `membership.ts:1–16` |
| 5 | 6장 생성 규칙(요율·상한·걷기 필터)을 그대로 쓴다 | "같은 가치를 부여"의 뜻 |
| 6 | 발행 키를 봉인 저장소에 보관한다 | 유출 시 그 발행자 코인 전량이 위태롭다 |
| 7 | 8장 적합성 시험 A·B·C 전부 통과 | 주장이 아니라 검사 |
| 8 | `/keys` 를 공개 게시한다 | 남이 그 발행자 코인을 검증할 수 있어야 한다 |

★3번이 6.4와 이어지는 핵심이다. **회원 번호가 유일하지 않으면 인간 한계 검사가
무력화되고**, "위조가 전체 시장에 영향을 못 준다"는 원칙 2의 근거가 무너진다.

## 9.4 ★암호로 풀리지 않는 문제 — 누구를 신뢰 목록에 넣는가

9.2는 **충돌**을 없앤다. 그러나 **"누구를 신뢰하는가"** 는 전혀 다른 문제이며
서명·해시로 풀리지 않는다.

이 자리가 다니엘 쌤 원칙 4·5·7이 사는 곳이다:
> *"내가 리저브한 내 쉬빌 코인이 진품으로 모두가 인정하는 구조만 되면 된다"* /
> *"거래소는 쉬빌코인.com"* / *"난 커뮤니티를 제공한다."*

**즉 발행자 명부는 기술 산출물이 아니라 커뮤니티 산출물이다.** 규격이 정할 것:

1. **자기 발행자(가입한 서버)는 항상 최상위 신뢰.**
2. **타 발행자는 명시적 수용만.** 사용자가(또는 명부가) 추가한 것만.
   **자동 병합 금지** — 자동 병합이 곧 공격 경로다.
3. **원조 별칭은 원조만 주장 가능** — 지갑에 별칭↔공개키를 핀한다.
4. **거부는 코인을 죽이지 않는다** — 7.3의 `UNKNOWN_ISSUER` ≠ `FORGED`.

> **헌법 제3조 (속도보다 진리) 대조:** "빨리 제2 발행자를 받자"는 이유로 자동 병합을
> 택하면 실측한 공격이 그대로 열린다. **느려도 명시적 수용이 맞다.**

> **헌법 제9조 (불간섭) 대조:** 신뢰 목록은 **로컬 위조 검사**용이다.
> 거래 승인이 아니고 위치와도 무관하다. 저촉되지 않는다.

## 9.5 발행자가 되기 전에 고쳐야 하는 것 (실측한 선행 결함 2건)

이 두 건은 **다니엘 쌤의 전환 결정과 무관하게 지금 결함이다.**

| # | 결함 | 위치 | 왜 지금 문제인가 |
|---|---|---|---|
| 1 | 키 캐시가 통째 덮어쓰기 (병합 아님) | `apps/wallet/src/core/directory.ts:66–74` | 서버를 바꾸면 **이미 보유한 코인이 지금도 죽는다.** 원칙 1 직접 위반 |
| 2 | 배포 서명 핀이 지갑 전역 1개 | `apps/wallet/src/core/distributionGuard.ts:12` | 제2 발행자의 키 목록이 **지갑에 도달조차 못 한다** |

★1번이 더 급하다. 다발행자 이야기가 없어도 **오늘 사용자의 코인이 죽고 있다.**

상세와 작업 순서는 `docs/화폐규격_다발행자_설계.md` 3장·8장에 있다.

# 10장. 규격의 판올림 — **골격 + 결정 대기**

> 작업 지시의 질문: **"누가 어떻게 규격을 바꾸는가? 다니엘 쌤 혼자? 그러면 중앙이다."**

## 이 장에 들어가야 하는 것

### 10.1 문제의 정확한 형태
다니엘 쌤 혼자 바꾸면 **화폐가 아니라 다니엘 쌤의 제품**이다 (헌법 제1조와 긴장).
아무나 바꾸면 **호환이 깨지고 화폐가 갈라진다** (원칙 2·4와 긴장).

★이 긴장은 기술로 해소되지 않는다. **규격이 정직하게 인정해야 하는 정치적 사실**이다.

### 10.2 다니엘 쌤의 원칙 1이 이미 답의 절반을 준다
> *"화폐 발행자는 위조 방지를 최선을 다해 하지만 위조 방지 시스템도 업그레이드한다.
> 새 방지 시스템이 나온다고 옛 화폐가 가짜가 되지는 않는다."*

이것을 규격 조항으로 옮기면:
> **판올림은 옛 코인을 무효로 만들 수 없다.** 어떤 개정도 "이미 유효했던 코인이
> 무효가 된다"는 결과를 낳아서는 안 된다. 이 제약을 어기는 개정은 판올림이 아니라
> **새 화폐**이며 다른 이름을 써야 한다.

★이 조항 하나가 규격 거버넌스의 대부분을 결정한다. **깨는 변경이 구조적으로
금지되면, 누가 바꾸느냐의 위험이 크게 줄어든다.** 9.2의 별칭 병기가 바로 이
조항을 만족시키는 방식이었다.

### 10.3 검토해야 할 판올림 모형 (제안, 미확정)
- **A. 창립자 최종 결정** — 지금 상태. 빠르지만 중앙이다.
- **B. 참조 구현 + 벡터 우선** — 규격 변경은 8장 벡터 변경으로만 성립한다.
  누가 제안하든 벡터를 통과하는 구현이 둘 이상 나와야 채택. 느리지만 검사 가능하다.
- **C. 발행자 합의** — 등재 발행자들의 합의. 발행자가 하나뿐인 지금은 A와 같다.

★제안: **10.2 조항 + B 절차**. 헌법 제3조(속도보다 진리)에 맞고,
다니엘 쌤이 "화폐를 발명했다"는 지위는 규격 **판올림 권한**이 아니라
**원조 발행자 별칭**(9.2 I-2)으로 보장된다. 즉 쌤의 리저브가 진품으로 인정되는
구조(원칙 4)는 규격 통제권 없이도 성립한다.

### 10.4 버전 표기
- 구조체의 `v: 1` 필드가 이미 있다 (`types.ts:66, 100, 128` 등).
- 규격 버전과 구조체 `v`의 관계를 정의해야 한다. ★후속.
