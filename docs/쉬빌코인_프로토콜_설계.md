## 0. 설계 철학 및 확정 파라미터

### 0.1 설계 철학

- 쉬빌 코인은 **최소 노동 기반 화폐**다. 가치의 원천은 연산(해시)이 아니라 인간의 도보이며, 가치의 소비처는 투기 시장이 아니라 순례길 위의 실물 서비스(잠자리·식사·샤워)다.
- **PoW(작업증명)는 어떤 단계에서도 절대 채택하지 않는다.** 에너지 소모로 희소성을 만드는 모델은 프로젝트 이념과 정면으로 충돌한다.
- 코인의 구매력은 권장 가격표로 실물 서비스에 고정(peg)된다. 시세 형성·거래소 상장·2차 시장 유통은 설계 목표가 아니며, 오히려 억제 대상이다.
- 검증의 목표는 "완벽한 부정 차단"이 아니라 **"부정의 기대이익 < 부정의 비용"** 상태를 만드는 것이다. 1일 40 SHV(잠자리 4박 상당)라는 낮은 상한 자체가 가장 강력한 경제적 방어선이다.

### 0.2 확정 파라미터 (변경 금지)

| 항목 | 값 |
|---|---|
| 단위 | SHV |
| 발행 비율 | 인증 경로에서 검증된 도보 1 km = 1 SHV |
| 1인 1일 발행 상한 | 40 SHV (인간 보행 한계 근거) |
| 권장 가격표 | 잠자리 10 SHV · 식사 5 SHV · 샤워 3 SHV · 풀 패키지 18 SHV |
| 1단계 | 온체인 없음. 서버 원장(폐쇄형 포인트) |
| 2단계 | 저에너지 PoS 체인(Polygon / NEAR / Celo 등) 토큰 전환 |
| 합의 방식 | PoW 절대 배제 |

## 1. 발행 규칙 상세

### 1.1 거리 측정 기준

- **측정 대상 거리 = 인증 경로(공식 트레일 폴리라인)에 투영(map-matching)된 진행 거리.** GPS 원시 궤적의 누적 이동거리가 아니다.
  - 근거: GPS 지터(정지 상태에서도 좌표가 흔들려 거리가 누적되는 현상)와 지그재그 보행으로 인한 거리 부풀리기를 원천 차단한다.
- 절차:
  1. 클라이언트가 수집한 GPS 포인트열을 서버가 공식 트레일 폴리라인에 스냅(map-matching, 예: Valhalla/OSRM 계열 엔진 또는 자체 구현).
  2. 스냅된 트레일 상의 시작점~끝점 구간의 **트레일 정의 거리**(사전 계산된 구간 테이블 값)를 발행 기준 거리로 사용.
  3. 왕복·역주행 구간은 방향 전환 지점을 기준으로 분할하며, **동일 구간의 같은 날 중복 통과는 1회만 인정**한다(왕복 부풀리기 방지). 다만 트레일 특성상 정당한 왕복 구간(막다른 전망대 등)은 구간 테이블에 예외 플래그로 등록한다.
- 고도 보정: 발행 거리는 수평 투영 거리 기준. 고도 가중치(오르막 보너스 등)는 1단계에서 도입하지 않는다(파라미터 단순성 유지, 쟁점 8.1 참조).

### 1.2 반올림 및 최소 단위

- SHV 내부 정밀도: **0.1 SHV (100 m 단위)**. 원장에는 정수 데시-SHV(dSHV)로 저장한다(부동소수점 금지, `amount_dshv: int`).
- 세션 확정 시 검증 통과 거리를 100 m 단위로 **내림(floor)** 처리한다.
  - 예: 검증 거리 17.38 km → 17.3 SHV 발행.
  - 내림을 선택하는 이유: 시스템이 사용자에게 유리하게 초과 발행하는 방향의 누적 오차를 차단. 잔여 미터는 소멸시키며 이월하지 않는다(이월 시 세션 간 결합 검증 복잡도 증가).
- 지불 최소 단위도 0.1 SHV. 가격표는 정수이므로 실사용 마찰 없음.

### 1.3 부분 구간 처리

- 하나의 걷기 세션 안에서 검증 탈락 구간(속도 초과, 지오펜스 이탈, 센서 불일치 등)이 있어도 **세션 전체를 기각하지 않고 구간 단위로 분리 정산**한다.
  - 세션을 검증 상태가 균질한 **세그먼트**로 분할 → 세그먼트별 통과/탈락 판정 → 통과 세그먼트 거리 합산 후 1.2의 내림 적용.
  - 예: 20 km 세션 중 3 km가 차량 이동으로 판정 → 17 km 인정.
- 탈락 세그먼트는 사유 코드와 함께 사용자에게 고지한다(투명성·이의제기 근거).
- 세그먼트 최소 길이 200 m 미만의 파편은 인접 세그먼트 판정에 흡수한다(노이즈로 인한 과잉 분할 방지).

### 1.4 일일 상한 적용

- 상한 40 SHV는 **사용자 기준 1역일(현지 시간대, 이스라엘 IST 00:00~24:00)** 단위로 적용.
- 자정에 걸친 세션은 자정 시각 기준으로 두 날에 분할 귀속한다.
- 상한 도달 후 초과 도보는 발행 없이 기록만 남긴다(통계·배지용). 이월 불가 — "어제 못 받은 분량을 오늘 받기"를 허용하면 상한의 부정 억제 효과가 붕괴한다.

### 1.5 경로 지오펜싱 — 회랑(corridor) 폭 제안

| 구간 유형 | 회랑 반폭(트레일 중심선 기준 편측) | 근거 |
|---|---|---|
| 개활지·사막 구간 (네게브 등) | **50 m** | GPS 수신 양호, 우회 유인 낮음. 좁게 유지 |
| 산악·와디(협곡) 구간 | **100 m** | 지형에 의한 GPS 멀티패스 오차 증가 |
| 삼림 구간 | 75 m | 수관에 의한 신호 감쇠 |
| 도시 통과 구간 (예루살렘 인근 등) | **150 m** | 도심 협곡(urban canyon) 오차 + 정당한 보도 우회 |
| 공식 우회로·대체로(홍수 시 와디 우회 등) | 별도 폴리라인 등록 | 회랑 확장이 아니라 경로 추가로 대응 |

- 회랑 판정: 포인트 단위가 아닌 **슬라이딩 윈도(예: 60초)** 단위로 이탈률을 계산. 윈도 내 포인트의 30% 이상이 회랑 밖이면 해당 세그먼트를 이탈로 판정. 순간 오차 1~2포인트로 기각하지 않는다.
- 회랑 폭은 구간 테이블의 속성으로 관리하여 코드 배포 없이 조정 가능하게 한다.

## 2. Proof of Walk 검증 파이프라인

### 2.1 파이프라인 개요

```
[클라이언트]                          [서버]
센서 수집 → 온디바이스 사전검증 → 기기 서명·배치화 → 제출
                                        → 무결성 검증(서명·재전송·시퀀스)
                                        → 규칙 기반 필터 (결정적)
                                        → ML 이상 탐지 (확률적)
                                        → 판정: 자동승인 / 보류·수동심사 / 기각
                                        → 발행 확정 (원장 기록)
```

- 클라이언트 수집 항목:
  - GPS 궤적: 좌표, 시각, 고도, 수평정확도(HDOP/accuracy), 위성 수, mock-location 플래그
  - 가속도계/자이로: 원시 파형이 아닌 **온디바이스 요약 특징값**(걸음 케이던스, 보행 파형 주기성 점수, 축별 분산) — 전송량·배터리·프라이버시 고려
  - 걸음 수: OS 걸음 카운터(iOS CoreMotion / Android Step Counter) 누적값
  - 속도 프로파일: 구간별 순간 속도. **정상 보행 대역 시속 2~6 km** 기준
  - 기기 메타데이터: 모델, OS 버전, 무결성 증명 토큰(Play Integrity / App Attest)
- 기기 서명: 앱 최초 실행 시 기기 보안 영역(Android Keystore / iOS Secure Enclave)에 키쌍 생성. 공개키를 서버에 등록. 모든 제출 배치는 이 키로 서명하며, 배치에는 단조 증가 시퀀스 번호와 이전 배치 해시를 포함(해시 체인 → 삭제·재정렬 탐지).

### 2.2 단계별 검증 항목 및 탈락 기준

#### A단계 — 클라이언트 수집·사전검증 (온디바이스)

| 검증 항목 | 통과 기준 | 탈락(미기록) 기준 |
|---|---|---|
| 위치 권한·정밀도 | 정밀 위치 허용 | 대략적 위치만 허용 시 세션 시작 불가 |
| mock location 플래그 | OS 플래그 false | 플래그 true 시 세션 시작 차단 + 서버 통보 |
| 샘플링 무결성 | GPS 5~15초 간격 유지 | 60초 이상 공백 구간은 갭 마커로 표시(오프라인 규약 4장 적용) |
| 배터리 세이버 간섭 | 백그라운드 수집 정상 | 수집 중단 시 사용자 경고 후 세션 일시정지 |

#### B단계 — 제출 무결성 (서버, 결정적 즉시 기각)

| 검증 항목 | 통과 기준 | 기각 기준 |
|---|---|---|
| 기기 서명 | 등록 공개키로 검증 성공 | 서명 불일치 → 배치 기각 |
| 시퀀스·해시 체인 | 단조 증가, 이전 해시 일치 | 결번·중복·체인 단절 → 배치 기각 + 계정 플래그 |
| 재전송(replay) | 배치 ID 최초 제출 | 기제출 배치 ID → 무시(멱등 처리) |
| 기기 무결성 증명 | Play Integrity `MEETS_DEVICE_INTEGRITY` / App Attest 유효 | 실패 → 세션 기각, 반복 시 기기 차단 |
| 타임스탬프 정합 | 기기 시각 vs 서버 수신 시각 편차 허용 범위 내(오프라인 지연 감안한 규약 별도) | 미래 시각 데이터 → 기각 |
| 1기기 1계정 | 기기 키 ↔ 계정 매핑 유일 | 동일 기기 키의 다계정 제출 → 전 계정 보류 |

#### C단계 — 규칙 기반 필터 (서버, 세그먼트 단위)

| 검증 항목 | 통과 기준 | 세그먼트 탈락 기준 |
|---|---|---|
| 속도 대역 | 이동평균 속도 2~6 km/h (휴식 0~2 km/h는 발행 0으로 무해) | **60초 이동평균 > 8 km/h** 지속 → 차량/자전거 의심 탈락. 6~8 km/h는 감점(ML 입력) |
| 순간 점프 | 인접 포인트 간 implied speed ≤ 15 km/h | 순간이동(텔레포트) 포인트 → 해당 포인트 폐기, 빈발 시 세그먼트 탈락 |
| 지오펜스 | 1.5절 회랑 판정 통과 | 윈도 이탈률 ≥ 30% → 이탈 탈락 |
| 걸음-거리 정합 | 걸음수 × 보폭(0.5~0.9 m 대역) ≈ GPS 거리, 오차 ±30% 이내 | 걸음수 대비 거리 과다(차량) 또는 거리 대비 걸음수 과다(제자리 흔들기) → 탈락 |
| 케이던스 | 분당 60~140보 | 보행 파형 없이 거리만 진행 → 탈락 |
| GPS 품질 | accuracy 중앙값 ≤ 30 m | 저품질 구간은 발행 제외(기각 아닌 미인정) |
| 위성/신호 정합 | 위성 수·SNR 프로파일이 실외 보행 패턴 | 전 구간 균일·완벽한 신호(스푸퍼 특성) → ML 가중 플래그 |
| 일일 상한 | 당일 누계 + 신규 ≤ 40 SHV | 초과분 발행 절사(1.4절) |
| 체크포인트 정합 | 통과한 체크포인트 스캔 기록과 궤적 시간 일치 | 체크포인트 구간인데 스캔 전무 + 기타 감점 요인 동반 → 보류 |

#### D단계 — ML 이상 탐지 (서버, 확률적)

| 항목 | 내용 |
|---|---|
| 모델 형태 | 1단계 초기: 그래디언트 부스팅(XGBoost류) 이진 분류 + Isolation Forest 비지도 병행. 라벨 축적 후 시퀀스 모델 검토 |
| 입력 특징 | 속도 분포 모멘트, 케이던스-속도 상관, 정지/보행 전이 패턴, 고도 변화 vs 지형 DEM 정합, 세션 시작 시각·위치의 과거 이력 정합, 계정 행동 이력(신고 수, 과거 기각률), 기기 특성 |
| 출력 | 부정 확률 점수 0~100 |
| 판정 임계 | 점수 < 30: 자동 승인 / 30~70: **발행 보류 + 수동 심사 큐** / > 70: 자동 기각 + 계정 플래그 |
| 운영 원칙 | ML 단독으로 계정 제재 불가. 제재는 규칙 기반 증거 또는 수동 심사 확인 필요. 오탐 이의제기 절차 필수 |

#### E단계 — 발행 확정

- 승인 세그먼트 거리 합산 → 내림 → 일일 상한 적용 → **발행 트랜잭션(MINT)** 을 원장에 기록.
- 발행 확정 지연 목표: 온라인 제출 기준 5분 이내(순례자가 저녁에 엔젤에게 당일분으로 지불 가능해야 함). 보류 건은 24시간 내 심사 SLA.
- 모든 판정(승인·탈락·사유 코드)은 감사 로그로 불변 보존.

## 3. 부정행위 유형별 방어

Sweatcoin·STEPN의 교훈: (1) 걸음수 단독 검증은 흔들기 기계·에뮬레이터 팜에 무력했다. (2) 토큰에 외부 시세가 붙는 순간 부정의 기대이익이 폭증해 검증 비용이 감당 불능이 됐다(STEPN의 GPS+모션 결합 검증도 시세 급등기에는 산업화된 치팅 팜을 막지 못했다). (3) Sweatcoin은 낮은 환금 가치와 교환 상한으로 부정 유인을 구조적으로 눌렀고, 이것이 기술 검증보다 효과적이었다. → 쉬빌 코인의 핵심 방어는 **낮은 상한 + 폐쇄형 사용처 + 다중 신호 교차검증**의 3중 구조다.

| 부정 유형 | 공격 방식 | 방어 계층 |
|---|---|---|

## 4. 오프라인 프로토콜

이스라엘 국립 트레일의 네게브 사막 등지는 수일간 무통신이 정상 상태다. 오프라인은 예외 처리가 아니라 **1급 시나리오**로 설계한다.

### 4.1 오프라인 걷기 기록

- 클라이언트는 통신 여부와 무관하게 항상 동일하게 수집·서명한다. 차이는 제출 시점뿐이다.
- 로컬 저장 규약:
  - 배치(예: 10분 단위)마다 즉시 기기 키로 서명 후 암호화 저장(플랫폼 keystore 파생 키).
  - 배치 간 해시 체인 유지 → 오프라인 기간 중 데이터 선별 삭제·조작이 재접속 시 드러남.
  - 각 배치에 **기기 단조 시계(monotonic clock) 값 + 벽시계 값**을 함께 기록. 재접속 시 서버가 두 시계의 정합으로 오프라인 기간 중 시계 조작을 탐지.
  - 로컬 보존 한도: 최소 14일분. 저장 공간 임계 도달 시 사용자 경고(제출 전 삭제 금지).
- 재접속 시 제출:
  - 전체 미제출 체인을 순서대로 업로드. 서버는 체인 무결성 검증 후 통상 파이프라인(2장)으로 처리.
  - 오프라인 기간의 일일 상한은 **각 역일별로 소급 적용**(1.4절과 동일). 3일치 일괄 제출이어도 하루 40 SHV씩만 발행.
  - 장기 오프라인 데이터는 ML 심사에서 체크포인트 스캔 기록(7장)을 가중 참조한다 — 무통신 구간일수록 물리적 앵커의 비중이 커진다.

### 4.2 오프라인 대면 지불 (순례자 → 엔젤)

- 문제: 순례자와 엔젤 모두 오프라인일 수 있다. 서버 확인 없는 지불은 이중지불 위험이 있다.
- 설계: **소액 한도 + 예약 잔고 + 서명 수표(cheque) 모델**

  1. **오프라인 지불 한도**: 계정당 미정산 오프라인 지불 누계 **상한 25 SHV** (풀 패키지 18 SHV + 여유). 한도는 마지막 온라인 동기화 시점에 서버가 부여하는 **오프라인 지불 허가증(spending voucher)** 에 명시 — 서버 서명 포함, 유효기간 7일, 당시 잔고 이하로 발급.
  2. 지불 절차:
     - 순례자 앱이 지불 전표 생성: `{지불자ID, 수취인(엔젤)ID, 금액, nonce, 허가증 참조, 타임스탬프}` 를 기기 키로 서명.
     - 엔젤 앱과 **QR 상호 스캔**(또는 NFC 탭)으로 전표 교환. 엔젤 앱은 허가증의 서버 서명·유효기간·한도 잔여를 로컬 검증 후 수락.
     - 양측 모두 전표를 로컬 저장, 각자 재접속 시 서버에 제출.
  3. **이중지불 처리 (개념)**:
     - 서버는 허가증 단위로 지불 전표를 정산. 동일 허가증의 전표 합계가 한도 초과 시, 타임스탬프 순으로 한도 내 전표만 유효 처리.
     - 초과분은 지불자 잔고에서 우선 충당하고, 잔고 부족 시 **음수 잔고 허용 + 계정 발행 정지**(향후 발행분으로 자동 상환). 엔젤이 손해 보지 않는 구조를 원칙으로 한다(엔젤 신뢰가 생태계의 기반).
     - 고의적 이중지불 반복 계정은 오프라인 지불 권한 회수.
  4. 위험 노출 상한: 한 계정이 시스템에 끼칠 수 있는 최대 손실 = 25 SHV(약 잠자리 2.5박). 산업적 공격 가치가 없는 수준으로 설계.

- 완전 무전력 상황 대비(선택): 종이 백업 — 서버가 발급한 1회용 QR 수표(고정 금액 5/10 SHV)를 사전 인쇄 소지. v1 범위 외, 8장 쟁점.

## 6. 2단계 온체인 전환 설계

### 6.1 체인 선정 기준 (Polygon / NEAR / Celo 비교 관점)

- 필수: PoS 계열 저에너지 합의, 트랜잭션 수수료가 소액 지불(3~18 SHV)에 무의미할 만큼 낮을 것, 모바일 지갑 UX 성숙도.
- 권장: 수수료 대납(meta-transaction / gas abstraction) 지원 — 순례자가 가스용 네이티브 토큰을 보유할 필요가 없어야 한다. 이 기준에서 Celo(모바일 우선, 전화번호 매핑)와 NEAR(계정 추상화)가 강점, Polygon PoS는 생태계·도구 성숙도가 강점. 최종 선정은 쟁점 8.7.

### 6.2 토큰 컨트랙트 기능 목록

표준: ERC-20 호환(또는 대상 체인 등가 표준) + 확장 기능. 업그레이더블 프록시(초기) → 거버넌스 성숙 후 동결.

| 기능 | 명세 |
|---|---|
| **발행 권한 구조** | `MINTER_ROLE`을 **검증 서버 오라클의 멀티시그(예: 2-of-3)** 에만 부여. EOA 단독 발행 불가. 역할 관리는 타임락(예: 48h) 걸린 관리자 멀티시그 |
| **서버 검증 오라클** | 오프체인 검증 파이프라인(2장)이 확정한 발행분을 오라클이 서명하여 `mintWithProof(user, amount, sessionRef, sig)` 호출. `sessionRef`(세션 해시)를 온체인 기록 → 오프체인 감사 로그와 대조 가능. 동일 sessionRef 재사용 거부(멱등) |
| **일일 상한 강제 (온체인)** | 컨트랙트 수준에서 `dailyMinted[user][day] + amount ≤ 400 dSHV` 를 revert 조건으로 강제. **서버가 해킹되어도 체인이 상한을 지키는 이중 방어** |
| **전역 발행 속도 제한** | 하루 전체 발행량 상한(활성 사용자 수 × 40의 상식적 배수)을 두어 오라클 키 유출 시 피해 상한 설정 |
| **소수점** | decimals를 1로 두거나(dSHV 정합) 18로 두되 발행·지불을 0.1 단위로 강제 — 쟁점 8.8 |
| **전송 정책** | 초기: 화이트리스트 전송(등록 사용자·엔젤 지갑 간만) → 투기적 2차 시장 형성 억제. 개방 여부는 거버넌스 결정 사항 |
| **일시정지(pause)** | 오라클 침해 등 비상시 발행·전송 정지. 가디언 멀티시그 |
| **소각(burn)** | 엔젤 수취분의 재순환/소각 정책 구현용 (쟁점 8.6) |
| **비기능** | 스테이킹 이자·수익 분배 기능 **금지** — 증권성·투기화 차단 |

### 6.3 포인트 → 토큰 이관 절차

1. **원장 동결 스냅샷**: 사전 공지된 시점에 1단계 원장 쓰기 동결 → 전 계정 잔고 스냅샷 + 원장 해시 체인 최종 해시 공개(감사 가능성).
2. **외부 감사**: 스냅샷 총액 = 누적 MINT − 누적 소각/수수료 정합 검증. 감사 보고 공개.
3. **지갑 바인딩**: 사용자가 앱 내에서 온체인 주소 생성/연결(계정 추상화 지갑 권장 — 시드문구 UX를 순례자에게 강요하지 않음). 앱이 기존 기기 키로 바인딩 요청 서명 → 1단계 신원과 온체인 주소의 대응을 서버가 기록.
4. **클레임 방식 이관**: 일괄 에어드랍이 아닌 **사용자 주도 claim** (`claimMigration(snapshotProof)`). 스냅샷을 머클 트리로 커밋하고 머클 증명으로 청구 — 서버 오류로 인한 과다 발행 위험 차단. 클레임 기한(예: 12개월) 후 미청구분 처리 정책은 쟁점 8.9.
5. **병행 운영 기간**: 이관 후 일정 기간(예: 3개월) 1단계 지불 API를 온체인 프록시로 유지 — 엔젤 단말 업데이트 지연 흡수.
6. **1단계 원장 퇴역**: 병행 기간 종료 후 서버 원장은 읽기 전용 아카이브로 전환.

## 7. 체크포인트(QR / NFC 비콘) 설계 개념

### 7.1 목적

- GPS·센서만으로 닿지 못하는 **물리적 현존 증명(proof of physical presence)** 앵커 제공. 특히 무통신 구간(4장)에서 궤적 데이터의 신뢰 가중치를 높인다.
- 부수 효과: 순례 스탬프(스탬프 투어) 경험 요소, 트레일 운영 주체와의 협력 접점.

### 7.2 배치

- 설치 지점: 트레일 주요 결절점 — 구간 시·종점, 급수 지점, 대피소, 엔젤 거점, 주요 갈림길. 밀도 제안: **10~20 km당 1개** (하루 도보에 1~3회 통과).
- 스캔은 **발행의 필요조건이 아니다**(비콘 파손·분실이 순례자 불이익이 되면 안 됨). 검증 파이프라인의 **가점 신호**로만 작동. 단, 장기 오프라인 제출 건은 스캔 부재 시 심사 가중치 상향(4.1절).

### 7.3 정적 QR vs 동적 NFC

| 방식 | 개념 | 장점 | 약점 | 용도 |
|---|---|---|---|---|
| 정적 QR (금속판 각인) | 체크포인트 ID + 위치 서명이 담긴 고정 QR | 무전원·무유지보수·초저가·사막 환경 내구 | 사진 공유로 원격 스캔 위조 가능 | 기본 배치 전면 적용 |
| 동적 NFC 비콘 (배터리/태양광) | 탭 시 **시간 기반 롤링 코드**(TOTP 유사)를 서명하여 발급 | 원격 위조 불가 — 그 시각 그 자리 증명 | 전원·유지보수 비용, 도난 | 요충지·부정 다발 구간 선별 배치 |

- 정적 QR의 위조 보정: 스캔 이벤트를 단독 신뢰하지 않고 **스캔 시각·위치가 GPS 궤적과 정합**할 때만 가점(궤적 없이 스캔만 있는 패턴은 오히려 감점). 즉 정적 QR도 궤적과 묶이면 위조 비용이 상승한다.
- 스캔 데이터 규약: `{checkpoint_id, scanned_at(단조+벽시계), device_sig, (NFC의 경우) rolling_code}` — 오프라인 배치 체인에 포함되어 함께 서명·제출.
- 관리: 체크포인트 레지스트리(좌표, 방식, 설치일, 상태), 파손 신고 기능, 코드 로테이션 절차(정적 QR 교체 주기).
