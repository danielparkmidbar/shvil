## 0. 제1원칙 — 기본은 아무것도 요구하지 않는다

> "아주 심플하게. 설치하고 걸으면 형성. 설계된 트레일은 정상 형성,
> 벗어나거나 일상은 조금 생성. 사용자는 설명을 찾아보지 않아도 직관적으로 알게 됨."

**확정 UX 원칙:**
- 앱을 설치하고 걷기 시작하면 **아무 등록·설정·인증 없이** 코인이 생성된다.
  (현 구현 확인: 가입 없이 걷기·정산·QR 지불 전부 동작 — 이미 충족. 이 원칙을 지킨다.)
- 등록된 트레일 위 = 정상 생성. 벗어남/일상 = 조금 생성.
  사용자는 화면의 생성 속도 차이로 이를 **직관적으로** 배운다 — 설명서가 필요 없다.
- 가입(전화 OTP+이메일)이 필요한 순간은 **관계가 시작될 때뿐**: 엔젤 등록, 메신저, 마켓.
- 아래 1~4장의 모든 기능은 **운영자가 특별한 목적으로 얹는 선택 계층**이다.
  기본 걷기 경험에 어떤 복잡성도 추가하지 않는다.

> ⚠ 요율 확인 필요 (결정 대기 T-1): 다니엘 쌤 말씀 중 "벗어나면 1/1000"이
> 현재 확정 파라미터(코스 이탈 1/10, 일상 1/1000)와 다르다.
> 이탈·일상을 하나로 합쳐 1/1000로 단순화하자는 뜻인지 확인 필요.

## 1. 보물 마이닝 (Treasure Mining) — 숨겨진 코인 찾기

### 개념
운영 주체가 트레일의 특별한 존(홍보 목적·프로모션)에 쉬빌 코인을 **숨겨둔다**.
걷는 사람이 그 포인트에 도달하면 실시간 지시가 나타난다:

> "북쪽으로 10걸음 → 동쪽으로 30걸음 → 남쪽으로 3걸음"

지시대로 **몸으로 정확히 움직이면** 보물이 열리고 코인을 받는다.

### 이중 목적 (다니엘 쌤)
1. **완주 동기**: 트레일 완주를 이끄는 게임적 재미 (포켓몬 사냥과 유사 —
   통상 이동 인증인 줄 알았는데 선물처럼 엑스트라 코인이 나올 수도 있다)
2. **보안 수단**: "정말 그 길을 걷지 않으면 만들어낼 수 없는, 현장 실시간
   몸-걸음 인증." GPS 좌표는 조작할 수 있어도, 실시간 랜덤 지시에 맞춰
   걸음 센서+상대 이동이 함께 움직이는 것은 원격으로 위조하기 어렵다.

### 기술 설계 스케치 — 인증은 폰에서 완결, 서버 왕복은 회계 1회 (M9 구현 완료)
> 다니엘 쌤: "암호화되어 랜덤으로 출력되고, 사용자가 맞게 움직이면 인증이 되는
> 방식이지 서버 인증 방식이 아니다. 자신의 스마트폰에서 이뤄진다."

**구현된 아키텍처 (2026-07-15):**

- **이동 검증은 100% 폰 로컬이다.** 서버는 걸음·방향·좌표를 전혀 받지 않는다 —
  받는 필드 자체가 존재하지 않는다 (회귀 테스트로 고정).
- 운영자는 보물 명세(`TreasureSpec`: 존 좌표·반경, 보상액, 총량, 기간, 이동 지시)를
  등록하고, 서버가 배포 서명을 붙여 배포한다 (`GET /treasures` — 기존 /courses
  패턴). 지갑은 이를 캐시한다(오프라인 우선). **지시가 공개되어도 존에 도착해
  몸으로 수행하지 않으면 소용없다.**
- 폰이 존에 들어서면 배너 → 챌린지 시작. 판정 입력은 **존 진입 시점 대비 상대
  변위**(Δ북/Δ동, GPS 델타 적산)와 **걸음 증분**(만보기)뿐이며, 휘발성 버퍼
  (CorridorEngine과 같은 패턴)에서만 살고 다리마다 즉시 폐기된다. 판정은 순수 함수
  `verifyLeg`(packages/shared/src/treasure.ts) — 보폭 0.5~0.9 m 대역 + 방향 ±35° +
  걸음 ±40%(최소 ±3걸음), 짧은 다리(<8걸음)는 GPS 정확도(도심 5~15 m)에 묻히므로
  걸음 수 위주 판정. mock location 감지 시 세션 차단.
- **획득 시 서버 왕복 1회** (`POST /treasures/claim`, 기기 키 서명 인증):
  이 왕복이 필요한 이유는 인증이 아니라 **수량 한정 발행의 회계**다 — 잔여 수량·
  유효기간·1인 1회를 한 곳에서 셈해야 "보물 N개 한정"이 성립한다. 서버가 받는 것은
  memberId + treasureId + **transcriptHash**(각 다리 판정 요약의 sha256 — 이동
  원자료가 아니라 성공 요약의 해시)뿐이다. 통과 시 승인서(SignedGrant,
  kind: `TREASURE`, 보물 발행 키 — 기존 격려 코인 발행 흐름 재사용)를 반환하고,
  **민팅은 폰에서** 이루어진다 (BONUS 계보 — 걸음 코인으로 둔갑 불가).
- 보상 0(무보상 인증 미션)은 같은 메커니즘으로 스탬프 기록만 남긴다 (코인 없음).
- **오프라인이면** 성공 요약을 큐(kv)에 저장했다가 통신 복구 시 자동 청구한다 —
  광야 무통신에서도 몸 인증 자체는 그 자리에서 완결된다.
- 투명성: `/transparency/promo`에 보물 발행 수·총량 집계 공시 (T-3).

**후속 과제 (미구현 — 다니엘 쌤 원안의 완전형):** 서버 왕복 0회의 **완전 오프라인
봉인 그랜트** — 그랜트를 이동 패턴에서 유도되는 키로 암호화해 배포하고 폰이
로컬로 봉인을 여는 방식. 수량 한정 회계(선착순 N명)와 오프라인 완결을 동시에
만족시키는 설계가 필요해 후속 마일스톤으로 넘긴다. 지시의 보물별 랜덤 생성
(현재는 운영자 등록 시 확정)도 이때 함께 다룬다.

### 헌법 정합
- 발행 주체: 운영자 프로모션 발행 (격려 코인과 같은 서명 키 체계, 공시 의무) ✅
- 서버는 승인하지 않는다 — 인증(이동 검증)은 폰 로컬 완결. 서버 왕복은 수량 한정
  발행의 회계 1회뿐이며, 이는 엔젤 보너스·격려 코인과 동일한 "발행 자격 확인"이다 ✅
- 위치 비저장 — 상대 변위만 사용, 휘발. 서버·디스크에 이동 데이터 없음 ✅

## 2. 몸 인증 (Body Verification) — 보상 없는 인증 미션

보물 마이닝과 **같은 메커니즘, 다른 목적**. 코인 보상 없이(또는 모르게)
"이 구간을 실제로 이동했다"는 인증 자체가 목적이다.

- 운영자가 트레일 특정 지점에 **미션**을 설정할 수 있다 (예: 자전거 트레킹 인증 —
  3장 참조, 완주 인증 강화, 클레임 증빙 보조).
- 사용자에게는 가벼운 확인으로 보인다. 가끔은 서프라이즈 코인이 나온다(1장과 연결).
- 다양한 용도로 확장 가능한 **범용 현장 실증 프리미티브**다: "이 시각, 이 존에,
  이 몸이 있었다"를 서버 신뢰 없이 증명한다.

## 3. 자전거 모드 (Bike Trekking)

> "트레일을 자전거로 하는 경우도 많다. 완주 시간과 관계없이 자전거 트레킹도
> 코인을 받을 수 있다. 에너지 사용에 비례하는 코인이니 걷는 사람보다 보상이
> 적지만 큰 차이는 아니다."

- 사용자가 **도보/자전거를 스스로 선택**한다 (선언 기반 — 감시 아님).
- 요율은 에너지 비례로 도보보다 낮게 (수치는 결정 대기 T-2).
- **인증 방식이 다르다**: 자전거는 걸음 센서가 없어 이동 거리만으로 확인 불가
  → 트레일 특정 포인트의 **몸 인증 미션**(2장)으로 실주행을 확인한다.
  (자전거를 세우고 지시대로 몇 걸음 걷는 것 — 자연스럽고 안전한 인증)
- 속도 필터 조정: 현 걷기 필터(차량 배제)와 별도의 자전거 프로파일 필요.
  인간 한계 프로파일도 자전거용 별도 산정 (일 이동거리가 도보의 3~5배).

## 4. QR 스팟 — 사업자 참여 계층

> "트레일 근처 호텔은 방문 유도를 위해 코인을 자기 사업장에 숨길 수 있다.
> 레스토랑·주유소는 트레킹과 관계없이 QR 스캔만으로 코인을 제공해 고객을 유치한다."

### 4-0. 무기명 벽-QR 바우처는 폐기한다 (2026-07-16, 두 차례 적대적 감사 결론)

첫 M10 구현은 사업자 코인을 **임시 베어러 키로 봉인**해 QR에 싣고 첫 스캐너가 여는
"무기명 바우처"였다. 두 차례 독립 적대적 감사가 이를 반려했다:
- **1차 (HIGH)**: 같은 QR을 N명에게 반복 노출하면 코인 1개가 N개로 포크. 이중사용이
  감지돼도 임시 베어러 키라 **범인을 특정 못 해** 아무도 소명 등재 안 됨 — 헌법의
  사후 소명 책임 모델이 끊긴다.
- **2차 (Medium-High)**: 1차를 "발급자 결속"으로 고쳤더니, 이번엔 QR을 본 누구나
  공개 증명을 재생해 **무고한 사업자를 대량 소명 등재(프레이밍)**할 수 있게 됨.

**근본 원인**: 무기명 오프라인 베어러로 코인을 주는 것은 곧 "중앙 원장 없이
이중지불을 막는 것"이다. 쉬빌은 의도적으로 중앙 원장이 없다 → 이 방식은 구조적으로
안전할 수 없고, 한 구멍을 막으면 다른 구멍이 열린다. **접근을 버린다.**

### 4-1. 대신 — 검증된 두 안전 경로로 같은 목적을 이룬다

| 목적 | 안전한 구현 | 상태 |
|---|---|---|
| **사업자가 손님에게 코인 지급 (대면)** | 기존 **대면 지불**을 그대로 사용 — 사업자가 손님 지갑의 수령 QR을 스캔해 이전. 두 기기 서명으로 완결, 이중사용 원천 불가(사업자 잔액에서 빠짐). 계보 RECEIVED. | **이미 됨** — 추가 구현 불필요 |
| **손님이 스캔만 하면 코인 (벽 QR, 무인)** | **스팟 보물** — 보물 마이닝(M9)의 서버 회계(수량·1인1회·기간)를 재사용. 서버가 슬롯을 세므로 이중사용 불가. 코인 출처(사업자 예치·소각 재발행)와 오프라인 여부는 신중 설계 필요. | **M12 정식 마일스톤** |
| **무보상 위치 인증 스탬프** | 순례길 스탬프의 디지털판. 코인이 걸리지 않아 저위험. 위치·시간 결속은 M9 몸 인증 프리미티브 재사용. | **M12에 포함** |

**핵심 원칙(불변)**: 사업자는 발행 주체가 아니다 — 마켓에서 **구매한** 코인만
재배포한다. 경제 순환(걷는 사람 생성 → 엔젤 지불 → 엔젤 판매 → 사업자 구매 →
손님 유치 재배포)은 그대로다. 다만 그 재배포를 **무기명 베어러가 아니라 서버
회계(스팟 보물) 또는 대면 이전**으로 한다.

### 4-2. 왜 서두르지 않는가

코인이 걸린 무인 QR은 이중지불 난제의 정면이다. 두 번 데인 만큼, **스팟 보물은
서버 회계 설계(코인 예치/소각 재발행 흐름)를 제대로 세우고 반드시 적대적 검증을
통과한 뒤** 파일럿에 넣는다. 그때까지 사업자 코인 지급은 **대면 지불**로 충분하다.

### 4-3. M12 적대적 검증 결과 — 통과·시정·남는 위험 (2026-07-17)

M12(스팟 보물) 구현에 적대적 검증이 **조건부 GO**를 줬다. 핵심(총량 보존·이중지불
방지)은 통과했고, 아래 조건을 코드·문서에 반영했다.

**시정 완료 (코드):**
- **V-3 (헌법 중요) — 가짜 걷기 코인 세탁 차단.** 악성 사업자가 자가 서명 WALK
  코인(금액 상한 없음)을 민팅해 예치하면, 인간 한계 검사를 우회해 진짜 TREASURE
  계보로 재배포되는 발행 우회 세탁이 가능했다. 예치(`/spot/deposit`)가 sync의
  초과생성 탐지(`walk_proof_stats`/`checkOverproduction`)를 우회하는 조용한 세탁
  경로였기 때문이다. → 예치 소각 코인의 지문을 **sync와 동일한** 탐지 경로에 연결해
  (공유 모듈 `server/src/anomaly.ts`), 예치도 생산자 인간 한계 검사·소명 등재 대상이
  되게 했다. 인간 한계 초과 fake-walk 코인을 예치하면 생산자가 소명 대기 등재된다.
- **V-2 — `/spot/deposit` 무제한 배열 DoS.** `body.coins` 길이 상한 100
  (`/sync/coins`의 500보다 낮춤 — 예치는 코인마다 전체 계보 검증이라 더 무겁다) +
  SPLIT 재귀 깊이 상한 32(verifyCoin 폭주 방지). 초과 시 코드 에러(자연어 금지).

**남는 위험 (근본 완화는 결정 대기 — 아래 R-스팟-현장결속):**
- **V-1 — 현장 결속 없음(원격 청구/Sybil).** 스캔 청구는 **spotId만 알면 원격으로
  가능**하다. 서버는 위치를 볼 수 없다는 **헌법 제9조**의 직접 귀결로 스캐너가 실제로
  스팟에 있는지 증명할 수 없다. 즉 "벽 QR 스캔"은 위치 증명이 아니라 spotId 취득
  수단일 뿐이며, `GET /spot`이 spotId·위치를 공개하므로 스캔 없이도 청구가 성립한다.
  → 이는 사업자의 **방문 유인**을 무력화한다(집에서, 혹은 Sybil 계정 다수로 슬롯을
  원격 소진). **완화로 넣은 것**: 회원당 청구 버스트 상한(창 내 최근 청구 수 대조 —
  1인 계정의 대량 원격 자동화만 무디게 한다). **한계**: Sybil은 계정이 다수라
  버스트 상한을 우회하고, 1인 원격 청구 자체도 못 막는다.
- **V-4 — 정찰(reconnaissance).** 공개 `GET /spot`이 스팟 **위치 + 예치 총액 +
  잔여 슬롯**을 인증 없이 드러낸다 → 어디에 얼마가 남았는지 원격 정찰이 가능하다.
  이는 맵에서 "걸어갈지 말지 결정"하게 하려는 **다니엘 쌤 결정 2번**(위치·규모 공개가
  기능 요건)의 귀결이라 제거하면 기능이 깨진다. 위험을 명시로 남긴다.

### 결정 대기 — R-스팟-현장결속 (다니엘 쌤)

V-1의 근본 완화는 **M9 몸-걸음 인증(현장 실시간 랜덤 지시 수행)을 스팟 청구에
결합**하는 것이다 — 그러면 "그 자리에서 몸으로 걷지 않으면 청구 불가"가 되어 원격·
Sybil 청구가 막힌다. 그러나 이는 **0층(설치하고 걸으면 끝)의 단순함**과 상충할 수
있고(레스토랑·주유소 QR은 트레킹과 무관한 즉시 스캔이 원안), 스팟마다 몸 인증을
필수화할지·일부만 할지·무보상 스탬프와 어떻게 나눌지는 **제품 결정**이다.
→ **임의로 몸인증을 필수화하지 않는다.** 다니엘 쌤 결정 대기 항목으로 남긴다:
스팟 청구에 M9 몸-걸음 인증을 (전면/선택) 결합할 것인가, 아니면 V-1/V-4를
"게임적 동기 + 선착순 희소성 + 버스트 상한 + 투명성 공시"로 감수할 것인가.

## 5. 기능 계층 요약

| 계층 | 요구되는 것 | 목적 |
|---|---|---|
| **0. 기본 걷기** | 없음 — 설치뿐 | 코인 생성. 영원히 이대로 충분 |
| 1. 보물 마이닝 | 그 존에 가서 지시대로 움직이기 | 완주 동기 + 실걷기 보안 인증 |
| 2. 몸 인증 미션 | 지점에서 지시대로 움직이기 | 보상 없는 현장 실증 (자전거 인증 등) |
| 3. 자전거 모드 | 모드 선택 | 에너지 비례 보상 + 포인트 인증 |
| 4. QR 스팟 | 현장 QR 스캔 | 사업자 참여·코인 실수요·스탬프 |

0층은 신성불가침 — 위 계층이 0층의 단순함을 해치면 그 기능이 잘못된 것이다.
