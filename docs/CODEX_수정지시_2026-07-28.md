## 0. 먼저 — 이 작업은 잘한 부분이 많다

되돌리라는 지시가 아니다. **네 가지는 그대로 살린다:**

| 살릴 것 | 이유 |
|---|---|
| `@expo/app-integrity` 연동 | 무결성이 구조적으로 항상 UNVERIFIED이던 문제를 실제로 고쳤다 |
| `paymentAuthorization.ts` (지불 전 생체 확인) | fail-closed 설계가 정확하다. 생체 정보를 앱이 보지 않는 것도 맞다 |
| 만보기 **권한**까지 확인 | 센서가 있어도 권한 거부면 0 SHV이던 문제를 잡았다 (단 §4 오탐 수정 필요) |
| 위치 서비스 꺼짐 확인 · `#starting` 가드 · APK 빌드 준비 | 전부 정당한 개선 |

**발행량 계산은 한 글자도 안 건드렸다** — `params.ts`·`walkFilter.ts`·`ledger.ts`·`rates.ts`·`corridorEngine.ts`가 diff에 없다. 이스라엘 60일 완주 시뮬 수치도 동일하다. 그 판단은 옳았다.

문제는 **새로 켠 백그라운드 추적 하나**다. 그것이 두 가지 심각한 결과를 낳는다.

## 1. 【치명】 화면 끄고 걸으면 코인이 0이 된다

### 무엇이 문제인가

`startLocationUpdatesAsync` + `foregroundService`로 GPS는 계속 받는다. **그런데 만보기는 백그라운드에서 멈춘다.**

Expo 자신의 문서가 명시한다 (`node_modules/expo-sensors/src/Pedometer.ts:27`):

> Pedometer updates will **not** be delivered while the app is in the background.

라이브러리 원본도 같다:
- 안드로이드 `expo-sensors/android/.../SensorProxy.kt:99` — `OnActivityEntersBackground { onHostPause() }` → `stopObserving()`
- iOS `expo-sensors/ios/PedometerModule.swift:94` — `OnAppEntersBackground { stopUpdates() }`

한편 `walkService.ts`의 `#windowTimer`(60초 `setInterval`)는 **계속 돌아 창을 닫는다.** 결과:

```
화면 꺼진 동안의 모든 창 → steps: 0
  ↓
packages/shared/src/walkFilter.ts:64
  if (sample.steps === 0) return reject('NO_STEPS');
  ↓
전량 기각 → 0 SHV
```

화면을 다시 켜면 만보기가 누적 기준점부터 재개되어 걸음이 한 창에 몰리는데, **그 창마저 보폭 불일치(`STEP_DISTANCE_MISMATCH`)로 기각된다.**

### 왜 위험한가

사용자는 상단에 **"쉬빌 걷기 기록 중"** 알림을 보면서 하루를 걷고 **0 SHV**를 받는다.
직전 커밋(`2b2ff93`)에서 없앤 "조용한 0 SHV" 문제가 **더 큰 규모로 되살아났다.**
헌법 제3조(정직화)·제6조 위반이다 — 앱이 되고 있다고 말하면서 안 되고 있다.

### 왜 테스트가 못 잡았나

**`walkService`에 테스트가 0건이다.** `apps/wallet/src/core/__tests__/` 22개 중 없다.
코인이 만들어지는 유일한 입구가 회귀 그물 밖이라 1,080개가 전부 통과했다.

### ★수정 방향 — 권고: (A)

#### (A) 백그라운드 위치 추적을 뺀다 ← **권고**

가장 정직하고, **§2 문제도 함께 사라진다.**

- `TaskManager.defineTask` / `startLocationUpdatesAsync` / `foregroundService` 제거
- `watchPositionAsync` 포그라운드 추적으로 복귀 (원래 동작)
- 화면 문구를 사실대로: "**화면을 켜 둔 채 걸어 주세요.** 화면이 꺼지면 걸음이 기록되지 않습니다."
- ★이유를 함께 적어라 — "휴대폰 운영체제가 화면이 꺼지면 걸음 센서를 멈춥니다"

**남기되 끄는 방법도 가능하다**: 코드는 두되 기본 비활성 + 실험 기능 플래그.
단 **기본이 꺼져 있어야 하고**, 켤 때 위 두 문제를 사용자에게 알려야 한다.

#### (B) 백그라운드를 유지하려면 — 반드시 이 둘을 다 해야 한다

**(B-1) 백그라운드 동안 창을 닫지 마라.**
지금 구조의 핵심 오류는 **"걸음을 모른다"를 "걸음이 0이다"로 처리**하는 것이다.
`walkFilter`의 `steps === 0` 기각은 실시간 판정에서는 옳다(차량·스푸핑 배제).
그러나 백그라운드 구간의 걸음은 0이 아니라 **미상**이다.

→ 앱이 백그라운드로 가면 `#windowTimer`를 멈추고 GPS 픽스만 버퍼에 쌓는다.
→ 포그라운드 복귀 시 그 구간의 **누적 걸음 증분**을 얻어 창에 배분한다.

**(B-2) 누적 걸음 증분을 실제로 얻을 수 있는지 먼저 확인하라.**
★이것을 확인하지 않고 (B)를 구현하지 마라. 확인 항목:
- iOS: `CMPedometer.queryPedometerData(from:to:)`로 과거 구간 조회가 되는가?
  `expo-sensors`의 `Pedometer.getStepCountAsync(start, end)`가 이것을 노출하는가?
- 안드로이드: `TYPE_STEP_COUNTER`는 부팅 이후 누적값이라 백그라운드에서도 증가한다.
  `expo-sensors`가 이 누적값을 읽는 경로를 주는가? 없으면 네이티브 모듈이 필요한가?
- **얻을 수 없으면 (B)는 성립하지 않는다. (A)로 가라.**

배분된 걸음이 보폭 검사를 통과하는지도 확인해야 한다 —
한 창에 몰아넣으면 `STEP_DISTANCE_MISMATCH`가 난다. **창별로 시간 비례 배분**이 필요하다.

## 2. 【높음】 좌표가 디스크에 남는다 — 헌법 제9조 위반 + 사용자에게 거짓 고지

### 무엇이 문제인가

백그라운드 위치 경로는 안드로이드에서 반드시 `JobScheduler`를 거친다:

```
expo-location/android/.../LocationTaskConsumer.kt:265, 305
  → taskManagerUtils.scheduleJob(context, mTask, data)   // data = 위경도 PersistableBundle

expo-task-manager/android/.../TaskManagerUtils.java:203-205
  new JobInfo.Builder(jobId, jobService)
      .setExtras(extras)        // ← 위경도·고도·속도·타임스탬프
      .setPersisted(true)       // ← ★재부팅을 넘겨 디스크에 보존
```

`setPersisted(true)`는 안드로이드가 그 job의 extras를 **`/data/system/job/jobs.xml`에 기록**한다는 뜻이다. 좌표가 앱의 휘발성 버퍼를 벗어나 **OS 파일에 남는다.**

### 왜 특히 나쁜가

같은 코드가 사용자에게 이렇게 말한다 (`walkService.ts:133`):

> "좌표는 코스 판정 직후 폐기되고 거리와 걸음만 남습니다."

**사실이 아닌 것을 알림으로 고지하고 있다.** 헌법 제9조(위치 비저장)와 CLAUDE.md 10번("좌표는 휘발성 버퍼에서만") 위반이면서, 제3조(정직화) 위반이기도 하다.

### 수정 방향

- **§1의 (A)를 택하면 이 문제도 함께 사라진다.** 그것이 이 둘을 한 번에 푸는 이유다.
- (B)를 택한다면: `setPersisted(true)`는 `expo-task-manager` 안에 있어 우리가 못 바꾼다.
  `patch-package`로 패치하는 것은 취약하다(업그레이드마다 깨진다).
  **그 경우 알림 문구를 사실대로 고치고, 이 편차를 문서에 명시해야 한다** —
  그리고 그것은 헌법 위반을 감수하는 결정이므로 **다니엘 쌤 결재 사항**이다. 임의로 하지 마라.

## 3. 【중간】 `RECEIVE_BOOT_COMPLETED` 미선언 — 첫 백그라운드 픽스에서 터질 수 있다

안드로이드는 `setPersisted(true)` job을 스케줄하는 앱이 `RECEIVE_BOOT_COMPLETED` 권한을 갖고 있지 않으면 `JobScheduler.schedule()`에서 `IllegalArgumentException`을 던진다.

- `TaskManagerUtils.java:152-158`의 try/catch는 **`IllegalStateException`만** 잡는다
- `node_modules` 전체 grep 결과 이 권한 선언 **0건**
- 새 `app.json`의 `android.permissions`는 `ACTIVITY_RECOGNITION` 하나로 줄었다

**§1의 (A)를 택하면 무관해진다.** (B)를 택하면 `app.json`에 권한을 추가하고, 실기기에서 확인하라:
```
adb logcat | grep -i "TaskManagerUtils\|RECEIVE_BOOT"
```
※ prebuild 템플릿 매니페스트가 이 권한을 넣어 준다면 무해하다 — **미확인 가설이다.** 확인하고 판단하라.

## 4. 【중간】 iOS 만보기 권한 오탐 — 원래 되던 아이폰이 못 걷게 된다

### 무엇이 문제인가

```ts
const pedometerAvailable = hasPedometer && motionPermission?.status === 'granted';
```

이 값이 `false`면 `Pedometer.watchStepCount`를 **아예 구독하지 않는다**.
기존 코드는 권한 결과와 무관하게 구독했으므로 권한이 뒤늦게 떨어져도 스스로 살아났다.

- 안드로이드는 안전하다 — Q 미만은 빈 권한 배열이 `granted`로 집계되고, Q 이상은 `ACTIVITY_RECOGNITION` 정식 요청이다
- **iOS가 위험하다** — `EXMotionPermissionRequester.m`은 `CMPedometer.authorizationStatus()`가 `NotDetermined`면 `'undetermined'`를 돌려준다. 그 순간 `pedometerAvailable=false`로 **고정**되고 세션 내내 재확인하지 않는다 → 전 창 `NO_STEPS` → 0 SHV. 걷기를 껐다 켜야만 복구된다.

### 수정 방향

`watchStepCount`는 **조건 없이 구독**하고, `pedometerAvailable`은 **화면 표시용 플래그로만** 쓴다.
또는 첫 창 마감 시 권한을 한 번 더 확인해 재구독한다.

★화면 노출 자체는 정상이다 — `HomeScreen.tsx:103`·`WalkScreen.tsx:133`에서 경고가 실제로 보인다. 그 부분은 건드리지 마라.

## 5. 【중간】 성공한 시작이 빨간 '오류'로 표시된다

`walkService.ts:170-173`이 정상 시작인데도 `walkStartError`에 경고 문구를 넣는다:

```ts
wallet.setWalkRuntime({ walkTracking: true, walkStartError: '화면이 꺼지면 기록이 멈출 수 있습니다…' });
```

`HomeScreen.tsx:102`는 이 필드를 `styles.error`(굵은 빨강)에 ⚠를 붙여 렌더한다.
→ 정상 동작 중에 빨간 오류가 계속 보인다. **실패와 경고가 섞이면 진짜 실패가 묻힌다.**

### 수정 방향
`walkStartWarning` 같은 별도 필드를 두고 다른 스타일로 표시하라. `walkStartError`는 실패 전용으로 남긴다.

## 8. ★반드시 추가할 것 — `walkService` 테스트

이번 사고의 근본 원인이다. **235줄을 고쳤는데 테스트가 0건**이라 1,080개가 전부 통과했다.

최소한 이것들을 넣어라 (`apps/wallet/src/core/__tests__/walkService.test.ts`):

1. **★백그라운드 구간이 0 SHV가 되지 않는다** — 이번 결함의 회귀 테스트.
   (A)를 택했다면 "백그라운드에서는 추적하지 않는다"를 단언하라.
2. 만보기 권한 미상(`undetermined`)이어도 걸음 구독이 살아 있다 (§4 회귀)
3. 위치 권한 거부 시 사유가 상태로 나온다
4. 시작 실패 후 재시도가 가능하다 (`#starting` 가드가 안 막는다)
5. 오프라인·서버 없음에서 시작된다 (0층)
6. 정상 시작 시 `walkStartError`가 `null`이다 (§5 회귀)

## 11. 하지 말아야 할 것

- **발행량 계산을 건드리지 마라** — `params.ts`·`walkFilter.ts`·`ledger.ts`·`rates.ts`·`corridorEngine.ts`.
  지금까지 안 건드린 것이 옳았다. 건드리면 이스라엘 시뮬 수치가 바뀌고, 그것은 통화정책 변경이다.
- **`walkFilter.ts:64`의 `NO_STEPS` 기각을 완화하지 마라.** 그것은 차량·스푸핑 방어다.
  문제는 그 검사가 아니라 **"미상"을 "0"으로 넘기는 쪽**이다.
- **파라미터를 낮추지 마라** — 하루 상한·난이도 상한·GRANT 상한.
  낮추면 이미 만들어진 옛 코인이 소급해서 무효가 된다(`docs/소급무효화_경로.md`).
  올리는 방향만 안전하다.
- **테스트를 약화시켜 통과시키지 마라.** 기대값을 낮추거나 케이스를 지우는 것은
  방어를 지우는 것이다.
- **헌법 위반을 감수하는 결정을 임의로 하지 마라** (§2의 (B) 경로). 다니엘 쌤 결재 사항이다.
