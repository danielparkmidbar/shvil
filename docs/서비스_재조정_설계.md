# 서비스 재조정 설계 — 두 사이트·한 지갑, 각자의 주인에게

> 2026-07-14 다니엘 쌤 지시. 이 문서는 쉬빌엔젤/쉬빌리스트 사이트와 지갑의 기능을
> **서비스 주체 기준으로 전면 재배치**하는 설계서다. 코드 착수 전 다니엘 쌤 확인용.
> 헌법(돌판 십계명)과 작업지시서가 이 문서에 우선한다.

---

## 0. 지도 원리 (다니엘 쌤 말씀 그대로)

> "중요한 원리는 이것은 **선의 기반**이라는 것이다. 코인이 오가지만 사실 코인은
> 미래의 기대 이익이지, 현재 그것을 목적으로 쉬빌리스트와 엔젤이 존재하는 것이 아니다.
> 하지만 코인을 통해 이 무브먼트에 참여하는 사람이 많아지길 원한다."

설계 규칙으로 번역하면:

1. **모든 화면의 1순위는 환대와 여정이다. 코인은 2순위로 배치한다.**
   (예: 엔젤 홈의 첫 화면은 "오는 손님"이지 "코인 잔액"이 아니다.)
2. **사이트는 문이고, 지갑이 집이다.** 양쪽 모두 사이트는 가입할 때 들르는 곳,
   가입 후의 모든 관계(신청·승인·정보·감사)는 지갑을 통해 흐른다.
3. **각 사이트는 자기 주체만 섬긴다.** 엔젤의 일이 리스트 사이트에, 리스트의 일이
   엔젤 사이트에 섞이지 않는다.

## 0-1. 확정: 웹 로그인은 만들지 않는다 (2026-07-14 다니엘 쌤 위임 → 개발팀 결정)

다니엘 쌤이 "웹 로그인 시 앱과 기능 동일" vs "웹은 설명·가입·다운로드만" 중 설계를
위임함. **후자 채택 + 웹 로그인 자체를 만들지 않음.** 근거:

1. **열쇠가 폰에 있다**: 코인 서명·회원 증서·E2E 메시지 키는 기기 전용. 웹에서 회원
   기능을 하려면 키를 서버/브라우저로 복사해야 하며, 이는 "두 기기 간 서명으로 거래
   완결" 원칙(헌법)을 깬다. 웹 로그인 전면 기능은 보안을 깨야만 가능하다.
2. **비밀번호 제로 시스템 유지**: 현재 시스템에 비밀번호가 없다(OTP+기기 서명).
   웹 계정을 만들면 비밀번호·세션·피싱 공격면이 통째로 생긴다.
3. 걷기·GPS·QR 대면 지불은 물리적으로 폰의 것이다.
4. 무투자 원칙 = 작은 팀 — 기능 이중 구현은 개발·감사 부담 2배.

**"양쪽 기능 거의 같게"는 웹 로그인이 아니라 지갑의 이중 모드(리스트/엔젤)로 이룬다**
— 누구나 한 앱에서 양쪽 역할을 수행한다 (호혜 원칙 7조와 정합).

| 표면 | 역할 |
|---|---|
| 두 웹 (로그인 없음, 계정 없음) | 비전 설명 · 공개 열람(지도 대략위치·코스·리더보드·투명성) · 가입 시작 · 앱 다운로드 (QR) |
| 지갑 앱 | 모든 회원 기능: 가입 완결·걷기·코인·지불·예약·메시지·별점·감사 카드·마켓·캘린더 |

웹은 개인정보를 아무것도 저장하지 않는다 — 계정 자체가 없으므로.

### 웹 콘텐츠 원칙 — "여행 전엔 노트북, 여행 중엔 폰" (2026-07-14 다니엘 쌤)

웹은 **여행을 준비하는 과정**을 섬긴다. 노트북 큰 화면을 전제로:
- **큰 이미지의 사진** — 트레일 풍경·환대의 장면이 첫 화면을 채운다
- **게시판의 글** — 동행 모집, 여정기, 커뮤니티 소식을 편히 읽는 넓은 본문
- **트레일 지도** — 화면 가득 펼쳐 전체 여정을 한눈에 보는 와이드 지도
- 한눈에 보는 정보 밀도: 표·비교·개요 중심 (모바일 축약형이 아니라 데스크톱 우선 설계)

여행이 시작되면 모든 것은 폰(지갑 앱)으로 — 걷기·지불·예약·메시지·정산.
반응형은 유지하되, 웹의 기준 화면은 데스크톱이다.

## 1. 두 주체의 여정 (다니엘 쌤 서사 → 확정 사용자 흐름)

### 1-1. 쉬빌엔젤의 여정 (shvilangel.org → 엔젤 지갑)

```
[사이트 — 가입까지만]
① shvilangel.org 방문
② 내 집 주변 트레일 선택 + 언어 선택
③ 지도에서 이웃 엔젤들 확인 (닉네임 + 제공 서비스 정도만 — 엔젤끼리는 이 수준이면 충분)
④ 내 집 주소/마을 이름 입력 → 지도에 자동 핀 → 핀 손으로 미세 조정
⑤ 지갑 다운로드 안내 → 최소 개인정보 입력 (전화 OTP + 이메일 — 지시서 확정)
⑥ 제공 가능한 서비스 등록 (잠자리 유형·식사·샤워·인터넷·수용 인원·조건)
⑦ 완료 → 내 집이 엔젤로 지도에 게시됨
[이후 — 전부 지갑에서]
⑧ 투숙 신청 수신 (알림) → 일정 확인 → 승인/거부
⑨ 승인 시 신청자 정보 열람 (신청자가 동의해 첨부한 프로필)
⑩ 접대 → 코인 수령 (대면 QR) → 감사 카드 수신
⑪ 모인 코인을 마켓에 판매 (무정가 리스팅 → 가격 제시 → 승인 → USDC)
⑫ 캘린더 관리 (가능/불가 날짜), 별점·후기 확인
```

### 1-2. 쉬빌리스트의 여정 (shvilist.org → 리스트 지갑)

```
[사이트 — 가입까지만]
① shvilist.org 방문 (예: 이스라엘 국가 트레일을 걸으려는 사람)
② 회원 가입 + 지갑 다운로드
③ 트레일 시작 지역 검색 → 그 지역 엔젤들 + 예약 가능 여부 표시
④ 엔젤 클릭 → 제공 서비스·별점·감사 카드(공개분) 확인
⑤ 출발지·종착지 입력 → 예상 채굴 코인 미리 계산
⑥ 전체 여정을 포인트-포인트로 계획 (구간별 엔젤 후보 지정)
[이후 — 전부 지갑에서]
⑦ 투숙 신청 발송 → 엔젤의 승인/거부 회신 수신
⑧ 걷기 시작 → 코인 적립 (예약 없어도, 노숙해도 코인은 생긴다 — 원칙 유지)
⑨ 접대받음 → 대면 QR 지불 → 감사 카드 발송
⑩ 완주 → 커뮤니티에 완주 알림 → 엑스트라 코인 (격려 코인)
⑪ 등록을 잊었으면 증빙 올려 클레임 → 커뮤니티 인정 → 코인
⑫ 도네이션 / 마켓 판매 / 동행 팀 만들기
```

## 3. 헌법·지시서 정합성 검토 (신규 기능이 원칙을 깨지 않는가)

| 신규 기능 | 원칙 충돌 검토 | 판정 |
|---|---|---|
| 투숙 신청/승인 | 서버가 "거래 승인"을 하게 되는가? → **아니다.** 예약은 코인 거래가 아니라 **사람 사이의 일정 약속**이다. 신청·승인은 E2E 메시지(구조화된 카드)로 두 사람 사이에 오가고, 서버는 릴레이만 한다. 코인 지불은 지금처럼 대면 QR 서명 교환으로 완결 | ✅ |
| 예약 가능 캘린더 | 위치 추적인가? → 아니다. 엔젤이 **자발 공개**하는 가능/불가 날짜뿐. 다만 "언제 집이 비는지"가 공개되는 부작용이 있으므로 **기본은 '가능 여부'만 공개**(구체 날짜는 신청자에게만) 권장 | ✅ 조건부 |
| 신청자 정보 열람 | 개인정보 최소 수집 위반? → 서버에 저장하지 않는다. 신청자가 **동의하고 선택한 프로필 항목**을 E2E 메시지에 첨부해 엔젤에게만 전달. 서버는 암호문만 중계 | ✅ |
| 상호 별점 | 커뮤니티 모니터링의 일부로 정합. 단 **보복 방지**: 양쪽 모두 제출 후(또는 14일 후) 동시 공개하는 이중 봉인 방식 권장 | ✅ 설계 필요 |
| 감사 카드 | 메신저의 특수 메시지 타입. 엔젤이 공개를 선택하면 프로필의 "게스트북"에 게시 | ✅ |
| 예상 코인 계산기 | 확정 요율(1km=1SHV×난이도, 일 40 상한)로 클라이언트가 계산. 서버 승인 없음. **"예상치이며 실제 걸음으로만 확정"을 명시** | ✅ |
| 동행 팀 | 게시판(서버) + 팀 채팅. 그룹 E2E는 후속 단계로 (초기: 게시판 + 1:1 메시지) | ✅ 단계적 |

**결론: 전부 헌법 안에서 구현 가능하다.** 서버에 새로 생기는 것은 ①투숙 신청 릴레이(암호문)
②캘린더 가능 여부(자발 공개) ③별점 집계 ④동행 게시판 — 어느 것도 거래 승인·위치 추적이 아니다.

## 4. 신규 기능 상세 설계

### 4-1. 엔젤 등록 흐름 (사이트에서 시작, 지갑에서 완결)
- 사이트는 **미리보기와 안내까지만**: 트레일 선택 → 주소/마을 입력(지오코딩) → 핀 확인.
- 실제 등록(서명 필요)은 지갑에서: 사이트가 입력값을 QR/딥링크로 지갑에 넘김 →
  지갑이 PUT /angels/me 서명 호출. (웹은 개인키가 없으므로 등록 권한이 없다 — 보안 유지)
- 주소 문자열은 **서버에 저장하지 않는다.** 좌표만 저장 (현행 유지).

### 4-2. 투숙 신청/승인 (지갑 메신저 확장)
- 새 메시지 타입 `BOOKING_REQUEST`: {날짜 범위, 인원, 동의한 프로필, 한마디}
- 새 메시지 타입 `BOOKING_REPLY`: {APPROVED / DECLINED / SUGGEST(대안 날짜), 한마디}
- 전부 E2E 암호화 — 서버는 내용을 볼 수 없다. 상태 표시는 지갑 로컬 + (선택) 엔젤이
  캘린더에 반영. 사이트의 "예약 가능 여부"는 캘린더 공개값을 읽는다.

### 4-3. 예상 코인 계산기
- 입력: 출발 포인트, 종착 포인트 (코스 위 지점 선택)
- 계산: 코스 폴리라인로 구간 거리 × 난이도 계수, 일 상한 40 SHV 반영한 일수별 시뮬레이션
- 출력: "약 N SHV (D일 기준)" + "예상치입니다. 코인은 실제 걸음으로만 생성됩니다."

### 4-4. 상호 별점
- 투숙이 실제 있었던 관계에서만 평가 가능 (감사 카드 or 대면 지불 이력 기준)
- 이중 봉인: 양쪽 제출 완료(또는 기한) 시 동시 공개 — 보복 별점 방지
- 표시: 엔젤 프로필(리스트가 봄), 리스트 프로필(엔젤이 신청 승인 때 봄)

### 4-5. 감사 카드
- 메시지 타입 `THANKS_CARD`: 템플릿(쪽지 느낌) + 자필 텍스트 + 여정 정보(선택)
- 엔젤이 "공개" 선택 시 프로필 게스트북에 게시 (빈집 방명록의 디지털판 —
  다니엘 쌤 경험: 엔젤이 빈집을 내어주면 리스트들이 쪽지·감사 카드를 남기고 간다)

### 4-6. 동행 찾기 (팀)
- shvilist.org 게시판: 내 여정(구간·날짜) 공개 + "함께 걸을 사람" 모집
- 팀은 3~4인 권장 표기 (신뢰도 — 다니엘 쌤 경험)
- 지갑: 팀원끼리 1:1 메시지 (그룹 채팅은 후속)
- 후속 아이디어: 팀 단위 투숙 신청 (엔젤 입장에서 3~4인 팀이 더 신뢰됨)

## 5. 구현 마일스톤 제안 (M5~M8)

| 단계 | 내용 | 규모 |
|---|---|---|
| **M5. 사이트 재배치** | 지도를 shvilist.org로 이관+예약가능 배지 자리, shvilangel.org에 "엔젤 되기" 흐름(주소→핀→지갑 연결), 투명성 양쪽 배치, 문구를 "선의 우선" 어조로 정비 | 중 |
| **M6. 예약** | 캘린더(엔젤 지갑+서버 공개값) + BOOKING_REQUEST/REPLY 메시지 + 지갑 손님 탭/여정 탭 | 대 |
| **M7. 신뢰 계층** | 상호 별점(이중 봉인) + 감사 카드 + 게스트북 | 중 |
| **M8. 동행·계산기** | 동행 게시판 + 예상 코인 계산기 + 팀 투숙 신청 | 중 |

각 단계 완료 기준: 테스트 통과 + 실 HTTP E2E 시나리오 갱신 + 다니엘 쌤 화면 확인.
